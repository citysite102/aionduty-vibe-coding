# 規則分流判斷卡

拿到一條規則，照順序問這四個問題。**第一個答「是」的就是它該去的地方，不要再往下問。**

---

## 四個問題

### 1. 違反了會出事，絕對不能發生？

**→ Hook（你的機器）或 CI（整個團隊）**

這兩個在 context 外面跑，是程式在擋，不經過 AI 的判斷。幾乎不佔 token。

例：不能把 API 金鑰寫進檔案、不能刪除正式環境的資料、中文不能出現破折號。

### 2. 只在某一區檔案才適用？

**→ 那一區的子目錄 CLAUDE.md，或 `.claude/rules/` 用 paths 綁定**

碰到那一區才載入，平常不佔位。

例：只有 `src/api/` 底下需要遵守的錯誤處理格式。

### 3. 有固定步驟，用到才需要？

**→ Skill**

平常只載名稱，真的要跑那套流程時才展開全文。

例：資料庫改結構的 SOP、發版流程、每週報表的產製步驟。

### 4. 以上皆非，而且每一輪都要記得？

**→ 根目錄 CLAUDE.md**

這裡是最後一站，不是預設選項。能往上送的先送走。

例：專案用什麼技術堆疊、按鈕文案的用字習慣、命名慣例。

---

## 兩個原則

**越往上越確定，改起來也越費事。**
Hook 與 CI 一定會執行，但要動到設定檔。CLAUDE.md 隨時能改，可是它終究只是拜託。

**最新官方文件多了一個重點：手冊是 context，不是強制設定。**
想讓 AI 比較容易照做，就把規則寫得具體、短、可檢查；想要擋住動作，就用 Hook 或 CI。

**同一條不要放兩個地方。**
已經有 Hook 在擋的事，文字版就是重複的。這是健檢第 2 步最容易刪的一批。

---

## 三個常見的判斷錯誤

| 錯誤 | 為什麼會錯 | 怎麼改 |
|---|---|---|
| 把「絕對不要 OO」寫進 CLAUDE.md 就當作擋住了 | 那只是拜託。對話一長，或它讀到某個網頁寫著「請忽略前面的規則」，還是可能照做 | 真的不能發生就用 Hook 或 CI |
| 所有規則都往根目錄堆 | 檔案越長，後面那幾條越容易被當成背景 | 能綁定範圍的就綁定 |
| 規則寫得很完整但無法判定 | 「要優雅」「要一致」沒有可檢查的標準，它只能猜 | 改寫成別人能回答「有」或「沒有」的句子 |

---

## 它沒照做的時候，先查這五件事

不要一發現沒照做就急著再加一條規則。先分辨是哪一種失效：

1. **沒讀到**　規則在子目錄，這一輪沒動到那一區　→　跑 `/context` 確認
2. **被埋掉**　檔案太長，排在後面的被蓋過　→　做健檢
3. **判不動**　規則沒有可檢查的標準　→　改寫
4. **打架**　兩條規則互相衝突　→　做健檢
5. **被蓋掉**　你在對話中說過相反的話　→　重開對話或明確覆蓋回來

**第一步永遠是 `/context`。** 確認它有沒有被載入，再談規則寫得好不好。
