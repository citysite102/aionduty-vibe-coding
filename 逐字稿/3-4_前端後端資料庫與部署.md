## Slide 24｜一次請求的完整流程：前端、後端與資料庫

**畫面**
情境切換列／模擬器：左邊前端卡（React 19、Tailwind、Browser ＋ Browser Console）、中間會跑封包的管線、右邊後端卡（Node.js、Express、Postgres（資料庫）＋ Server Log）／底部 Payload 預覽。

**逐字稿**

> 前端、後端、資料庫，這三個詞你大概聽過，但被問到差在哪的時候答不太出來，這很正常，因為光看名字看不出來。
>
> 名字先擺著不用記，這一頁用看的比用背的快。上面可以選情境，先看登入驗證。
>
> 模擬器上那一堆字你一個都不用讀懂。你只要盯一件事：那個小膠囊從哪裡飛到哪裡，中間停在誰身上。
>
> 左邊是前端，英文叫 Client，就是你看得到、點得到的那一層。右邊是後端，英文叫 Server，你看不到，它在別的地方跑。兩邊卡片下面那幾個小標籤是它們各自常用的工具，現在不用管，之後你交代工作的時候它會自己挑。
>
> 我按一次發送。
>
> 前端的 Console 先動：發送請求，攜帶帳號密碼。中間那個藍色的小膠囊就是這張點單紙，它從左邊飛到右邊。
>
> 到了右邊，後端的 Log 說：收到新請求。然後是處理中，正在比對密碼，並檢索使用者資料庫。這中間左邊那一層在做什麼？在等。它的 Log 寫著：請求已送達後端，正在等待處理結果。
>
> 接著綠色的膠囊往回飛，那是回應。後端說：驗證成功，產生安全憑證，準備回傳前端。前端收到之後解析 JSON，登入憑證儲存完畢，導向 Dashboard 畫面，最後是綠色的 200 OK。
>
> 底下這一條是剛才飛來飛去的那兩個膠囊裡面裝的東西。點單紙那一邊是 email 跟密碼，回來那一邊是一串憑證加上使用者名字。形狀你認得，就是上一段講的 JSON。
>
> 這一整趟的用處在哪裡？在於它壞掉的時候你問得出對的問題。
>
> 畫面按了沒反應、送出去之後對方沒回、資料查回來是錯的，這是三件不一樣的事，發生在三個不一樣的地方。分不出來的時候，你只能跟它說「還是壞的」，然後它就開始亂猜，三層都去動一遍。分得出來，你就能說「請求有送出去，但後端沒回」，範圍一下子縮掉三分之二。

**這頁的教學意圖**：看一次完整的來回，之後出事時分得出問題落在哪一層。
**預估時間**：5 分鐘

## Slide 25｜前端與後端各自負責什麼

**畫面**
上方情境切換列／三欄：左「前端負責」、中「API 來回傳什麼」、右「後端與資料庫」／每欄底下各一行「目標」／頁尾一句可以直接用的指令。

**逐字稿**

> 一樣從登入驗證看起，這一次三欄同時攤開。
>
> 我不逐條念，那些字你看得比我講的快。你要看的是形狀：同一件「登入」，左邊在管畫面，中間在管兩邊怎麼對話，右邊在管安全跟資料。三欄底下各有一行目標，那一行才是每一欄真正的職務。
>
> 我挑兩條講，因為它們解釋了你天天看到、但大概沒想過為什麼的事。
>
> 左邊那條「按下登入之後按鈕轉圈圈，不讓你連按三次」。你按下登入按鈕會轉一下、再按沒反應，就是這一條。它防的是你連按三下，後端收到三次請求。
>
> 右邊那條「密碼存的是算過的結果，不存你打的那串字」。這就是為什麼你忘記密碼的時候，網站只能讓你重設一組新的，沒辦法把舊的寄給你。它自己也不知道你的密碼是什麼，它手上那個值回推不回去。
>
> 你會發現凡是牽涉到「不能被別人看到」「不能被別人改」的，都在右邊那一欄。
>
> 上面還可以切到購物結帳跟搜尋篩選，換了情境，三欄的內容全換，但分工的形狀一模一樣：前端顧畫面跟防呆，API 負責約定欄位，後端跟資料庫扛安全跟資料。
>
> 這兩頁的用法就在最下面那一句。你不用自己去寫這三層，但你要知道一件事會牽動到哪幾層，才發得出完整的指令，也才驗收得了。
>
> 這也就是「不懂也做得出來，為什麼要學」的具體答案：學這三層不是為了自己寫，是為了發包的時候不漏掉一層。
>
> 所以你可以一次講完：「幫我實作登入驗證情境的前端介面，並開好對應的 API 與資料庫欄位。」而不是分三次講，每次都要自己想辦法接回去。

**這頁的教學意圖**：知道一件事牽動哪幾層，才發得出完整的指令。
**預估時間**：5 分鐘

## Slide 26｜全塞一張表，還是拆表用 id 串

**畫面**
開場一塊先定義資料庫（像 Excel，但會擋格式、而且兩張表對得起來）／左右對照：紅色「什麼都塞在同一張表」一張 orders.xlsx 加三個問題，綠色「一件事只存一個地方」三張小表加三個好處／綠色 Callout「所以你要看得懂的是這個」／頁尾「兩種資料庫，先認得名字就好」。

**逐字稿**

> 網頁一關掉，剛才輸入的東西就沒了。這件事每個自己做東西的人都會撞到一次，而且撞到的當下通常想不到是資料庫的問題，只覺得「我明明存過了」。
>
> 要留住，就得寫進資料庫。那資料庫到底是什麼？這個詞前面出現過好幾次，我一直沒有正面講。
>
> 它就是一個專門用來長期放資料的地方。你先把它想成 Excel，那個想像有八成是對的：一張表，最上面那列是欄位名稱，底下每一列是一筆資料。
>
> 剩下那兩成是差別。第一，你在 Excel 的電話欄位打中文它不會攔你，資料庫會，因為你事先說過那一欄只能放電話。第二，Excel 的兩個分頁基本上是各自獨立的，資料庫的兩張表可以互相對應，這一頁右半邊整個就是在做這件事。
>
> 但把東西寫進去只是第一步。同一批資料，擺法不一樣，今天看起來一模一樣；差別要等到你想改一筆客戶資料、或者想算某一項東西賣了幾份的時候才冒出來。
>
> 左邊是沒有設計的樣子，就一張表，像一份 Excel。客戶、電話、品項三個欄位，三筆訂單。
>
> 三個問題。第一，同一個客戶重複寫在每一列。王小明出現兩次，電話也跟著抄兩次。他換電話，你要一列一列改，漏掉一列就有兩個電話並存。
>
> 第二，你看第三列，名字打錯一個字，王小明變成王小名；電話少了那兩個橫線。對系統來說這就是另外一個人，這個人的消費紀錄從此對不起來。
>
> 第三，第一列的品項是「牛肉麵逗號滷蛋」，兩樣東西擠在同一格。要算滷蛋賣了幾份，只能一格一格用眼睛看。
>
> 這三個問題長得不一樣，根是同一個：同一件事被存了不只一份。
>
> 右邊是拆過的。一件事只存一個地方，其他人用 id 指過去。
>
> 先講 id 是什麼，因為這一頁其他東西全掛在它上面。id 就是系統自己給每一筆資料的編號，一筆一個，不重複，而且它不會因為你改名字、改電話就跟著變。它的職務只有一個：永遠指得到同一筆。
>
> 所以客戶表只有一列，編號 1，王小明，電話只存這一份。訂單表那一欄 customer_id 寫的就是 1，兩筆訂單都指向同一個人，名字一次都沒有再抄。再下面 order_items，一份餐點一列。
>
> 右邊那三個好處我不念，它們就是左邊那三個問題各自反過來。換來的是同一句話：一件事只存一份，要改的時候只要改那一份。
>
> 那你要做什麼？你不用會寫 SQL，這件事我可以很肯定地說。
>
> 但 AI 不會主動問你要哪一種。你只說「幫我做一個訂單系統」，它給你的很可能就是左邊那張什麼都塞在一起的表，而且它會跑得很好，你當下看不出問題。等到資料存了三個月才發現，表要重拆，已經寫進去的每一筆也要跟著搬，那時候的成本跟現在完全不是同一個量級。
>
> 所以你要做的只有一件事，而且它數得出來：AI 給你一張表的時候，看同一個人的名字有沒有出現在兩列以上。有，就是左邊那種，叫它拆。
>
> 擋的時候這樣講，這句可以直接抄：「客戶資料不要重複寫在每一筆訂單裡，拆成一張客戶表，訂單用 id 指過去。客戶被刪掉的時候，他的訂單要一起刪嗎，你有處理嗎？」
>
> 最後這一塊只要認得名字。一種叫關聯式，大家習慣直接叫它 SQL，因為它用的查詢語言就叫 SQL，代表是 PostgreSQL 跟 MySQL。每張表有哪些欄位要先講好，好處是它會幫你擋掉對不起來的資料。訂單、金流這種不能錯的東西用它。
>
> 非關聯式，NoSQL，MongoDB、Firestore。每一筆想放什麼就放什麼，開發的時候很快，代價是沒有人幫你把關。
>
> 沒有特別理由就選 SQL。但底下那一句比選哪一種更要緊：會不會出事，看的是資料有沒有拆開。

**這頁的教學意圖**：你不用會寫 SQL，但你要看得懂它給的表，才擋得下來。
**預估時間**：6 分鐘

## Slide 27｜從本機到上線：交給託管平台

**畫面**
「本機能跑 ≠ 別人看得到」兩個對照框／中段兩張卡：Vercel、Supabase／下段「一句話發包給 Claude Code」的四步指令，以及一段「不是按一個鍵就好」／最後一塊「那第 2 步擋下來的金鑰，後來去哪了？」四格流程，加一個 muted Callout「但純前端的專案，金鑰藏不住」。

**逐字稿**

> 做出第一個東西之後，多數人的下一個動作是想傳給朋友看，然後就卡在這一頁。
>
> 先建立一個觀念：本機能跑，不等於別人看得到。
>
> 你在自己電腦上開那個網頁的時候，網址列是 localhost 冒號 5173 這種。關鍵在 localhost 那個字，它的意思是「這台電腦」，而「這台」指的是打開它的那一台，不是你的那一台。所以你把網址傳給朋友，他的電腦會去找他自己那一台，當然找不到。這是很多人第一次做完東西最困惑的地方：明明我這裡好好的。
>
> 右邊是解法：把東西放到一台一直開著、而且不是你那一台的電腦上。這一步就叫部署。好消息是你不用自己架伺服器，交給託管平台就好。課程最後你會把自己做的任務計時器走完這一步，拿到一個可以傳給別人的網址。
>
> 兩個平台。
>
> 左邊 Vercel，放網頁用的。連上 GitHub 之後，你每次更新程式碼，它就自動重新上線，你完全不用碰伺服器。
>
> 網址從哪來，這個問題常常有人問。它會直接送你一個免費的，長得像「你的專案名點 vercel 點 app」，馬上就能傳給別人。想換成自己的名字才要去買網域，那是另外一件事，而且不影響你先把東西傳出去。
>
> 下面還列了同類的 Netlify、Cloudflare Pages、GitHub Pages，做法幾乎一樣，挑一個就好。
>
> 右邊 Supabase，是你要存資料或要會員登入的時候用的。你不用自己架資料庫伺服器，也不用管備份跟維運。上一頁那些表就放在這種地方。這正是繞過「資料庫很複雜」的方法：別自己架，用託管的。
>
> 最下面是實際怎麼做。一句話發包給 Claude Code，但這一句話有四步。
>
> 先在本機開一次，確認畫面正常、沒有錯誤訊息。檢查資料夾裡有沒有不該公開的東西，金鑰、個人資料，有的話加進 .gitignore。建立 Git repository，做第一次 commit，推上我的 GitHub。連結 Vercel 完成部署。
>
> 然後是三句話交代規矩：需要我登入授權的時候停下來告訴我要點哪裡；完成後把上線網址給我，並確認那個網址真的打得開；中間任何一步失敗，用白話說明卡在哪，先不要自己重試。
>
> 這段指令長，是因為它把要做什麼、做完給我什麼、什麼時候該停下來都講完了。指令寫得完整，來回就少。
>
> 最後這一行要看清楚：不是按一個鍵就好。Agent 能幫你跑完上面四步，但中間你要自己登入 GitHub 和 Vercel 授權，那是你的帳號，它沒有辦法代你點同意。
>
> 我特別講這一句，是因為這種地方最容易讓人覺得「怎麼跟說好的不一樣」，然後以為自己哪裡做錯了。沒有做錯，那一步本來就該停在你這裡。省下來的是不用學那些指令，不是完全不用動手。
>
> 最後這一塊，是上面那段指令第 2 步留下來的缺口。它叫它把金鑰加進 .gitignore，擋住不要跟著推上去。擋住之後呢？你的網站上線了，程式還是要拿得到那把金鑰才打得動 API。
>
> 所以金鑰不跟著程式碼走，它自己有一條路，畫面上這四格就是。
>
> 第一格，你的電腦。金鑰寫在一個叫 `.env` 的檔案裡，你自己建一個，只有你這台有。
>
> 第二格，推上 GitHub 的時候。`.gitignore` 把 `.env` 列進去，git 就根本不會碰它，所以雲端那一份程式碼裡面沒有金鑰。
>
> 第三格，上線之後。同一組金鑰，你要到 Vercel 或 Supabase 的後台再填一次，那個欄位叫環境變數。平台跑你的程式的時候才把值餵進去。所以從頭到尾，金鑰沒有出現在任何一個會被別人拿到的檔案裡。
>
> 第四格方向不一樣。前三格擋的是別人，這一格擋的是 AI。在 `settings.json` 裡寫一條 deny，擋掉讀取 `.env`，它連看都看不到，也就不會在某一次回答裡順手把那串字貼出來。這一條第八章會實際掛一次。
>
> 這四格你現在不用做，因為你的計時器用的那支 API 不用金鑰。等你之後接一支要金鑰的，照這條路走就對了。
>
> 但最下面那個但書我一定要講，因為它是這一整塊最容易被誤會的地方：純前端的專案，金鑰藏不住。
>
> 程式碼被送到瀏覽器的那一刻，裡面的字串使用者打開開發者工具就看得到。你放在平台的環境變數也一樣，因為打包的時候它已經被寫進去了。環境變數擋得住「別人翻你的 GitHub」，擋不住「別人打開你的網站看原始碼」。
>
> 所以要金鑰的 API 有兩條路。要嘛用那種本來就設計成可以公開的金鑰，它能做的事由服務那一端的規則限制住；要嘛就得有一層後端替你保管，前端只跟你自己的後端講話。這個取捨案例三會實際走一次。

**這頁的教學意圖**：localhost 傳不出去；部署交給託管平台，但授權那一步只有你能做；金鑰有自己的一條路，而且純前端藏不住。
**預估時間**：7 分鐘

### 1.【矛盾】`10c_M1_WebArch` 寫著「下面三欄不用讀懂每一個字」，但這一頁畫面上沒有三欄（已驗證）

> **結果**：已處理（`f3a70ad`）。那句改成描述這一頁真的有的東西，順便刪掉九組沒人取用的死資料。

- `10c_M1_WebArch.tsx:315` 那段小字說「下面三欄⋯」，可是它下面是前端卡、中間的傳輸管線、後端卡，資料庫只以一個 `Postgres（資料庫）` 標籤出現在後端卡裡。
- **team-lead 查證確認根因**：`scenarios` 裡的 `frontendDuties`、`backendDuties`、`dbDuties` 三組資料在這個檔案完整定義了三個情境共九組，但**整頁的 JSX 從頭到尾沒有取用它們任何一次**（真正的三欄在下一頁 `10c2`）。那段提醒應該是跟著三欄一起搬走的，人留下來了。
- 後果是學員照字面往下找一個不存在的東西。
- **建議**：把那句改成描述這一頁真的有的（兩張卡與中間那一來一回），三層那句留給下一頁；同時刪掉這個檔案裡那三組死資料。

### 2.【矛盾】`10c2_M1_WebArchDuties:44` 還寫著「收到 Token 後安全儲存」（已驗證）

> **結果**：已處理（`f3a70ad`）。統一成登入憑證。

- `10c` 的前端 Log 已經統一成「登入憑證儲存完畢」，`10c2` 的前端第三條仍是 Token。
- 兩個問題：Token 在這裡第一次出現、沒有定義；而章節五會有另一個完全不同意思的 token（計費單位）。
- **建議**：改成「收到登入憑證後安全儲存」。Payload 預覽框裡的 `{"token": "..."}` 是 JSON 的欄位名，維持原樣沒關係。

### 3.【矛盾】`10c2` 的標題涵蓋不到畫面上的三分之二

> **結果**：已處理（`f3a70ad`）。標題改成「前端、API 與後端各自負責什麼」，`LIVE_TITLES` 同步。

- 標題是「前端與後端各自負責什麼」，但畫面是三欄：前端、API、後端與資料庫。反而是前一頁的標題寫了資料庫。

- **建議**：標題補上這兩樣。改的話 `LIVE_TITLES` 要一起改，而且要注意新標題的寬度上限（D-5 的 40 半形寬）。

### 4.【缺漏】`10c3_M1_Deploy` 的發包指令用到了下一頁才講的 Git 與 GitHub

> **結果**：已處理（`f3a70ad`）。指明第 3 步的 Git 是下一段的主題。

- 指令第 3 步是「建立 Git repository，做第一次 commit，推上我的 GitHub」，但 Git 在下一頁、GitHub 在再下一頁。
- 這是 `09b` 那張路線圖排出來的順序造成的（部署是第五站、Git 是第六站），不是單一頁的錯。逐字稿用「這兩個字是下一站」接過去。
- **建議**：不想動順序的話，在那段指令下面補半句說明 Git 是下一段的主題就夠。
