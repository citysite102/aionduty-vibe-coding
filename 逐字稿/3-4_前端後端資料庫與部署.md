## Slide 24｜一次請求的完整流程：前端、後端與資料庫

**畫面**
情境切換列／模擬器：左邊前端卡（React 19、Tailwind、Browser ＋ Browser Console）、中間會跑封包的管線、右邊後端卡（Node.js、Express、Postgres（資料庫）＋ Server Log）／底部 Payload 預覽。

**逐字稿**

> 前端、後端、資料庫，這三個詞你大概聽過，但被問到差在哪的時候答不太出來，這很正常，因為光看名字看不出來。
>
> 名字先擺著不用記，這一頁用看的比用背的快。上面可以選情境，先看登入驗證。
>
> 模擬器上那一堆字你一個都不用讀懂。你只要盯一件事：那個小膠囊從哪裡飛到哪裡，中間停在誰身上。
>
> 左邊是前端，英文叫 Client，就是你看得到、點得到的那一層。右邊是後端，英文叫 Server，你看不到，它在別的地方跑。兩邊卡片下面那幾個小標籤是它們各自常用的工具，現在不用管，之後你交代工作的時候它會自己挑。
>
> 我按一次發送。
>
> 前端的 Console 先動：發送請求，攜帶帳號密碼。中間那個藍色的小膠囊就是送出去的那一包，它從左邊飛到右邊。
>
> 到了右邊，後端的 Log 說：收到新請求。然後是處理中，正在比對密碼，並檢索使用者資料庫。這中間左邊那一層在做什麼？在等。它的 Log 寫著：請求已送達後端，正在等待處理結果。
>
> 接著綠色的膠囊往回飛，那是回應。後端說：驗證成功，產生安全憑證，準備回傳前端。前端收到之後解析 JSON，登入憑證儲存完畢，導向 Dashboard 畫面，最後是綠色的 200 OK。
>
> 底下這一條是剛才飛來飛去的那兩個膠囊裡面裝的東西。送出去那一邊是 email 跟密碼，回來那一邊是一串憑證加上使用者名字。形狀你認得，就是上一段講的 JSON。
>
> 上面那三個情境你可以自己切。我切到搜尋篩選，因為這裡有一個很多人誤會的地方，就寫在左邊那一行的括號裡。
>
> 你在搜尋框打字，還沒按下去就跳出來的那些關鍵字建議，也是這樣一來一回跑的，只是它跑的是另一支 API。你每停手一下，前端就送一次，後端只回一小包字串，前端把它畫成下拉選單。按下去之後才是這一頁在模擬的那一支，回來的是完整的商品資料。同一個搜尋框，兩支不一樣的請求。
>
> 這一整趟的用處在哪裡？在於它壞掉的時候你問得出對的問題。
>
> 我先擋一個誤會：這不是說你以後有辦法自己判斷問題出在哪一層。你不用判斷，你只要描述得出你看到什麼。畫面上那三種講法對應的就是剛才膠囊經過的三個地方，你挑一句講，就已經幫它省掉大半。
>
> 差在哪裡？你只說「它壞了」，Agent 手上沒有線索，只能三層都去動一遍，動完你還得從頭驗一次。你說「請求有送出去，但後端沒回」，範圍一下子縮掉三分之二，它知道要從哪裡開始看。

**這頁的教學意圖**：看一次完整的來回；之後出事時描述得出是哪一段，不是學會自己判斷。
**預估時間**：6 分鐘

## Slide 25｜前端與後端各自負責什麼

**畫面**
上方情境切換列／三欄：左「前端負責」、中「API 來回傳什麼」、右「後端與資料庫」／每欄底下各一行「目標」／頁尾一句可以直接用的指令。

**逐字稿**

> 一樣從登入驗證看起，這一次三欄同時攤開。
>
> 我不逐條念，那些字你看得比我講的快。你要看的是形狀：同一件「登入」，左邊在管畫面，中間在管兩邊怎麼對話，右邊在管安全跟資料。三欄底下各有一行目標，那一行才是每一欄真正的職務。
>
> 我挑兩條講，因為它們解釋了你天天看到、但大概沒想過為什麼的事。
>
> 左邊那條「按下登入之後按鈕轉圈圈，不讓你連按三次」。你按下登入按鈕會轉一下、再按沒反應，就是這一條。它防的是你連按三下，後端收到三次請求。
>
> 右邊那條「密碼存的是算過的結果，不存你打的那串字」。這就是為什麼你忘記密碼的時候，網站只能讓你重設一組新的，沒辦法把舊的寄給你。它自己也不知道你的密碼是什麼，它手上那個值回推不回去。
>
> 你會發現凡是牽涉到「不能被別人看到」「不能被別人改」的，都在右邊那一欄。
>
> 上面還可以切到購物結帳跟搜尋篩選，換了情境，三欄的內容全換，但分工的形狀一模一樣：前端顧畫面跟防呆，API 負責約定欄位，後端跟資料庫扛安全跟資料。
>
> 這兩頁的用法就在最下面那一句。你不用自己去寫這三層，但你要知道一件事會牽動到哪幾層，才發得出完整的指令，也才驗收得了。
>
> 這也就是「不懂也做得出來，為什麼要學」的具體答案：學這三層不是為了自己寫，是為了發包的時候不漏掉一層。
>
> 所以你可以一次講完：「幫我實作登入驗證情境的前端介面，並開好對應的 API 與資料庫欄位。」而不是分三次講，每次都要自己想辦法接回去。

**這頁的教學意圖**：知道一件事牽動哪幾層，才發得出完整的指令。
**預估時間**：5 分鐘

## Slide 26｜什麼是資料庫？

**畫面**
開場一塊：關掉就沒了，資料庫是專門長期放資料的地方，先想成 Excel／兩張卡「剩下那兩成，差在規則是你守還是它守」：會擋掉填錯的資料、不讓兩張表對不起來／一塊「兩種資料庫，先認得名字就好」（SQL／NoSQL）／sky Callout「你不用會寫 SQL，但它給你的表你要看得懂」。

**逐字稿**

> 網頁一關掉，剛才輸入的東西就沒了。這件事每個自己做東西的人都會撞到一次，而且撞到的當下通常想不到是資料庫的問題，只覺得「我明明存過了」。
>
> 要留住，就得寫進資料庫。那資料庫到底是什麼？這個詞前面出現過好幾次，我一直沒有正面講。
>
> 它就是一個專門用來長期放資料的地方。你先把它想成 Excel，那個想像有八成是對的：一張表，最上面那列是欄位名稱，底下每一列是一筆資料。
>
> 剩下那兩成是差別，就是中間這兩張卡。它們其實在講同一件事：規則是你守，還是它守。
>
> 第一，它會擋掉填錯的資料。你在 Excel 的電話欄位打中文，它不會攔你；資料庫會，因為你事先說過那一欄只能放電話。
>
> 第二，它不讓兩張表對不起來。這裡我先接一個問題，因為常用 Excel 的人馬上會想到：VLOOKUP 不是也查得到另一張分頁嗎？對，做得到，這件事試算表真的辦得到。差別不在做不做得到，在誰來保證它一直成立。
>
> VLOOKUP 是你寫在某一格裡的一條公式。來源那一列被刪掉，它就變成錯誤值；有人手動把那一格蓋掉，這個對應就消失了，而且不會有任何警告。資料庫是你一開始就講好「訂單要對到客戶」，講過這一次之後，你想寫一筆指向不存在客戶的訂單，它直接不收。
>
> 再來這一塊只要認得名字。一種叫關聯式，大家習慣直接叫它 SQL，因為它用的查詢語言就叫 SQL，代表是 PostgreSQL 跟 MySQL。每張表有哪些欄位、哪幾欄必填，要先講好。先講好的代價是之後想改欄位比較麻煩，換來的是它會退件：數字欄位塞了一句中文、必填的沒填、訂單指到一個不存在的客戶，它都不收。
>
> 它還保證一件事要嘛全做完、要嘛整個不算。你下一筆訂單，系統要同時扣庫存、建訂單、記一筆帳，這三件中間如果斷掉，它不會讓你只做一半。這一條才是訂單跟金流都用 SQL 的原因。
>
> 另一種叫非關聯式，NoSQL，MongoDB、Firestore。每一筆想放什麼就放什麼，欄位不用先講好，改需求的時候很快。
>
> 代價是剛才那些保護預設都不在。不是它做不到，是你要自己補：程式裡每一個會寫資料的地方都得自己寫一次檢查，漏掉一個地方就寫進去了。而且要把好幾張表湊在一起查的時候會很吃力。
>
> 沒有特別理由就選 SQL，訂單、金流、庫存這種寫錯了要人去善後的尤其是。這兩個名字你現在不用挑，知道它們是同一類東西的兩種做法就好。
>
> 最後這一塊是這一頁的立場：你不用會寫 SQL，這件事我可以很肯定地說。你不會自己去建資料表，那件事 AI 會做。
>
> 問題是它不會問你要怎麼擺。剛才講的那個客戶姓名電話，是抄進每一筆訂單裡，還是另外開一張客戶表、訂單只記編號？你只說「幫我做一個訂單系統」，它不會停下來問你，自己挑一種就開始寫了。

**這頁的教學意圖**：把「資料庫」這個從七項基礎就一直出現、卻沒被定義過的詞講清楚；跟 Excel 的差別不在做不做得到，在規則誰守；SQL 與 NoSQL 只要認得名字。
**預估時間**：5 分鐘

## Slide 27｜資料庫裡的資料怎麼擺

**畫面**
開場一句講差別什麼時候冒出來／左右對照：紅色「什麼都塞在同一張表」一張 orders.xlsx 加三個問題，綠色「一件事只存一個地方」三張小表加三個好處／綠色 Callout「它給你一張表的時候，數這一件事就好」。

**逐字稿**

> 同一批資料，擺法不一樣，今天看起來一模一樣；差別要等到你想改一筆客戶資料、或者想算某一項東西賣了幾份的時候才冒出來。
>
> 左邊是沒有設計的樣子，就一張表，像一份 Excel。客戶、電話、品項三個欄位，三筆訂單。
>
> 三個問題。第一，同一個客戶重複寫在每一列。王小明出現兩次，電話也跟著抄兩次。他換電話，你要一列一列改，漏掉一列就有兩個電話並存。
>
> 第二，你看第三列，名字打錯一個字，王小明變成王小名；電話少了那兩個橫線。對系統來說這就是另外一個人，這個人的消費紀錄從此對不起來。
>
> 第三，第一列的品項是「牛肉麵逗號滷蛋」，兩樣東西擠在同一格。要算滷蛋賣了幾份，只能一格一格用眼睛看。
>
> 這三個問題長得不一樣，根是同一個：同一件事被存了不只一份。
>
> 右邊是拆過的。一件事只存一個地方，其他人用 id 指過去。
>
> 先講 id 是什麼，因為這一頁其他東西全掛在它上面。id 就是系統自己給每一筆資料的編號，一筆一個，不重複，而且它不會因為你改名字、改電話就跟著變。它的職務只有一個：永遠指得到同一筆。
>
> 所以客戶表只有一列，編號 1，王小明，電話只存這一份。訂單表那一欄 customer_id 寫的就是 1，兩筆訂單都指向同一個人，名字一次都沒有再抄。再下面 order_items，一份餐點一列。
>
> 右邊那三個好處我不念，它們就是左邊那三個問題各自反過來。換來的是同一句話：一件事只存一份，要改的時候只要改那一份。
>
> 最後這一塊是這兩頁真正要你帶走的動作，而且它數得出來：它給你一張表的時候，看同一個人的名字有沒有出現在兩列以上。有，就是左邊那一種，叫它拆。
>
> 是的話這樣講，這句可以直接抄：「客戶資料不要重複寫在每一筆訂單裡，拆成一張客戶表，訂單用 id 指過去。客戶被刪掉的時候，他的訂單要一起刪嗎，你有處理嗎？」
>
> 為什麼要在第一天就擋？因為等到資料存了三個月才發現，表要重拆，已經寫進去的每一筆也要跟著搬，那時候的成本跟現在完全不是同一個量級。

**這頁的教學意圖**：擺法的差別什麼時候會冒出來；收尾是一個數得出來的動作，不是「看得懂就擋得下來」。
**預估時間**：5 分鐘

## Slide 28｜從本機到上線：交給託管平台

**畫面**
「本機能跑 ≠ 別人看得到」兩個對照框／中段兩張卡：Vercel、Supabase／下段「一句話發包給 Claude Code」的四步指令，以及一段「不是按一個鍵就好」／最後一塊「那第 2 步擋下來的金鑰，後來去哪了？」四格流程（每一格右上角標著「你自己做」或「可以發包」），加一個 muted Callout「但純前端的專案，金鑰藏不住」。

**逐字稿**

> 做出第一個東西之後，多數人的下一個動作是想傳給朋友看，然後就卡在這一頁。
>
> 先建立一個觀念：本機能跑，不等於別人看得到。
>
> 你在自己電腦上開那個網頁的時候，網址列是 localhost 冒號 5173 這種。關鍵在 localhost 那個字，它的意思是「這台電腦」，而「這台」指的是打開它的那一台，不是你的那一台。所以你把網址傳給朋友，他的電腦會去找他自己那一台，當然找不到。這是很多人第一次做完東西最困惑的地方：明明我這裡好好的。
>
> 右邊是解法：把東西放到一台一直開著、而且不是你那一台的電腦上。這一步就叫部署。好消息是你不用自己架伺服器，交給託管平台就好。課程最後你會把自己做的任務計時器走完這一步，拿到一個可以傳給別人的網址。
>
> 兩個平台。
>
> 左邊 Vercel，放網頁用的。連上 GitHub 之後，你每次更新程式碼，它就自動重新上線，你完全不用碰伺服器。
>
> 網址從哪來，這個問題常常有人問。它會直接送你一個免費的，長得像「你的專案名點 vercel 點 app」，馬上就能傳給別人。想換成自己的名字才要去買網域，那是另外一件事，而且不影響你先把東西傳出去。
>
> 下面還列了同類的 Netlify、Cloudflare Pages、GitHub Pages，做法幾乎一樣，挑一個就好。
>
> 右邊 Supabase，是你要存資料或要會員登入的時候用的。你不用自己架資料庫伺服器，也不用管備份跟維運。上一頁那些表就放在這種地方。這正是繞過「資料庫很複雜」的方法：別自己架，用託管的。
>
> 最下面是實際怎麼做。一句話發包給 Claude Code，但這一句話有四步。
>
> 先在本機開一次，確認畫面正常、沒有錯誤訊息。檢查資料夾裡有沒有不該公開的東西，金鑰、個人資料，有的話加進 .gitignore。建立 Git repository，做第一次 commit，推上我的 GitHub。連結 Vercel 完成部署。
>
> 然後是三句話交代規矩：需要我登入授權的時候停下來告訴我要點哪裡；完成後把上線網址給我，並確認那個網址真的打得開；中間任何一步失敗，用白話說明卡在哪，先不要自己重試。
>
> 這段指令長，是因為它把要做什麼、做完給我什麼、什麼時候該停下來都講完了。指令寫得完整，來回就少。
>
> 最後這一行要看清楚：不是按一個鍵就好。Agent 能幫你跑完上面四步，但中間你要自己登入 GitHub 和 Vercel 授權，那是你的帳號，它沒有辦法代你點同意。
>
> 我特別講這一句，是因為這種地方最容易讓人覺得「怎麼跟說好的不一樣」，然後以為自己哪裡做錯了。沒有做錯，那一步本來就該停在你這裡。省下來的是不用學那些指令，不是完全不用動手。
>
> 最後這一塊，是上面那段指令第 2 步留下來的缺口。它叫它把金鑰加進 .gitignore，擋住不要跟著推上去。擋住之後呢？你的網站上線了，程式還是要拿得到那把金鑰才打得動 API。
>
> 講這四格之前，我先把金鑰這個東西重新講一次，因為前面提過，但那是好幾頁以前的事，而且到現在你手上一把都還沒有。
>
> 一把金鑰就是一串字，長得像 `sk` 開頭再接一長串亂碼。它不是加密過的密碼，它就是一張通行證：誰拿著這串字，對方的伺服器就把他當成你。
>
> 你什麼時候會拿到？你去申請一支要收費或要認人的 API 的時候。地圖、寄信、金流、翻譯、AI 模型，這些都要。申請完它給你那一串字，不少服務只讓你看一次，關掉頁面就要重新產一把。你的計時器現在用的那支天氣 API 不用金鑰，所以你還沒撞到這件事。
>
> 那它外流會怎樣？不是「有點危險」這種講法，是很具體的三件事。第一，那串字多半綁著你的付款方式或你的用量額度，別人撿去打，帳單算你的。第二，沒有登出這回事，你只能去後台把那一把作廢、再產一把新的，然後把所有用到它的地方全部換過。第三，公開的 GitHub repo 會被機器人掃，專門找的就是這種字串，這不是假設性的風險。
>
> 所以金鑰不跟著程式碼走，它自己有一條路，畫面上這四格就是。
>
> 先看每一格右上角，有的寫「你自己做」，有的寫「可以發包」。這條線怎麼劃，比四個步驟本身還重要：那串金鑰本人會經手的，你自己做；只是改一個設定檔的，叫它做沒差。
>
> 我說一下為什麼要特別標。這一整章都在教你怎麼發包，走到這裡很自然會想「那金鑰也一起交給它處理」，然後把那串字貼進對話框，請它幫你寫進檔案裡。貼下去的那一刻，這把金鑰就送出去了一次，而且留在你的對話紀錄裡。前面三格的防護，在這一步全部白做。
>
> 第一格，你的電腦。金鑰放在一個叫 `.env` 的檔案裡。檔案本身可以叫 AI 幫你建，那只是一個空殼；但裡面那串字要你自己填進去，填在編輯器裡，不是貼在對話框裡。
>
> 第二格，推上 GitHub 的時候。`.gitignore` 這個字這裡第一次出現，它是一份你自己列的清單，放在專案資料夾裡，寫進去的檔案 git 根本不會碰。所以你把 `.env` 列進去，雲端那一份程式碼裡面就沒有金鑰。這一格從頭到尾沒有碰到金鑰本人，交給它做。
>
> 第三格，上線之後。同一組金鑰，你要到 Vercel 或 Supabase 的後台再填一次，那個欄位叫環境變數。平台跑你的程式的時候才把值餵進去。所以從頭到尾，金鑰沒有出現在任何一個會被別人拿到的檔案裡。這一格也是你自己做，而且多一個理由：那是你登入的後台，跟剛才講的授權一樣，它進不去。
>
> 第四格方向不一樣。前三格擋的是別人，這一格擋的是 AI。在 `settings.json` 裡寫一條 deny，擋掉讀取 `.env`，它連看都看不到，也就不會在某一次回答裡順手把那串字貼出來。這一格也只是改設定檔，一樣可以交給它。這一條第八章會實際掛一次。
>
> 這四格你現在不用做，因為你的計時器用的那支 API 不用金鑰。但你之後一定會接到要金鑰的，所以我把三種情境攤開來講，你對照自己在哪一種。
>
> 第一種，東西只在你自己電腦上跑，沒有要給別人看。這種最單純，`.env` 就夠了，金鑰從頭到尾沒離開過這台機器。四格裡你只會用到第一格跟第四格。
>
> 第二種，推上 GitHub，用 Vercel 上線，而且是純前端的網頁，也就是沒有後端那一層。這一種最容易出事，就是畫面最下面那個但書在講的：純前端的專案，金鑰藏不住。
>
> 為什麼？因為純前端的程式最後會被打包成一包檔案，送到每一個訪客的瀏覽器裡。你寫在環境變數的那串字，打包的時候就被寫進那包檔案了。訪客按 F12 打開開發者工具，翻一下就看得到。環境變數擋得住「別人去翻你的 GitHub」，擋不住「別人打開你的網站看原始碼」。這兩件事常常被當成同一件。
>
> 所以第二種情境的解法不是藏得更好，是換一把金鑰。很多服務會給你兩把：一把設計上就是要放在瀏覽器裡給人看的，它能做什麼由你在對方後台設的規則決定，例如只能讀、不能寫、只能讀你指定的那幾張表；另一把權限全開、繞得過所有規則，那一把絕對不能進前端。Supabase 就是這樣發的，你註冊完在後台會看到它們分開列著。拿錯把是這一類意外最常見的原因。
>
> 第三種，你有一層後端，或是用 Supabase 這種把後端一起託管掉的服務。這一種最乾淨：金鑰只放在後端那一側，前端只跟你自己的後端講話，那串字從來不會送到任何人的瀏覽器。需要保密的金鑰就走這條路，沒有第二個選擇。
>
> 三種情境的判準只有一句：那串字最後會不會被送到瀏覽器。會，就只能放可以公開的那一把；不會，才輪得到你自己保管。這個取捨案例三會實際走一次。

**這頁的教學意圖**：localhost 傳不出去；部署交給託管平台，但授權那一步只有你能做；金鑰是一張通行證，它有自己的一條路，碰得到金鑰本人的那兩段不能發包；三種情境的判準是那串字會不會被送到瀏覽器。
**預估時間**：10 分鐘
