## Slide 54｜讓 AI 有工具可用：MCP 與 Skills

**畫面**
開場一句講兩者的分工。左右兩卡：MCP（標準化環境擴充）與 Skills（工作流程封裝），各附一張架構示意。中段一塊「底層其實是同一件事：工具呼叫」，下面三個常見狀況。最後一塊講 Agent Plugins，再一條 YouTube 連結。

**逐字稿**

> 六個零件裡，第二個是工具，我們現在就來補這一塊。前面說過，沒給工具它就只能跟你講話；而要給它工具，實際上會碰到的就是 MCP 跟 Skills 這兩個詞。
>
> 這兩個詞你大概在哪裡看過，而且多半是混著看到的，有人把它們講得像同一件事。
>
> 它們確實都在做同一件大事：讓 AI 從只會聊天變成能真的做事。但加的東西不一樣，這一句先記住，它會省掉你後面很多困惑：照 MCP 接上一個服務，多的是它碰得到的範圍；裝一個 Skill，多的是它照著做的步驟。
>
> 先看 MCP。它是一套開放的溝通規範，規定 AI 工具跟外部服務之間要怎麼互相說話。
>
> 這裡有一個很多人會誤會的地方，我把它講死：規範本身不含資料，也不會給出權限。你要另外裝一個 MCP 伺服器，GitHub 的、資料庫的、雲端硬碟的，照這套規範接上去，而且在接的時候自己授權，AI 才碰得到那個系統。
>
> 所以 MCP 比較像插座的規格，不是電。你家沒有插座，知道規格也沒用，插座裝好了還要有人幫你送電進來。
>
> 右邊是 Skills。把特定的工作流程寫成一個技能包，檔案叫 `SKILL.md`。它跟 `CLAUDE.md` 的差別就是上一段講的那個漸進式揭露：平常 AI 只載入它的名稱，需要時才展開完整步驟，所以它平常不佔位置。
>
> Skills 這邊也有一個要講清楚的：它不會讓它多出原本沒有的能力。它是一份寫好的做法，不是新的手。真正會讓它多碰得到東西的是 MCP。這個區分很重要，不然你會以為裝了一個 Skill 就能連到新的系統。
>
> 中間這一塊是底層機制，聽懂它，後面很多怪現象就有解釋了。
>
> 不管是 MCP 還是 Skills，模型本身都不會直接連網、也不會動你的檔案。它做的事只有一件：輸出一段「我要用這個工具、參數長這樣」的請求。真正去執行的是外面的程式，執行完把結果送回來給它看。
>
> 知道這件事之後，下面三個常見狀況就都講得通了。
>
> 第一個，它說它做了，其實沒做。這件事你遲早會遇到，而且遇到的時候會非常困惑。
>
> 原因就在剛才那個機制：它的輸出只是一段請求，所以它完全可以「用講的」描述一個工具呼叫，而沒有真的發出去。它不是在騙你，它是真的以為那樣算做完了。
>
> 所以看到它宣稱完成的時候，去看實際的結果，不要只信它的回報。
>
> 第二個，工具太多反而變笨。每接一個 MCP，它的工具清單就變長，選錯的機率也跟著上升。只裝你這個專案真的會用到的。
>
> 第三個，工具回傳的內容不可盡信。它從網頁或外部系統讀回來的文字，可能包含惡意的指示。那些內容是資料，不是命令。這也是為什麼下一段要先講權限邊界，再往下動手。
>
> 最後這一塊講一個正在發生的變化。Amazon、Cursor、Microsoft、OpenAI、Vercel 共同發布了一個叫 Agent Plugins 的格式，把 Skills 跟 MCP 設定放進同一個資料夾，讓不同工具讀同一包。
>
> 這件事對你的影響不大，因為那個資料夾裡裝的就是剛才講的 Skills 跟 MCP 設定，沒有新東西要學。
>
> 不過有一點要提醒：Claude Code 目前不在支援名單裡，它用的是自己的格式。所以你在網路上看到別家的 plugin，不要直接拿來裝。
>
> 這種支援名單隨時會變，你之後看到它支援了也不用意外。要變的是能不能直接裝，不是這兩樣東西本身。

**這頁的教學意圖**：MCP 給範圍、Skills 給步驟；兩者底層都是工具呼叫，所以它有可能「說做了但沒做」。
**預估時間**：6 分鐘

## Slide 55｜同一個個人網站，裝與不裝 Skill

**畫面**
上方是共用的前提：履歷存成檔案放進資料夾，兩邊用完全同一段話，並列出那段指令三條。下面三塊：沒裝 Skill 的示意圖、先叫 `frontend-design` 的示意圖、一段講「你要驗收版面」的提醒。最後一條講去哪裡裝。

**逐字稿**

> 實驗設計要先講清楚，不然結論不成立：兩邊用的是完全同一段話、同一份履歷，唯一的差別是有沒有使用 Skill 來完成這個任務。
>
> 先看那段話本身，它其實是一個很好的指令範例。
>
> 第一條，用 `@resume.md` 這份履歷做一個單頁的個人網站，內容只用履歷裡寫的，沒有的不要自己補。注意它指的是檔名，不是「這份」。指檔名它就不用猜。
>
> 第二條，只新增 `index.html` 跟 `style.css`，資料夾裡其他檔案不要動。這是講明不要動什麼。
>
> 第三條，做完先在本機開起來給我看，我確認版面之後你再繼續調。這是說好做完先給我看。
>
> 這三件事寫進去，它就不用猜。你後面每一次交代工作都可以照這個骨架。
>
> 沒裝 Skill 的結果在這裡。什麼都置中、三張一樣的卡片、字級沒有落差。
>
> 它其實不難看，交出去也不會有問題。但你應該看過很多長這樣的網頁，因為它是一個通用的版面，沒有哪一個地方是照著你這份履歷的內容決定的。
>
> 裝了之後是這樣。差別在流程：它先挑定一種調性，編輯感、極簡、工業風之類的，再讓字級、留白、對齊照那個調性走。所以它不是變好看了，是它先做了一個選擇。
>
> 這兩張都是示意圖，不是實際截圖，你自己跑出來的不會長得一模一樣。
>
> 不過接下來這件事，裝再多 Skill 都幫不了你：你不用會寫版面，但你得看得出版面好不好。
>
> 看過的好版面不夠多，你只講得出「怪怪的」，講不出哪裡該改，然後它改了三次你還是覺得怪。而做出來的東西是要給別人看的，驗收不了就等於你沒有在決定它的樣子，是它在決定。
>
> 我自己的習慣是，平常看到喜歡的網站就順手截圖存起來，要改版面的時候直接把那張圖貼給它。貼一張圖，比你用文字形容半天有用。這件事等一下會整段講。
>
> 最後是裝的地方。`frontend-design` 在 Anthropic 官方市集，倉庫名稱畫面上有，用 `/plugin` 裝。社群另外有一個叫 `ui-ux-pro-max` 的。Skill 的名字跟市集位置都會換，下一頁講的那三條裝法不會。
>
> 所以 Skill 其實是一份先寫好的設計判斷。它讓 AI 在動手之前先選一個方向，而不是直接套一個最安全的版型。

**這頁的教學意圖**：Skill 改的是流程不是品味；而版面的驗收能力是你自己的事，Skill 補不了。
**預估時間**：5 分鐘

## Slide 56｜參考設計與區塊名稱，讓指令更精準

**畫面**
上方是三格進程：沒裝 Skill、裝了 Skill、再加參考設計，前兩格灰階，第三格亮著。中間是第二段指令。下面一塊列出一頁網站的四個常見區塊（Navigation Bar、Hero、Card、Footer），各附白話解釋。最後一個 Callout。

**逐字稿**

> 剛才說貼一張圖比用文字形容有用，那要怎麼貼才真的有用？還有一件比圖更重要的事，我們一起看。
>
> 這一排三格是同一條線上的三個階段。前兩格你上一頁看過了，現在講第三格：在已經有 Skill 的基礎上，再給它一個參考設計。
>
> 參考設計可以是一張截圖、一個網址，或者一份配色與字體的說明。最省力的是截圖。
>
> 看這段指令怎麼寫。第一句就把範圍圈死：這張是我要的風格，沿用現在這一版的內容，只改外觀。
>
> 然後三條。第一條講明要照著抄的是什麼：配色、標題跟內文的字級差距、分隔線粗細。注意它不是說「照這張做」，是點名了三個項目。第二條講明不能動的：文字內容跟區塊順序不要動。第三條是保險：改完把前後兩版並排開給我看，我沒說可以之前不要蓋掉舊版。
>
> 第三條這個習慣建議你養起來。它改外觀的時候很容易順手改掉別的東西，留著舊版你才比得出來。
>
> 給圖的理由很實際：配色跟字級的差距用文字描述很費力，你要講「標題比內文大一點但不要太大」，那句話裡沒有一個字是可以執行的。給一張圖準得多。
>
> 如果我們希望更精準地叫 AI 調整版面，接下來這一塊就得會：畫面上每一塊區塊的名字。
>
> 網頁是一塊一塊拼起來的，每一塊都有通用的名字。最上面那條放 logo 跟選單的，叫 Navigation Bar。一進來第一眼看到的大標區，叫 Hero。一塊一塊並排的內容方塊，叫 Card。最下面那條放聯絡方式跟版權的，叫 Footer。
>
> 名字有什麼用，比一下這兩句話就知道了。一句是「Navigation Bar 改成捲動時固定在最上面」，另一句是「上面那一條讓它黏著」。第二句它得先猜是哪一條、黏在哪、什麼時候黏；第一句它一件都不用猜。
>
> 這些名字不是我自己取的，是元件庫在用的通用叫法，所以你講出去別人也聽得懂。你有空翻一次 Ant Design 或 Bootstrap 的元件清單，畫面上每一塊該怎麼稱呼大概就有概念了。你不一定要用那些元件庫，但這幾個名字你之後每次要改版面都會用到。
>
> 最後把三件事的分工講完：Skill 讓它每次都照同一套做法做，參考設計管的是外觀。而名字管的是精準度，知道每一塊叫什麼，你才講得出要調哪裡，來回的次數也會少很多。

**這頁的教學意圖**：參考圖解決外觀的描述成本；會叫區塊名字才是你長期改得動東西的關鍵。
**預估時間**：5 分鐘

## Slide 57｜Skill 的三種來源，怎麼確認它裝好了

**畫面**
開場一句講三種來源拿到的是同一個東西。三張卡：自己寫一個、從市集裝、直接叫它裝，前兩張附路徑或指令，第一張與第三張各有一段可複製的話，中間那張放兩張實機截圖（輸入框打 `/plugin`、Plugins 面板的 Discover 分頁）。下面一個 amber 的 Callout 講「檔案建好了它卻沒反應」，最後一塊講怎麼確認裝好了。

**逐字稿**

> Skill 的來源有三種，但最後拿到的都是同一個東西：一份 `SKILL.md`，放在它找得到的資料夾裡。差別只在這份檔案是你自己寫的，還是拿別人做好的。
>
> 第一種標著「最穩」，自己寫一個。一個資料夾加一個檔案就是一個 Skill，路徑在畫面上：`.claude/skills/`，底下開一個以名稱命名的資料夾，裡面放 `SKILL.md`。
>
> 它最穩的理由是它不依賴任何東西：不用市集、不用網路，桌面版跟終端機都一樣。而且你也不用自己寫格式，跟 Claude 講就好，下面那段話可以直接複製：幫我建一個叫 `weekly-report` 的 Skill，內容是我每週整理報表的步驟，然後把步驟講給它聽。
>
> 第二種是從市集裝，也就是裝別人做好的。官方市集是 `anthropics/claude-plugins-official`，社群也有自己的市集。
>
> 這一格的兩張圖就是實機畫面。上面那張是你在輸入框打 `/plugin` 的樣子，按下去之後會跳出下面那個 Plugins 面板。
>
> 面板上面有兩個分頁：Yours 是你已經裝了哪些，Discover 是還可以裝什麼。切到 Discover，它會列出一整排，每一個都有一段說明寫它會做什麼。你先把這個清單瀏覽一遍，看看有沒有你現在就用得到的。
>
> 挑之前一定要看那段說明。裝一個你不知道它在做什麼的 Skill，等於讓一段你沒讀過的流程在你的專案裡跑。
>
> 第三種標著「懶人法」，直接叫它裝。你不確定該打哪個指令的時候，把名字給它就好：幫我安裝 `frontend-design` 這個 Skill，裝完告訴我怎麼叫它。它會自己去找、自己放到對的位置。
>
> 三種的排序是照「你掌握得了多少」排的，不是照難度。自己寫排第一，因為出事的時候你知道要去看哪裡。
>
> 接下來講一個很多人會卡住的狀況：檔案明明建好了，路徑也對，它就是沒反應。你會開始懷疑是不是格式寫錯，然後改半天。
>
> 答案是：先重開一次對話。
>
> 理由是新增的 Skill 跟規則檔是在對話開始的時候掃進來的。你在對話中途建的檔案，這一輪它不會知道。打 `/clear`，或者關掉重開，它就會掃到。
>
> 重開之後還是沒有，就檢查兩件事。資料夾名稱跟 `SKILL.md` 裡寫的 name 是不是一致。還有檔案是不是真的放在 `.claude/skills/` 底下，那個資料夾預設是隱藏的，你在 Finder 裡看不到它是正常的。
>
> 最後是驗收。最直接的辦法是點名叫它：用 `frontend-design` 這個 Skill 幫我改版面。它有沒有照那套流程走，你看它的回應就知道。
>
> 也可以打 `/context`，載進來的東西會列在裡面。這個指令你下一段還會再用到，那時候是拿來確認手冊有沒有被讀進去。

**這頁的教學意圖**：三種裝法通用一個原理；「建好了沒反應」的答案是重開對話，這一條要記住。
**預估時間**：5 分鐘

## Slide 58｜四個常用的 Skills

**畫面**
開場一句定義。第一格單獨放大：動工前先問清楚（`/grill-me`），附安裝指令、一段可複製的 Prompt、一個示範問句與四條行為說明。接著三格並排：文件處理、前端設計、網頁測試，每一格也各附一段可複製的 Prompt。

**逐字稿**

> 會裝了之後，接下來看四個我自己常用的。再提醒一次，Skill 就是把一套做法打包好，裝上就能用，需要的時候才載入。
>
> 第一個單獨放大，因為它跟另外三個的性質不一樣：另外三個是幫你做事，這一個是在你動手之前問你問題。
>
> 它的用途是這樣：你不必自己先寫出完整的規格。你叫它啟動之後，它會把你的計畫拆成一棵決策樹，逐一逼你把還沒想清楚的地方講明白。
>
> 畫面上這個示範問題很值得看，因為它就是你自己不會想到的那一類：倒數中途按「返航」，這一趟要算完成還是放棄？
>
> 你想做的是計時器，需求大概就是「記錄我完成了幾趟」。但中途放棄算不算一趟？這件事會決定你的資料怎麼存，而你沒回答，它就會自己挑一個。
>
> 而且它不是只丟問題給你，後面還附了建議跟理由：記成未完成，但仍留下紀錄，這樣你才看得出放棄率。你同意的話，一句話帶過就好。
>
> 下面四條是它的行為，其中兩條值得記。第一，它一次只問一題，等你答完才問下一題。一次丟十題給你，你會全部略過。第二，能自己查的它就去查，只把「決定」留給你。這兩條合起來就是一個好的提問流程長什麼樣，你之後自己寫指令也可以照這個標準要求它。
>
> 最後一條是操作：要自己打 `/grill-me` 才會啟動，它不會自己跳出來煩你。
>
> 下面三個比較直觀。
>
> 文件處理，讓它直接讀寫與產出 PDF、Word、Excel、簡報，不用自己另存另貼。這一組在 `anthropics/skills` 這個市集裡。底下那段 Prompt 你可以直接拿去用：把這份 PDF 裡的數字整理成一份 Excel，一個月份一個分頁，最後加一頁總計。這一個對非工程的工作最有感。
>
> 前端設計，就是剛才那個。底下這段 Prompt 是我最常用的用法：同一個需求先做三版靜態示意，A 精簡、B 功能齊、C 大膽一點，我挑一個再往下做，先不要做完整個網站。
>
> 最後那半句要留著。三版都做完整的，你的錢花了三倍，而你只會用一版。
>
> 網頁測試，自動開瀏覽器點來點去，驗證你的網頁功能真的能跑。Prompt 長這樣：用 `webapp-testing` 開瀏覽器，把這五個功能各點過一次，逐題回報通過或失敗。這一個在章節八會再出現，那時候它是你放手讓 Agent 自己跑的時候，那一道自動的檢查。
>
> 這四個的共同點是：都是你會一直重複做的事。你只做一次的事不需要 Skill，講一次就好。裝一堆用不到的，回頭看就是前面講的那個「工具太多反而變笨」。

**這頁的教學意圖**：四個常用 Skill 各解決什麼，以及每一個實際怎麼叫它。
**預估時間**：5 分鐘

- 另外三個 Skill 都是泛指一類（文件處理、前端設計、網頁測試），只有第一個給的是一個具體的斜線指令 `/grill-me`。但這一頁沒說它是官方市集的、社群的、還是要自己寫。上一頁剛教完三種裝法，學員讀到這裡的第一個動作就是去找它。
- 對照 Slide 55 的做法：那一頁的 `frontend-design` 有寫明市集倉庫名稱。同一份簡報兩種標準。
- **建議**：那一格補一行來源（市集名稱或倉庫），或者如果它是要自己寫的，就講明「這一個要自己寫，內容就是上面那四條行為」。

### 2.【矛盾】Skills 的「不會多出能力」在 Slide 54 講死，Slide 58 的網頁測試又像是新能力

- Slide 54 寫得很明確：「Skills 不會讓 Agent 多出原本沒有的能力，它是一份寫好的做法」，而且檔頭註解記著這句話是特地改過的。但 Slide 58 的網頁測試寫的是「自動開瀏覽器點來點去」，那在學員讀起來就是一個新能力。
- 實際上那個 Skill 要能動，背後得有瀏覽器自動化的工具（也就是 Slide 54 講的 MCP 那一邊），Skill 只是把使用流程包起來。兩頁相隔四頁，學員不會自己接起來。
- **建議**：網頁測試那一格的說明補半句點出它依賴什麼，例如「（要先有能開瀏覽器的工具，Skill 管的是怎麼測）」。這一句同時把 Slide 54 那組分工再釘一次。

### 3.【缺漏】Slide 57 的「自己寫一個」沒說 `SKILL.md` 裡面要有什麼
