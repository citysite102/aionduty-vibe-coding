## Slide 61｜動手搭建運作框架

**畫面**
四格，各有一段可複製的指令與一行「做完這格」要做的事。依序是：為計時器生成手冊、親眼看 context 被吃掉、讓它先問不要先寫、去看它自己記了什麼。最後一個灰底 Callout 給手上沒有計時器的人一條替代路，四格各自怎麼換都寫了。

**逐字稿**

> 接下來我們就要做出第一份完整的 `CLAUDE.md` 囉。底下這四格做的是同一份檔案。第一格請它生一份草稿，剩下三格才是重點，因為草稿直接拿來用是不夠的。
>
> 第一格，叫它讀一遍這個專案，幫你寫一份 `CLAUDE.md`。
>
> 指令後面那半句是「先不要存檔，貼出來給我看」，這句話建議你以後都加上去。只要是會生出檔案的請求，都先看過內容再決定要不要存。
>
> 它寫完你一定要改。它產出的草稿看起來會很完整，你很容易就直接收下來。
>
> 但它只看得到程式碼，看不到你腦子裡的規則。你為什麼不用外部圖片、為什麼按鈕要用那組詞，這些它猜不到，它只會把從程式碼裡歸納出來的現況寫下來。而現況不等於規則。
>
> 做完這一格，先把草稿存成 `CLAUDE.md`。
>
> 第二格是量一次你剛剛那份手冊要花多少。前面說過它每一次對話都會被送一次，但那是用講的，這一格你自己看到數字。
>
> `/context` 會列出這次對話目前帶了哪些東西、各佔多少。你剛存的那份手冊、你講過的話、它讀過的檔案，全部在那張清單上。
>
> 所以做法是前後各打一次。先打一次 `/context`，把用量記下來。然後叫它把 `index.html` 整份讀一遍，告訴你它有幾行。再打一次 `/context`，比一下用量多了多少。那個差額就是這一個檔案吃掉的量。
>
> 【停頓，讓兩個數字都停在畫面上】
>
> 你只是讓它讀了一個檔案，用量就往上跳了一塊。送進去的東西越多，額度消耗越快；如果你是走 API 計價的，那就直接反映在帳單上。
>
> 順便記兩個指令的差別。想清掉重來是 `/clear`，想留著摘要繼續是 `/compact`。
>
> 做完這一格，回頭看你剛存的那份草稿，挑出那些它光讀程式碼就查得到的條文，像是用了哪些套件、檔案放在哪個資料夾、指令怎麼跑。那幾條每次對話都在佔位置，而它本來就查得到，所以刪掉不會少任何東西。至於一份手冊該砍掉哪些、怎麼判斷哪一條留得住，章節六有一整段專門在做這件事。
>
> 第三格，讓它先問，不要讓它先寫。拿一個你自己也還沒想清楚的需求。
>
> 要貼的是這一整段，需求本身就寫在裡面：我想知道自己今天完成幾趟任務。這個需求我還沒想清楚，先不要寫程式，把你需要我決定的事情列出來問我。
>
> 它應該要問回這種等級的問題：答案只有你決定得了，它讀程式碼讀不出來。
>
> 按了返航、沒跑完的那次，算不算一趟？「今天」是算到午夜，還是從你這次打開頁面起算？關掉瀏覽器再打開，前面的紀錄要還在嗎？
>
> 這三題你不回答，它就會自己選，而且不一定會告訴你它選了什麼。
>
> 這是我覺得最值得養成的一個習慣：需求還沒想清楚的時候，先叫它問你，不要先叫它寫。它替你做的那些決定不會特別標出來，寫得又快，等到過兩天數字不對，才要回頭查它當初怎麼算的。
>
> 做完這一格，你剛剛做的那三個決定，就是三條新規則。補進手冊，下次它不用再問一遍。
>
> 第四格是一個很多人不知道的事：除了你寫的 `CLAUDE.md`，Claude Code 自己也會存筆記，而且預設就開著。
>
> 兩者的分工不一樣。手冊是你寫的規則，像「一律用繁體中文」這種。它的筆記是它自己學到的：你糾正過它的事、你偏好的做法、這個專案做過的決定。
>
> 有一件事它刻意不記：凡是它自己讀程式碼就查得到的，例如這個專案怎麼跑測試、檔案放在哪，它不會寫進筆記，因為那些它每次都查得到。它記的是那些你不講它就不知道的事。
>
> 打 `/memory`，去看它到底記了什麼。那些是純文字檔，你可以直接改或刪。
>
> 做完這一格，它記的東西裡如果有你希望每個人都遵守的，搬進手冊。理由是它的筆記是它自己的，換一台電腦、換一個人接手就沒有了；手冊會跟著專案走。
>
> 最後補一條給手上沒有計時器的人。開一個空資料夾，四格這樣換：第一格跟它說「幫我起一份空白的 `CLAUDE.md`」，規則寫你自己工作上真的有的那幾條；第二格改讀手邊任何一個長一點的檔案；第三格換成你工作上真的還沒想清楚的一個需求；第四格照走。

**這頁的教學意圖**：四格做完會有一份改過的手冊；其中第 2 格讓「上下文會被吃掉」變成看得見的數字。
**預估時間**：15 分鐘（動手，含實機）

## Slide 62｜補四條規則進 CLAUDE.md，再試它一次

**畫面**
開場一段講草稿缺什麼。兩步：第一步「把約定補進去」，列出四條規則與一段可複製的完整指令；第二步「驗收：規範真的有用嗎」，一段可複製的需求，底下三件要檢查的事。

**逐字稿**

> 我們剛剛產出的那份草稿，是它讀你現在的程式碼、加上你前面那幾句指令寫出來的，所以裡面只有它看得到的東西。現在要補的是另外一半：程式碼裡看不到的那些約定。
>
> 第一步，把約定補進去。畫面上那四條就是程式碼裡看不到的規則。
>
> 看懂它為什麼猜不到，你就知道自己的專案要補哪些。
>
> 第一條，深色星空背景，主色只用在當下要強調的那一個元素。它看得到你用了什麼顏色，但「只用在當下要強調的那一個」是一條原則，不是一個現況，程式碼裡沒有這句話。
>
> 第二條，星球與火箭一律用 canvas 或 CSS 畫，不得引用外部圖片。這一條是整頁最典型的例子：它看得到你現在沒有用外部圖片，但它完全不知道那是刻意的。下次它要加一顆星球，它會很自然地去找一張圖。
>
> 第三條，按鈕文案使用航太語彙：發射、待機、返航、補給。這一條給了具體的詞，所以它不用猜。
>
> 第四條，倒數的分鐘數要放在最上面當設定，不要散在程式碼裡。這一條管的是之後你改不改得動。
>
> 整段話開頭那一句也要抄：請在 `CLAUDE.md` 補上下面這幾條，原本已經有的不要動，以後每次進來都要遵守。
>
> 「原本已經有的不要動」這半句很重要，不然它會把整份重寫一次。更保險的做法是先叫它把打算改動的段落列出來給你看，你確認過再讓它寫，它動到別的地方你當下就攔得下來。
>
> 補完之後自己把整份讀一遍，看新加的那幾條有沒有跟舊的打架、或者同一件事在兩個地方各寫了一次。這件事章節六有一整套流程在做。
>
> 第二步是驗收。
>
> 有一件事千萬不要做：問它「你有讀手冊嗎」。它多半會說有，而且說得很肯定。這就是前面講過的那一條，它沒把握的時候看起來跟有把握一模一樣。
>
> 要這樣做：給它一個新需求，幫我加一個五分鐘的「補給時間」模式，樣式請遵守 `CLAUDE.md`。
>
> 然後看三件事：按鈕文案有沒有跟上航太那組詞、有沒有偷塞一張外部圖片進來、分鐘數有沒有寫死在程式裡。
>
> 這個做法你之後每次改完手冊都可以用：不要問它讀了沒，給它一個會踩到規則的任務，看它踩不踩。

**這頁的教學意圖**：手冊要補的是「程式碼裡看不到的約定」；驗收要靠一個會踩到規則的新任務，不是問它讀了沒。
**預估時間**：8 分鐘（動手）

## Slide 63｜用 /context 確認 CLAUDE.md 真的載入了

**畫面**
開場一句講 `/context`。中間一塊模擬的 `/context` 輸出：上半是 Context Usage 的四行（標著「示意，數字與欄位以你打出來的為準」），下半是 Memory files 那一段，列著 `CLAUDE.md` 3.7k tokens 與 `~/.claude/CLAUDE.md` 126 tokens。右邊三格問句：有沒有？有幾份？佔多大？最後一句收尾。

**逐字稿**

> 驗收沒過的時候，多數人的第一個動作是回去改規則的寫法。那通常不會有用。
>
> 第一個要排除的不是寫得好不好，是它這一輪到底有沒有被讀進去。在對話框打 `/context`，要看的是 Memory files 那一段。
>
> 畫面上這個是示意，欄位名稱跟數字以你自己打出來的為準。上半那幾行是這一輪的空間怎麼分掉的，你剛才前後各打一次 `/context` 比過的用量，就是看這一區。真正要看的是下半那一段，Memory files：它把這一輪讀進來的規則文件一個一個列出來，後面跟著各佔多少 token。
>
> 這裡就是你要盯的三件事。
>
> 第一，有沒有。你的 `CLAUDE.md` 不在那份清單裡，代表這一輪它根本沒被讀到。這種時候不要去改規則的寫法，那是在修一個沒有生效的東西。先解決有沒有，再談寫得好不好。
>
> 不在清單裡的原因有幾種。最常見的是這一輪開始之後才建立的：規則文件跟前面裝 Skill 的情況一樣，是在對話開始的時候掃進來的，中途新增的這一輪不會知道，打一次 `/clear` 重來就會進來。另一種是檔名或位置不對，`CLAUDE.md` 要全大寫，而且要放在你開啟的那個資料夾，或者它的上層。
>
> 第二，有幾份。全域的、專案的、子目錄的，可能同時載入；示意圖那兩行就是這樣，一份是這個專案的，一份是全域的。它是一個很難查的症狀的來源：兩條規則互相矛盾，多半發生在這裡。你在專案裡寫了一條，忘了家目錄那份還有一條相反的，它兩份都讀到了。
>
> 第三，佔多大。手冊越長，越後面的規則越容易被當成背景。官方建議一份控制在兩百行以內。
>
> 超過也不是壞掉，那個數字是提醒你回去做減法的門檻。真的減不下來還有一種做法：用路徑規則把手冊拆開，讓它只在你動到對應檔案的時候才載入。章節六會整章講這件事。
>
> 所以手冊改完之後，先打一次 `/context` 看它在不在清單裡，再繼續加規則。
>
> 順序是：先確認它有沒有被讀到，再看有幾份、彼此會不會打架，這兩件都沒問題，才去看規則本身寫得好不好。
>
> 順序反過來的話，你可能花半天在改一條根本沒被載入的規則。

**這頁的教學意圖**：規則沒生效的第一嫌疑是沒被載入；`/context` 一次看有沒有、有幾份、佔多大。
**預估時間**：4 分鐘

## Slide 64｜常見的三種錯誤規則寫法

**畫面**
開場一句講共通點。三組對照，每一組有「寫了沒用的那句」、為什麼沒用、改成什麼，以及一個分類標籤（無法判定、該用機制、指涉不明）。最後一個框給檢查方法。

**逐字稿**

> 這三種的共通點是：看起來都很像規則，讀起來也很順，但沒有任何一句驗得出來做到了沒。你剛剛寫的那份裡面，很可能就有一條長這樣。
>
> 第一種，無法判定。例句是「回覆要專業一點」。
>
> 為什麼沒用：專業是你心裡的標準，它沒有辦法對照。而且更麻煩的是做完了它自己也不知道算不算達成，所以它連「我做到了沒」都答不出來。
>
> 改成什麼：不要用驚嘆號，不要用「輕鬆搞定」這類說法，專有名詞第一次出現時附上英文原文。
>
> 改寫之後那三個項目，全部是看一眼就能回答有或沒有的。
>
> 第二種，該用機制。例句是「不要直接把東西推上 main 分支」。
>
> 這一句的問題跟前一句完全不同，它很具體，它也驗得了。問題是寫在手冊裡不保證會被照做。對話一長它就把這一條當成背景，而這種事錯一次就收不回來。
>
> 改成什麼：在 Hook 或 GitHub 的分支保護裡擋掉，讓程式攔。手冊裡只留一行提醒。
>
> 有些事情本來就不該用講的，規則的層次不只有「寫進手冊」這一種。章節六會整章展開。
>
> 第三種，指涉不明。例句是「照之前的做法，維持原本的風格」。
>
> 為什麼沒用：「之前」是哪一次？它不知道。你心裡想的那一版，它沒有辦法回頭找。這一句對你來說很清楚，因為你記得那一版長什麼樣，但那份記憶不在檔案裡。
>
> 改成什麼：直接把那個做法寫出來，或者指名檔案。指名檔案有兩個好處：你不用把整套樣式抄一遍，而且那個檔案之後改了，規則不用跟著改。
>
> 要更精準就把用法也寫死，例如「以後新增按鈕一律照 `src/components/Button.tsx` 改，不要另外寫一個」。這樣它不只知道去哪裡看，也知道下次該拿哪一份當範本。
>
> 檢查方法分兩步。第一步你自己答一次：只看做出來的東西，你能不能回答「有做到」或「沒做到」。「回覆要專業一點」你答不出來，「不要用驚嘆號」數一下就答得出來。
>
> 第二步，你自己也不確定的時候，把那句話貼給它，問它照這句話要怎麼判斷自己做到了沒。它只能回答「我會注意」，這一條就是寫了等於沒寫。
>
> 你剛寫的那份手冊，每一條都可以用這兩步問一次。

**這頁的教學意圖**：三種無效寫法各有各的病因；判斷標準是「只看做出來的東西，答不答得出有做到或沒做到」，分兩步驗。
**預估時間**：5 分鐘

### 1.【矛盾】Slide 61 第 2 格的「兩百行以內」與第 1 格的做法是反的

- 第 1 格叫它「讀一遍這個專案，幫我寫一份 `CLAUDE.md`」，這種生成出來的草稿通常很長，而且塞滿它從程式碼歸納出來的東西。第 2 格與 Slide 63 才告訴學員那些該刪、而且一份建議控制在兩百行以內。
- 順序本身是對的（先有東西才減得動），但第 1 格完全沒有預告，學員拿到一份三百行的草稿會以為自己做對了。
- **建議**：第 1 格的「做完這格」補半句，例如「它給的一定太長，先存著，下一格開始刪」。這一句同時把四格的連續性講出來。

### 2.【缺漏】Slide 63 的模擬輸出裡，兩份手冊的來源沒有標

- 畫面上列著 `CLAUDE.md`（3.7k tokens）與 `~/.claude/CLAUDE.md`（126 tokens），這正好示範了右邊第 2 格要講的「有幾份」。但那兩行只有路徑，沒有標哪一份是專案的、哪一份是全域的。
- 對非工程背景的學員來說，`~/` 這個符號代表什麼是章節四（選修）才講的，走主線的人沒看過。所以那一格「全域、專案、子目錄可能同時載入」在畫面上其實沒有對應物。
- **建議**：那兩行後面各加一個灰色小標，「← 這個專案的」與「← 全域，所有專案都吃得到」。這樣第 2 格的說明就有東西可以指。

### 3.【B-4】Slide 62 的替代路徑跟 Slide 61 的四格對不起來

- Slide 62 最後那個灰框寫「手上沒有計時器的話，開一個空資料夾，把上面那四條改成你自己工作上真的有的規則，一樣走得完這兩步」。但 Slide 61 的第 1 格是「讀一遍這個專案」，空資料夾裡沒有專案可讀，那一格走不完，也就沒有草稿可以接。
- 也就是說，這條替代路徑只對 Slide 62 這一頁成立，對整個單元不成立。
- **建議**：把這個灰框往前搬到 Slide 61，並改寫成涵蓋四格的版本（第 1 格改成「直接叫它幫你起一份空白的 `CLAUDE.md`」）。或者在 Slide 61 也補一句同樣的但書。

### 4.【缺漏】Slide 64 第二種「該用機制」提到 Hook，但這是全片第一次出現這個字

- 那一格的改法是「在 Hook 或 GitHub 的分支保護裡擋掉」。`Hook` 這個詞在 Slide 50 的六個零件裡是用「自動關卡」這個中文名稱出現的，沒有掛上英文；學員在這裡讀到 Hook 不會知道它就是那一格。
- 它真正被展開是在章節六（Slide 95 之後），中間隔了快三十頁。
- **建議**：兩種改法選一種。這一格改用 Slide 50 用過的詞「自動關卡（Hook）」，把兩邊接起來；或者 Slide 50 那一格的名稱就直接標成「自動關卡（Hook）」，讓這個詞從第一次出現就帶著英文。後者比較一勞永逸，因為這個字後面會出現很多次。

### 5.【指涉不明】Slide 62 整頁第一句的「它」出現四次，沒有先行詞

- `21b2_M2_HandsOnPrompt.tsx:43-45`：「上一頁第 1 格叫**它**生的那份草稿，是**它**讀完你的程式碼寫出來的，所以裡面只有**它**看得到的東西。現在補上**它**看不到的那一半：你腦子裡的規則。」
- 這是這一頁的第一句，畫面上在它前面沒有任何一個名詞可以當先行詞。
- 諷刺的是兩頁之後的 Slide 64 教的第三種無效寫法就叫「指涉不明」，例句是「照之前的做法」。
- 另外「上一頁第 1 格」是 B-4 點名的位置代稱，搬頁之後會安靜地指錯。
- **建議**：第一個「它」換成 `Claude`，一個先行詞就夠，後面三個自然有指涉。
