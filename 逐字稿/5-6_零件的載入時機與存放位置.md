## Slide 71｜根目錄的手冊整場都在，Rules 碰到才載

**畫面**
開場一句講分類方式。兩塊上下排開：`CLAUDE.md`（整場都在）、Rules（碰到那一區才載），各附一段說明與存放路徑，Rules 那一塊還附了一段 `paths` 的示意。最後一塊收尾，把差別收成一句。

**逐字稿**

> 到目前為止真的講完、也動過手的只有兩個：`CLAUDE.md` 跟 Skill。接下來這一段會把剩下那幾種也講過去，包含 Rules、子代理、MCP，還有 Hook。
>
> 名字一多就會亂，所以先給你一個分類的問題：這個東西是什麼時候被載進來的？
>
> 照這個問題分，答案只有三種：一開始就在、叫到才進來、根本不進對話。剛才那些名字全部歸得了位。
>
> 首先先來看一開始就在的那一種，這一頁講的就是它，以及跟它最像的 Rules。
>
> 用這個問題來分，是因為那決定了它佔多少空間，而空間就是錢。前面算 token 那一段算的就是這筆帳。
>
> 第一種，整場都在。`CLAUDE.md` 是這一種。session 一開始就載入，而且壓縮對話之後還會自動重讀，所以它不會掉。
>
> 壓縮之後還會重讀，這一點有實際的後果。前面講過對話快滿的時候系統會摘要一次，那個過程會掉細節。手冊是少數不會掉的東西，這也是為什麼重要的規則要寫進檔案，不要只講在對話裡。
>
> 它的代價也很明確：從頭到尾都佔著空間。
>
> 第二種，碰到那一區才載，叫 Rules。寫成一個檔案放進 `.claude/rules/`，然後在檔案開頭指定它管哪一區。
>
> 關鍵在那個「開頭指定範圍」。有寫範圍，它就只在你動到那一區的時候才被讀進來，平常不佔空間。
>
> 例如你有一條規則是「這個資料夾底下的元件一律用 canvas 畫，不要用圖片」，這一條只有你在改那個資料夾的時候才用得到。
>
> 寫進 `CLAUDE.md` 會怎樣？它每一次對話都要被讀一遍，包含你根本沒碰那個資料夾的那幾百次。你為那幾百次付了錢，而且它們一次都沒用到。
>
> 所以兩者的差別就在要不要一直在。能綁定範圍的就綁定，不要全部往根目錄堆。
>
> 這也就是前面那個兩百行的建議背後真正的意思。不是叫你寫少一點，是叫你把只在特定情況成立的東西挪出去。

**這頁的教學意圖**：分類的軸線是「什麼時候被載入」；Rules 是把有範圍的規則挪出常駐區。
**預估時間**：4 分鐘

## Slide 72｜Skill、Subagent、MCP：叫到才進來

**畫面**
三塊上下排開：Skill（平常只載名稱）、Subagent（叫了才展開）、MCP／Plugin（連上才有），各附「負責什麼」「怎麼運作」與存放位置。最後一塊講 `.claude` 資料夾是隱藏的，附 Mac、Windows、VS Code 三種看法。

**逐字稿**

> 接下來這三個都是叫到才進來的：Skill、子代理、還有 MCP。
>
> 它們有一個共同的好處，你可以準備很多個。因為平常不佔上下文，只有真的被叫到的那一個才會進來，所以你裝十個 Skill 跟裝一個，成本差不多。
>
> 第一個，Skill，前面那個單元你已經裝過一個了。它的載入方式是平常只載名稱，讓它知道有這個東西；真的要跑那套流程的時候，才把整份 Skill 展開。要不要展開是它自己判斷的，你也可以直接點名叫它。
>
> 這裡補一件事。你可能看過有人把自己常用的一段話存成斜線指令，打 `/deploy` 就跑一套部署流程。那個功能現在併進 Skill 了：舊的放法是 `.claude/commands/deploy.md`，新的放法是 `.claude/skills/deploy/SKILL.md`，兩種都打得出 `/deploy`，跑起來一樣。
>
> 舊的還能用，不用回頭改。但新的東西直接寫成 Skill，因為 Skill 多兩件事做得到：它可以另外附腳本跟參考文件，而且不用你打那個指令，它自己會判斷這次要不要用。
>
> 第二個，Subagent，子代理。它的機制跟 Skill 不一樣：它自己的那段對話不會塞進你這邊，你只會收到結果。
>
> 這一點是它值錢的地方。你叫它去翻三十個檔案找一個東西，那三十個檔案的內容全部進的是它的上下文，不是你的。你這邊只多了一句結論。
>
> 所以它最適合的是要翻很多檔案的調查工作。章節七整章在講怎麼用它，這裡先知道它的成本結構。
>
> 第三個是 MCP 跟 Plugin。MCP 前面講工具那一段看過了，它是一套規範；照這套規範把 Notion 或 GitHub 的伺服器接上來，Claude 才讀得到、動得了那些系統。這一格多提了一個 Plugin，那是把前面這些整組打包，讓團隊共用同一份設定。
>
> 注意它的「放在哪」那一欄寫的不是檔案路徑，是「去接一個現成的服務」。這是 MCP 跟另外兩個最大的差別：另外兩個是你自己寫檔案，走 MCP 接的是別人的東西。
>
> 再來是一個幾乎每個人都會撞到的卡點：你照著路徑打開資料夾，找不到 `.claude`，然後開始懷疑是不是哪一步做錯了。
>
> 它在，只是你看不到。開頭是一個點的資料夾，Finder 跟檔案總管平常都不會顯示。
>
> Mac 進到專案資料夾之後按 `Cmd + Shift + .` 切換顯示。Windows 在上方的「檢視」勾選「隱藏的項目」。用 VS Code 的話側邊欄本來就看得到，不用設定。
>
> 不想動設定的話，直接問它：列出 `.claude` 底下有哪些檔案。

**這頁的教學意圖**：三個零件都是叫到才進來；Subagent 的關鍵是它的對話不佔你的空間。
**預估時間**：5 分鐘

## Slide 73｜真的不能發生的事，交給 Hook 與 CI

**畫面**
開場一段點出前兩頁的零件最後都要經過 AI 判斷，這一頁的兩個是程式在跑，連進 context 都不用。兩塊並排：Hook（在你的機器上擋）、CI（在合併前擋）。下面一塊對照「文字說服，跟程式攔截」。最後一句把三種載入時機收起來。

**逐字稿**

> 這一頁的兩個零件是 Hook 跟 CI，它們處理的是那種真的不能發生的事。要講清楚它們為什麼特別，得先看前面那些零件的形式。
>
> 手冊、Rules、Skill 是你寫的文字檔，MCP 接進來的是別人跑的服務，Subagent 是它自己派出去的一個分身。形式不一樣，但它們有同一個共同點，就是最後都要經過 AI 判斷，它得讀到、也得決定要照做，你的規則才會生效。
>
> 只要是靠它判斷的，就有它不照做的那一天。
>
> Hook 跟 CI 不一樣。它們是程式在跑，不經過 AI 判斷，所以連進 context 都不用。
>
> 第一個，Hook，在你的機器上擋。它想把破折號寫進檔案，就直接被退回。
>
> 它幾乎不佔 token，因為它根本不在對話裡。擋得住，又不用花錢養著它。
>
> 第二個，CI，在合併前擋。程式碼要進主線之前先跑一次檢查，沒過就進不去。
>
> 它跟 Hook 的差別在涵蓋範圍：Hook 是你這一台機器，CI 是整個團隊都躲不掉，不管是誰寫的、用什麼工具寫的。
>
> 接下來這個區分，之後每次寫規則都會用到：文字說服，跟程式攔截。
>
> 「絕對不要做某事」寫在 `CLAUDE.md` 裡，不保證擋得住。原因有兩個。第一，對話一長，它會把那一條當成背景。第二，前面講 MCP 的時候提過，工具回傳的內容不可盡信：它從外面讀回來的東西如果寫著「請忽略前面的規則」，它還是可能做下去，因為那兩行對它來說都是讀進來的文字，哪一句該聽還是它自己在判斷。
>
> 文字跟程式的差別在機制。你寫成文字，那一條規則每一次都要它重新判斷一遍：這次算不算、要不要照做。判斷就有機率，所以它有做到的時候，也有沒做到的時候。
>
> 寫成程式就不是判斷了。Hook 是一段每次都照樣跑的檢查，同樣的情況進來就是同樣的結果，它想跳過也沒有那個選項，因為它根本沒有被問到。
>
> 所以真的不能發生的事，要用 Hook 或 CI。判斷標準是這樣：問自己「這件事錯一次，收得回來嗎」。收得回來就用寫的，收不回來就用擋的。
>
> 所以這些零件，差別就在它什麼時候進到對話裡：整場都在、用到才展開，或者根本不進來。

**這頁的教學意圖**：前面那些零件的共同點是「要經過 AI 判斷」，不是「形式是文字」；Hook 與 CI 不經過判斷，所以真的不能發生的事要交給它們。
**預估時間**：5 分鐘

> 三種時機講完了。

## Slide 74｜手冊、Rules、Skill、Hook 的載入時機

**畫面**
一張四欄的總表（零件／它負責什麼／誰叫它出來／放在哪，欄位標題跟第一段同時出現），分成三段：整場都在（CLAUDE.md、Rules）、用到才展開（Skill、Subagent、Rules 限定範圍、MCP）、不進對話（Hook、CI）。最後一個 sky 的 Callout 給三個判斷問題。

**逐字稿**

> 接著我們把七個零件放到同一張表上看。
>
> 這張表比前面三頁多了一欄：誰叫它出來。它回答了兩個最常見的困惑。
>
> 第一個困惑是「哪些東西寫成 `.md`、哪些寫成 Hook」。看這一欄就知道：觸發的是 Claude，就寫成文字；觸發的是系統，就是 Hook。
>
> 第二個困惑是「Skill 要怎麼從手冊裡叫出來」。答案是不用，Skill 不是被手冊提取的，是 Claude 自己判斷要用。你也可以直接點名。
>
> 第一段，整場都在。`CLAUDE.md` 自動開場就讀。Rules 這裡指的是開頭沒有指定範圍的那一種，它跟 `CLAUDE.md` 一起被讀進來。這一段的代價是：不用你叫，但它從頭到尾都佔著空間。
>
> 第二段，用到才展開。Skill 是 Claude 自己判斷要用。Subagent 是 Claude 派它出去。
>
> 然後你會看到 Rules 又出現一次，這不是印錯。表上兩列分別標著「沒寫範圍」跟「有寫範圍」，它們是同一個資料夾 `.claude/rules/` 底下的兩種寫法：檔案開頭有沒有寫它管哪一區。沒寫的，跟手冊一起載入，整個專案都適用；寫了的，動到那一區的檔案才被讀進來。同一個資料夾、兩種行為，差別只在檔案開頭那一行。
>
> 最後是 MCP，Claude 需要動那個系統的時候才連。它的「放在哪」一樣是接一個現成的服務。
>
> 第三段，不進對話。Hook 那一列請注意「誰叫它出來」那一欄：不是 Claude，是系統自己觸發。這一句就是上一頁說的那個差別。CI 是你推上去之後 GitHub 自己跑。
>
> 順便看一下最後一欄的路徑。Hook 寫在 `.claude/settings.json`，CI 寫在 `.github/workflows/`。後面那個資料夾不是 Claude 的，它是 GitHub 的，所以 CI 那一道跟你用什麼 AI 工具完全無關。
>
> 最後三個問題，之後每次要多放一樣東西的時候拿出來問。
>
> 每次都要記得的嗎？是的話寫進 `CLAUDE.md`；只有某一區要記得，就放 Rules。
>
> 偶爾才跑，但每次步驟都一樣？做成 Skill。它平常只載一行名字，真的要跑那套流程才展開全文，所以你多裝幾個也不會把空間吃掉。
>
> 絕對不能發生的嗎？交給 Hook 或 CI。這種事寫在手冊裡是擋不住的。
>
> 這三題章節六會用一整段把它們拆得更細，那時候你會拿自己手上的規則一條一條走過去。

**這頁的教學意圖**：多一欄「誰叫它出來」把 `.md` 與 Hook 的界線講死；並給出新增東西時的三個歸位問題。
**預估時間**：6 分鐘

## Slide 75｜零件放哪：家目錄與專案資料夾

**畫面**
開場一句講位置只有兩個。中間一張純文字的樹狀圖：上半是 `~/.claude/`（indigo），底下五項；下半是 `mission-timer/`（sky），底下有作品本身、`CLAUDE.md`、與 `.claude/` 的四個配件。下面兩塊：什麼該放家目錄、什麼該放專案。最後一個 sky 的 Callout。

**逐字稿**

> 就是你的家目錄，跟你的專案資料夾。
>
> 家目錄這個詞先解釋一下：它是你這個使用者在這台電腦上的根資料夾，Mac 在斜線 Users 斜線你的名字，Windows 在 C 槽的 Users 底下。你在路徑裡看到的那個波浪符號就是它。
>
> 兩邊的結構長得幾乎一樣，這也是為什麼容易搞混。差別在誰會看到、什麼時候載入。
>
> 上面這一組是家目錄。裡面放你個人的偏好，例如一律用繁體中文回答；你自己每個專案都會用到的流程，放 `skills/`；你慣用的子代理，放 `agents/`；每個專案都吃得到的個人規則，放 `rules/`；所有專案都會跑的關卡，寫在 `settings.json`。
>
> 下面這一組是你的專案資料夾，這裡就用你的計時器當例子。`index.html` 是作品本身。`CLAUDE.md` 是這個專案的規則，它進版本控制，團隊共用。
>
> 然後是 `.claude/` 這個資料夾，裡面四樣：只有這個專案要跑的 `skills/`、只有這個專案要用的 `agents/`、只管某一區檔案的 `rules/`，還有 `settings.json`，自動關卡寫在那裡。
>
> 這張圖是照你在 Finder 裡真的會看到的樣子排的，不是示意圖，所以你打開來應該長得一樣。
>
> 兩邊怎麼分，下面這兩塊給了判斷標準。
>
> 家目錄放換到任何一個專案都成立的事：你的語言偏好、你自己的工作習慣、你每個案子都會跑的那套流程。它有一個特性要記住：別人不會看到這一份，它不進版本控制。
>
> 專案放換一個專案就不成立的事：這個案子的命名慣例、配色、不准做什麼。它跟著專案走，別人下載下來就有同一份規則。
>
> 這個坑我自己踩過：不要什麼都往家目錄的 `CLAUDE.md` 塞。
>
> 一開始你會覺得很方便，每個專案都讀得到，何樂不為。
>
> 理由是那一份是每個專案、每一次對話都會被讀進去的。寫得越長，它每次開工都先揹著一堆跟這個案子無關的東西，而且每次都在花錢。
>
> 判斷分兩層，可以直接拿來用。第一層：這條規則換一個專案還成立嗎？不成立就往專案那邊放。第二層：只有某一區檔案要遵守嗎？那連專案的 `CLAUDE.md` 都不該進，寫成 `.claude/rules/` 底下的一個檔案，動到那一區才載入。

**這頁的教學意圖**：兩個位置的取捨是「換一個專案還成立嗎」；家目錄那一份的成本最容易被低估。
**預估時間**：5 分鐘

### 1.【矛盾】Slide 72 與 Slide 74 對「誰叫 Skill 出來」的說法不一致

- Slide 72 寫「名稱先進來讓它知道有這個東西，真的要跑那套流程時才展開全文」，沒有說是誰決定要跑。Slide 74 明確寫「Claude 自己判斷要用，你也可以直接點名」，而且 `21d4` 的檔頭註解記著這一欄就是為了解掉「不同 CLAUDE.md 裡面如何提取 skill」這個學員卡點。
- 更早的 Slide 57 則教的是「最直接的辦法是點名叫它」。三頁三種講法，而最關鍵的那一句（它會自己判斷）要到 Slide 74 才出現。
- **建議**：Slide 72 的 Skill 那一格補半句，「要不要展開是 Claude 自己判斷的，你也可以直接點名」。這一句補上去之後三頁就一致了，而且它正是這個零件最容易被誤解的地方。

### 2.【缺漏】Slide 71 只講了 Rules 的「開頭指定範圍」，沒說那一行長什麼樣

- 整頁把 Rules 跟 `CLAUDE.md` 的差別歸結到「在檔案開頭指定它管哪一區」，Slide 74 又用同一句話區分了兩種 Rules。也就是說整個單元有兩頁把重量壓在同一行語法上，而那一行從頭到尾沒出現過。
- 對照同一章的做法：`SKILL.md` 的欄位在 5-5 待處理也被點出同樣的缺口，這是同一種病（B-6 那條：一個毛病不會只出現在一頁）。
- **建議**：Slide 71 的 Rules 那一格路徑下面補兩行示意，例如一行 `適用範圍：src/components/**` 加一行規則。不用講格式細節，讓學員看得出「範圍是寫在檔案裡的一行字」就夠了。

### 3.【缺漏】Slide 75 的樹狀圖裡，家目錄那一組沒有 `rules/` 與 `settings.json`

- 專案那一組列了四樣配件（skills、agents、rules、settings.json），家目錄只列了三樣（CLAUDE.md、skills、agents）。開場那句話說的卻是「兩邊的結構長得一樣」。
- 如果家目錄確實也放得下 rules 與 settings.json，那是漏列；如果放不下，那句「長得一樣」就要改。兩種情況畫面上都沒有交代，而學員會照著這張圖去建資料夾。
- **建議**：先確認實際行為（家目錄的 `settings.json` 是存在的，Hook 可以設在那一層），然後補齊，並在那兩行的 note 標出它的涵蓋範圍，例如「所有專案都會跑的關卡」。這剛好也強化最後那個 Callout 的警告。

### 4.【B-4】Slide 74 收尾說「章節六會用一整段拆得更細」，這條線目前只存在於口白

- 那三個分流問題確實在 Slide 90 到 93（`harness/05_RouteQ1` 到 `08_RouteQ4`）被展開成四問，但 Slide 74 的畫面上沒有任何指向，而 `21d4` 的檔頭註解也沒有記這條線。

- **建議**：`21d4_M2_PartsMap.tsx` 的檔頭補一行，記下它跟 `harness/04b_RouteIntro` 那一組的對應關係（這裡是三題，那裡是四題，多的一題是什麼），順便確認兩邊的題目沒有互相打架。
