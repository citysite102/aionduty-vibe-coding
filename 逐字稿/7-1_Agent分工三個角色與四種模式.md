## Slide 131｜三個角色：指揮者、執行者、審查者

**畫面**
開場一段講為什麼要拆，接著一段定義「子代理」。中間三個方塊橫排，中間有箭頭：指揮者（Orchestrator，主色）、執行者（Subagent）、審查者（Subagent），各附職責與「它實際是什麼」。下面兩塊：這三個都內建、以及你實際要決定的那一件事。

**逐字稿**

> 任務一大，一個 Agent 從頭做到尾就容易出錯。理由很具體：它得同時記著整份規格、正在改的那個檔案、還有哪幾項沒驗。
>
> 東西一多，最先掉的通常是最後那一項，也就是驗收。這一點你應該有體感了，它做完之後說「已完成」，但你去看會發現有兩項沒做。
>
> 所以把它拆成三個角色。
>
> 拆之前先把一個詞講清楚，因為它前面已經出現過十幾次了，但沒有正面定義過：子代理。
>
> 下面那兩個標著 Subagent 的就是子代理。你派它出去做一件事，它自己那一段來回不會回到你的對話裡，只把結論交回來。
>
> 那跟你自己另外開一個對話問它，差在哪？差在兩件事。第一，那邊得到的東西你要自己搬回來，子代理是主 session 直接派、直接收。第二，那邊的來回會佔掉那個對話的空間，而子代理的來回不佔你這邊的。
>
> 三個角色。
>
> 指揮者，負責拆解任務、決定誰做什麼。它實際上就是 Claude Code 的主 session，也就是你現在對著講話的那一個。所以你不用去「建」一個指揮者，你一直都在跟它講話。
>
> 執行者，照著規格動手改程式碼。它是主 session 派出去的。
>
> 審查者，只讀不寫，專門挑錯。再派一個，只給它讀的權限。
>
> 「只給它讀的權限」這半句很重要，它是這個設計成不成立的關鍵。審查者如果能改，它挑到錯就會順手改掉，然後你永遠不知道它挑到過什麼。
>
> 下面這一塊講的是成本：這三個角色都在 Claude Code 裡面，不用另外裝東西。
>
> 還有一個進階選項可以先知道：審查者也可以指定別家的模型。好處是它不會沿用執行者的思路，所以看得到執行者看不到的問題。但那是進階的，現在不用管。
>
> 最後這一句是你實際要決定的：每一件子任務由你親自派，還是讓主 session 自己決定派給誰？
>
> 這一題沒有標準答案，但它會一路跟著你到這一章結束。

**這頁的教學意圖**：三個角色是職能不是三套工具；子代理的定義是「來回不回到你的對話裡」；審查者一定要只讀不寫。
**預估時間**：5 分鐘

## Slide 132｜把角色組起來的四種方式

**畫面**
左半是一張會動的示意圖，跟著步驟換三種。右半四張卡，按步驟依序亮起：指揮者（適合邊做邊決定）、執行者（適合範圍明確的一件事）、自治團隊（進階，知道有這回事就好）、流程腳本（適合每次都一樣的流程）。

**逐字稿**

> 這四種是四種組法，右邊每一張卡的標籤寫的是它適合什麼，那一行才是判準。
>
> 第一種，指揮者。它把大任務切成小塊、決定誰做、最後驗收。
>
> 適用的情況寫在標籤上：邊做邊決定。也就是你還不確定該怎麼做的時候用它，它會看著中間產出隨時調整計畫。
>
> 這一種是你的預設。你現在對著 Claude Code 講話，它就是在做這件事。
>
> 第二種，一次只派一個執行者。指揮者派一個子代理出去，做完收回來再派下一個。
>
> 它的特性上一頁講過：有自己的一份記憶，做完只回報結果，過程不佔主對話的空間。
>
> 適用的情況是「規則清楚、不需要懂整體」的活。畫面上舉的三個例子很具體：翻譯、跑語法檢查、改一批檔名。這三件事的共同點是做的人不需要知道這個專案在幹嘛。
>
> 第三種，自治團隊。好幾個子代理同時做，各自認領任務。
>
> 這一種的機制值得聽一下，因為它跟你想像的可能不一樣：它們不會互相對話。它們是共同讀寫同一批檔案，那批檔案就是它們共用的白板。
>
> 標籤上寫著進階，知道有這回事就好。而且畫面上給了兩個很誠實的理由：白板要你自己設計和維護，還有你同時審核得了幾件事，就是它的上限。
>
> 第二個理由才是關鍵。你開五個子代理同時跑，產出速度是五倍，但你的驗收速度還是一倍。你只是把瓶頸從它那邊搬到你這邊。
>
> 第四種，流程腳本。把分工寫成固定的步驟腳本，每次都照同一套跑。
>
> 它的性格跟第一種完全相反：不能臨機應變，但每次都會走完同樣的步驟。
>
> 適用的情況是步驟已經確定、而且要重複很多次。你前面學過的 Skill 就是這個概念的輕量版。
>
> 所以四種排在一起，你會看到一條軸：從最有彈性但最不穩定，到最穩定但最不彈性。選哪一種，看你現在知道多少。

**這頁的教學意圖**：四種組法排在「彈性 vs 穩定」這條軸上；自治團隊的真正上限是你的驗收速度。
**預估時間**：6 分鐘

### 1.【矛盾】Slide 132 的「執行者」被當成四種分工模式之一，但它跟另外三個不是同一類

- 四張卡是指揮者、執行者、自治團隊、流程腳本。其中指揮者、自治團隊、流程腳本是三種**組織方式**，而執行者是一個**角色**。
- Slide 131 剛把指揮者、執行者、審查者三個並列成「角色」，下一頁就把執行者跟兩種組織方式並列。而審查者在這一頁整個消失了。
- 學員讀完兩頁會分不出來：到底是三個角色還是四種模式，執行者為什麼會同時出現在兩邊。
- **建議**：Slide 132 的標題與引言加一句限定，把這四張定位成「把角色組起來的四種方式」，並把第二張改寫成「一次只派一個執行者」（那才是跟另外三種同一層的組法）。這樣審查者的缺席也說得通了，因為它在哪一種組法裡都在。

### 2.【A-3 違規】Slide 132 有三組 `repeat: Infinity`

- 指揮者那張圖有兩組（任務往外飛、結果飛回來），自治團隊那張有一組擴散的圓圈。A-3 第 2 條的例外是「真的要表達系統正在運轉時，全頁最多留一組，而且必須慢速、低對比」。
- 這一頁是三組，而且其中兩組同時在跑。另外 `scale: [0, 2.5]` 的擴散圈屬於 `animate-ping` 的等價物，A-3 直接點名禁止的那一類。
- 這一頁還跟 Slide 48（`20_M2_HarnessIntro`，見單元 5-1 待處理第 2 條）是同一個毛病，照 B-6 該一起處理。
- **建議**：兩張圖各留一組，而且改成跟著 `currentStep` 觸發一次就停。這一頁是預錄的，講者不會停在上面讓它跑，循環沒有任何功能。

### 3.【缺漏】Slide 131 說審查者「只給它讀的權限」，但沒說怎麼給

- 這半句是整個審查者設計的關鍵（能改的審查者會順手改掉問題），口白與畫面都講了，但沒有說那個權限在哪裡設。
- 下一頁（Slide 134）的子代理設定範例裡也沒有權限欄位，只有 `name` 與 `description`，然後靠一句「不要自己動手改」用文字約束它。而整個章節五花了很多篇幅在講「文字說服擋不住」。
- 也就是說這門課教的審查者，實際上是用它自己說「擋不住」的方式擋的。
- **建議**：確認子代理設定支不支援限制工具（如果支援，Slide 134 的範例要補上那一行）。如果不支援，Slide 131 那半句要改寫成「只交代它不要動手」，並在 Slide 134 說明這一層只是約定、驗收要靠你看它有沒有改過檔案。不能兩邊各講一套。

### 4.【缺漏】Slide 130 的路線圖第四塊「收成」在這一章找不到對應

- 路線圖寫著四塊，最後一塊是「收成，確認手上多了什麼」，`weight` 給 1。對照 `npm run units`，這一章是 Slide 130 到 143，最後一頁是 `26g_M3_Harvest`（Slide 143），確實有。
- 但那一頁屬於單元 7-3（中型專案演練，Slide 136-143）的最後一頁，也就是它被包在第三塊裡面，沒有自己的單元。
- 這不算錯，但路線圖把它畫成第四塊會讓人以為還有一段。
- **建議**：不用改結構。把第四塊的 `note` 改成講得更具體一點（「三樣東西：審查子代理、一次實測、一個判準」），讓它看起來像第三塊的收尾而不是新的一段。
