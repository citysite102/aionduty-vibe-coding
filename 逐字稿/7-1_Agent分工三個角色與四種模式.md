## Slide 126｜Agent 分工與品質控管（分節頁）

**畫面**
分節頁，MODULE 3。路線圖三塊：分工（4，從一個 Agent 變成一組：三個角色、四種模式、workflow）、品質防線（4，做一個只讀不寫的審查角色，再看兩組角色怎麼分工）、中型專案（8，從 User Story 拆到 API、資料與規範，最後收成）。括號裡的數字是相對寬度。

**逐字稿**

> Hello，我是 Samuel，接下來進到第七章。前面那一章走完，你手上有一份手冊。它管的是做法：用什麼技術、檔案怎麼放、哪些不要做。
>
> 但它不會幫你確認成品對不對。所以到現在為止，檢查一直是你一個人在做。你交代，它做，然後你自己讀過去。
>
> 整條流程裡只有你一個檢查點。做計時器那種大小還可以。等到題目變成有好幾個檔案、有資料、還有一份規範要遵守的專案，你就讀不完了，而讀不完的那部分，等於沒有人讀。
>
> 這時候直覺的做法有兩個：下次交代得更仔細一點，或是把規範寫得更完整，畢竟前面那一章整章都在做這件事。
>
> 但規則能做的事有上限，而那個上限前面已經講過了。寫成文字，它讀得到，可是不保證每次照做。寫成 Hook，它在你設的範圍裡一定會執行，可是它管的是你動了哪個檔案、用了哪個工具，它不會去看倒數跑完之後畫面對不對。
>
> 兩種都管不到成品。而成品到現在為止，還是只有你在看。所以少的不是規則，是分工：把不同的判斷交給不同的角色，而不是讓同一個對話從頭包到尾。

> 這件事有一個名字，叫多代理協作，英文是 Multi-Agent。這一章整章都在做它，所以先把名字給你，你在外面看到這個詞，講的就是接下來這些。
>
> 講到這裡你一定會想問一個問題，而且這一題值得回答，因為它是這一章成不成立的前提：為什麼要另外開一個角色？我直接叫它「寫完自己檢查一遍」不就好了嗎？
>
> 兩個理由。第一，它在驗自己。同一個對話裡，它剛剛才決定要這樣寫，而那些「我為什麼這樣寫」的理由都還在它手上。你再叫它檢查，它多半會跟你說沒問題，因為它拿得出理由。
>
> 換一個乾淨的角色進來，它沒有那段過程，只看得到成品。看成品跟看自己的理由，結論會不一樣。
>
> 第二，標準可以不一樣。同一份東西，你可以派一個只看欄位有沒有缺、另一個只看用字有沒有問題。一個人同時盯三件事一定會漏掉一件，三個各盯一件不會。
>
> 所以這一章的前提不是「多開幾個比較快」，是有些判斷同一個對話本來就做不到。
>
> 角色也不會只有挑錯的那一種。挑錯的最容易看出效果，所以等一下動手做的就是它；但同一套做法換一組標準，就是另一個角色。
>
> 這一章後面就用講師、學生、觀察員跑過一次模擬，那三個沒有一個在看程式碼。之後你的專案需要什麼角色，就再開什麼。
>
> 三塊。最花時間的是第三塊，一個中型專案的演練，把需求、API、資料跟規範拆開來做，那是這一章真正的重頭戲。
>
> 前面兩塊是為它做準備：第一塊把三個角色跟四種模式講清楚，第二塊動手，先做一個會退回的審查角色，再換一組角色跑一次模擬。
>
> 這一章不用再裝任何東西，這些角色全部都在你已經在用的 Claude Code 裡。你也不用去管理一支 AI 團隊，要決定的只有一件事：每一件工作交給誰。

**這頁的教學意圖**：這是單元 7-1 的第一個畫面，要自己說得出整章在做什麼（B-2c）。三件事：為什麼需要的是**分工**而不是「指令寫更仔細」或「規範寫更完整」；這件事的名字是**多代理協作（Multi-Agent）**；以及**為什麼不能叫同一個 Agent 自己檢查自己**（它在驗自己、而且一個對話只有一套標準）。第三件是整章的前提，前面章節沒有講過，不要省；「一個對話裝不下」那個理由留給下一頁，這裡不要先講掉。理由借的是章節五、六已經建立的兩件事：文字規則不保證照做，Hook 管的是工具與檔案不是成品。同時先講明角色不只審查者一種，免得學員把整章的結論收窄成「做一個 reviewer」。重心在中型專案的拆解。

> **2026-09-23 改寫**：講師回饋開場讀起來像 AI 生成，而且沒有說明為什麼需要掌握角色。
>

## Slide 127｜三個角色：指揮者、執行者、審查者

**畫面**
開場兩句講為什麼要拆（一個 Agent 從頭做到尾，任務一大就容易出錯；它得同時記著整份規格、正在改的那個檔案、還有哪幾項沒驗）。第三句把這種做法的名字講出來：多代理協作（Multi-Agent），並補一句你還是只對著一個對話框講話。接著一個灰框定義「子代理」：派它做一件事，它自己做完，只把結論交回來；框底下兩句並排，一句是例子（讀了二十個檔案，你這邊只收到「問題在第 42 行」），一句是跟自己另開視窗問的差別。中間三個方塊橫排，中間有箭頭：指揮者（Orchestrator，主色）、執行者（Subagent）、審查者（Subagent），各附職責與「它實際是什麼」。下面兩塊：這三個都不用安裝，以及你實際要決定的那一件事（子任務你一個一個派，還是交代完整件事讓指揮者自己拆），那一塊底下並排兩句，兩邊各示範一次你實際會打什麼字。

**逐字稿**

> 為什麼一個 Agent 從頭做到尾不夠？理由很具體：任務一大，它得同時記著整份規格、正在改的那個檔案、還有哪幾項沒驗。
>
> 東西一多，最先掉的通常是最後那一項，也就是驗收。
>
> 這種情況你大概遇過：它做完之後說「已完成」，語氣非常肯定，但你去看會發現有兩項沒做。它不是在唬你，是它真的以為做完了。
>
> 所以要把它切開：同一件事不再由一個 Agent 從頭做到尾，而是切給好幾個，一個做一段。開場講的多代理協作，指的就是這個動作。
>
> 先擋一個會嚇到人的想像：這不是要你同時開五個視窗、自己在中間調度。你還是只對著一個對話框講話，分出去的那幾個由它派。
>
> 那要拆成哪幾個角色？三個。拆之前先把一個詞講清楚，因為它前面已經出現過十幾次了，但沒有正面定義過：子代理。
>
> 下面那兩個標著 Subagent 的就是子代理。
>
> 你派它出去做一件事，它自己那一段來回不會回到你的對話裡，只把結論交回來。那跟你自己另外開一個對話問它，差在哪？差在兩件事。
>
> 第一，那邊得到的答案你要自己複製、自己貼回來；子代理是主 session 直接派出去、直接收回來，中間不用經過你的手。
>
> 第二，它中間做的事不佔你這邊的空間。舉個實際的例子：它讀了二十個檔案才找到那一行，那二十次讀取留在它那邊，回到你這裡的只有「問題在第四十二行」這一句。
>
> 好，三個角色。
>
> 第一個，指揮者，負責拆解任務、決定誰做什麼。它實際上就是 Claude Code 的主 session，也就是你現在對著講話的那一個。
>
> 所以你不用去「建」一個指揮者，你一直都在跟它講話。
>
> 第二個，執行者，照著規格動手改程式碼。它是主 session 派出去的子代理。
>
> 第三個，審查者，只讀不寫，專門挑錯。它也是派出去的，但只給它讀的權限。
>
> 為什麼一定要「只給它讀的權限」？這半句是整個設計成不成立的關鍵。審查者如果能改，它挑到錯就會順手改掉。
>
> 聽起來很方便，實際上你損失了最重要的那個資訊：你永遠不知道它挑到過什麼，也不知道那一類錯誤是不是一直在發生。
>
> 這裡要澄清一件事，因為「三個角色」聽起來像三個要去哪裡安裝的東西。不是。你不用安裝、不用註冊任何東西。
>
> 指揮者就是你現在在對話的那一個，你一直都在跟它講話。另外兩個，你講一句話就叫得出來，像是「請一個子代理去檢查 index.html」。
>
> 常用的那一種再把它寫成 .claude 斜線 agents 底下一個檔案，之後點名就出場，下一段會動手做一個。
>
> 還有一個進階選項可以先知道：審查者可以指定用別家的模型，它就不會沿用執行者的思路，所以看得到執行者看不到的問題。但那是進階的，現在不用管。
>
> 你實際要決定的只有一件事：子任務你一個一個派，還是把整件事交代完，讓指揮者自己拆、自己派？
>
> 兩邊差在你打什麼字。你自己派是「先讓一個子代理去檢查 index.html」，一次講一件；讓它派是「把這個頁面做完，再檢查一遍」，中間要分幾個子代理由它決定。
>
> 這一題沒有標準答案，但它會一路跟著你到這一章結束。

**這頁的教學意圖**：擋掉「要同時顧五個視窗」的想像（名字在分節頁已經給過，這裡把它接到動作上）；三個角色是職能不是三套工具；子代理的定義是「來回不回到你的對話裡」；審查者一定要只讀不寫。
**預估時間**：5 分鐘

## Slide 128｜四種分工方式，各適合什麼時候用

**畫面**
左半是一張會動的示意圖，跟著步驟換三種。右半四張卡，按步驟依序亮起：指揮者（適合邊做邊決定，第一句先講明**指揮者不是你，是你正在對話的那個 Claude**）、執行者（適合範圍明確的一件事）、自治團隊（實驗功能，預設是關的）、流程腳本（適合同一套事要做很多遍）。走到第四格時左半的圖會換成三個階段，每個階段底下有一排同時派出去的點。

**逐字稿**

> 三個角色可以怎麼組起來？有四種組法，而且它們不是誰比較高級。第一種，指揮者。這裡先擋一個常見的誤會：指揮者不是你。
>
> 你現在對著 Claude Code 講話，它就是指揮者，你交代一件事，它把大任務切成小塊、決定誰做、最後驗收。
>
> 它適合的情況是邊做邊決定：你還不確定該怎麼做的時候用它，它會看著中間產出隨時調整計畫。這一種也是你的預設，不用設定什麼就已經在用了。
>
> 第二種，一次只派一個執行者。指揮者派一個子代理出去，做完收回來再派下一個。它的特性前面定義子代理的時候講過：有自己的一份記憶，做完只回報結果，過程不佔主對話的空間。
>
> 適用的情況是「規則清楚、不需要懂整體」的活。三個例子：翻譯、跑語法檢查、改一批檔名。
>
> 這三件事的共同點是做的人不需要知道這個專案在幹嘛。
>
> 第三種，自治團隊。這一種不是一個 Claude 派出幾個子代理，而是好幾個完整的 Claude Code 同時在跑，共用一張任務清單，誰有空誰就認領下一件。
>
> 它跟子代理最大的差別是隊友之間可以直接講話。你可以叫它們互相挑戰對方的結論，官方文件自己舉的例子就是五個隊友各查一個假設，然後互相反駁，留下來的那個才採信。
>
> 它標著實驗功能，而且預設是關的，要先設一個環境變數才打得開。所以你現在照著試會找不到，這是正常的。知道有這回事就好，理由有兩個。
>
> 第一，每一個隊友都是一份完整的 Claude，token 吃得比單一個工作階段兇很多，官方建議從三到五個開始。
>
> 第二個理由才是關鍵，因為多開幾個看起來永遠很誘人：你開五個同時跑，產出速度是五倍，但你的驗收速度還是一倍。
>
> 你沒有解決瓶頸，你只是把瓶頸從它那邊搬到你這邊。而且東西堆在你這邊的時候，你更容易亂放行。
>
> 這又回到前面那條判斷標準：你驗得動多少，就只能放手多少。
>
> 第四種，流程腳本。前面三種有一個共同點：下一步要派誰，是 Claude 每一個回合現場決定的。第四種把這件事先寫成一支腳本。
>
> 腳本裡寫的是分成哪幾個階段、每個階段同時派幾個、誰的產出要交給誰覆核。
>
> 所以它換到兩件事。第一，它一次派得動幾十個，而不是一次一個。第二，每跑一次都是同一個形狀，不會這次派三個、下次派八個。
>
> 代價是它中途不改計畫，腳本怎麼寫就怎麼跑。
>
> 你前面學過的 Skill 是這個概念的輕量版，差別在 Skill 寫的是一個人的做法，腳本寫的是一群人的分工。
>
> 四種排在一起，你會看到一條軸：從最有彈性但最不穩定，到最穩定但最不彈性。選哪一種，看的是這件事的步驟你確定了沒有。
>
> 還沒確定就用第一種，讓它邊做邊調；同一套步驟已經跑過五次都一樣，就往第四種挪，把它固定下來。
>
> 不要一開始就想寫腳本，也不要跑了五十次還在每次重講。

**這頁的教學意圖**：四種組法排在「彈性 vs 穩定」這條軸上；四種的分界是「下一步由誰決定」；自治團隊的真正上限是你的驗收速度。
**預估時間**：6 分鐘

## Slide 129｜workflow：Claude 寫腳本，一次派出幾十個

**畫面**
三塊。第一塊「先講問題」，拿三十份履歷當例子：現在的做法是一份一份派，底下三條列出卡在哪（要重複交代三十次、三十份報告全堆進同一段對話、很難確定第三十份用的還是第一份那套標準）。第二塊講它是什麼：你描述任務，Claude 先寫一支腳本，腳本寫的是流程（分幾個階段、每階段派幾個、誰的產出交給誰覆核）；寫好先給你看過，你同意才交給執行環境在背景跑；最底下一行小字說腳本只管流程不管判斷。第三塊是一組範例，左邊藍框印學員打的那一句（接續開場那三十份履歷），右邊印它送回來、等你按同意的階段清單三列：分批篩選同時派 6 個、覆核不通過的一份派 1 個、彙整 1 個；底下一句說那張清單就是腳本的樣子，不對就現在叫它改。再底下是一張實機截圖（Claude 桌面版的 Background tasks），跑的是產生三十份測試用履歷，六個子代理各五份，看得到階段名稱、每個子代理分到的範圍、各自的 token 與時間，整支 10 分 04 秒、651.1k token。第四塊是一張三列的對照表，左欄是問題，中間藍框是「你自己派子代理」，右邊靛框是「交給 workflow」，三列分別是下一步派誰、中間結果放哪、一次派得動幾個。

## Slide 130｜什麼時候用 workflow，怎麼叫它出來

**畫面**
四塊。第一塊「三種輪得到它的情況」三格並排，每格上半是這份簡報真的做過的工作、下半是換成學員自己的工作：同一件事分批同時做（九章一章一份）、同一份東西各查一個面向（用字、顏色、口白對畫面）、後一輪專門挑前一輪的錯；底下一句說只做一兩件事就不用它。第二塊「腳本從哪裡來，兩種」左右並排：別人寫好的那一支（`/deep-research`）、讓 Claude 現場寫一支（`ultracode` 與用你自己的話）；底下一句把兩者的關係講清楚。第三塊是一段可複製的 Prompt，底下講跑起來之後怎麼看進度、怎麼停。最後一個琥珀色的框講錢跟方案，開頭引上一頁截圖那支的 651.1k token。

**逐字稿**

> 三種情況，我拿這份簡報自己的事當例子，比較有感。
>
> 第一種，同一件事分批同時做。這份簡報分成九章，每一頁都要挑出「不寫程式的人會卡住的句子」。
>
> 這裡要注意做法：不是一頁派一個。一百多個子代理同時跑，你收到的回報會比簡報還長。是一章一份，九份同時跑，而且九份拿到的是同一段指示。
>
> 換成你的工作就是三十份履歷分成五批、八十份會議紀錄一批十份。分幾批不是看總數，是看你想收到幾份回報。
>
> 第二種，同一份東西，各查一個面向。同一頁我要查的不只一件事：用字有沒有踩到禁用詞、顏色有沒有超出規範、口白跟畫面對不對得上。
>
> 這三件事各派一個，各看各的，互相不干擾。一個人同時盯三件事，一定會漏掉其中一件。
>
> 換成你的工作就是同一份合約，一個看金額、一個看期限、一個看違約條款。
>
> 第三種，後一輪專門挑前一輪的錯。第一輪挑出來的問題，交給第二輪一條一條去反駁，推翻得掉的就丟掉，剩下的才送到我面前。
>
> 這一種自己派要來回兩趟，寫進腳本一次就跑完。換成你的工作，履歷初篩完，再派一輪專門找「這個人不該被刷掉」的理由。
>
> 這三種的共同點是同一套指示要用在很多份東西上。反過來說，只做一兩件事就不用它，直接派一個子代理比較快，也比較便宜。
>
> 接下來是腳本從哪裡來，這裡有一個很多人會搞混的地方。先講結論：腳本有兩種來源，一種是現成的，一種是現場寫的。
>
> 現成的那一支叫 `/deep-research`。它是 Claude Code 內建、目前唯一一支已經寫好的 workflow，後面接一個問題，它會分頭去查、互相對照，最後給你一份附出處的報告。
>
> 流程已經在裡面了，你不用描述。想先看看 workflow 長什麼樣，從這一支開始最省事。
>
> 另一種是讓 Claude 現場幫你寫一支。做法是把 `ultracode` 這個字寫進你自己那句話裡，它看到就不照平常一步一步做，而是先針對你這件事寫一支腳本。
>
> 不想記這個字也可以，直接說「用 workflow 跑這件事」，官方文件把它當成同一種開關。
>
> 所以 `/deep-research` 跟 `ultracode` 不是兩個不同的功能，它們叫出來的是同一種東西。差別在腳本是現成的，還是等你開口才寫。
>
> 畫面上這一段你可以直接拿去試：把計時器的每一個功能列出來，一個一個檢查在手機上會不會壞掉，每一條結論都要另一個子代理覆核過再回報。
>
> 注意最後那半句，那就是第三種，後一輪專門挑前一輪的錯。workflow 真正值錢的地方在那裡，不是只把子代理開多一點。
>
> 送出之後它不會馬上開始，會先給你一張要跑哪幾個階段的清單，你按同意它才動。跑的時候打 `/workflows`，看得到每個階段派了幾個、花了多少 token；想停就在清單上按 `x`。
>
> 最後講錢。上一頁那張截圖裡的那一支，十分鐘跑掉六十五萬 token，而它只是產生三十份測試檔案。
>
> 它一次跑掉的 token 比你在對話裡做同一件事多很多，而且一樣算進你方案的用量，所以第一次不要整個專案丟下去，先拿一個資料夾或一個窄一點的問題試。
>
> 另外免費方案沒有這個功能；Pro 方案有，但要自己到 `/config` 把 Dynamic workflows 打開。

**這頁的教學意圖**：三種形狀對應實際會用的三種做法（分批、分面向、覆核），而不是「一頁派一個」；`/deep-research` 與 `ultracode` 是同一種東西的兩種來源；它很貴，要先小範圍試。
**預估時間**：5 分鐘
