## Slide 162｜什麼是 Graph Engineering？

**畫面**
上半先給「工作節點」的定義，再說明前面那一套跑的就是這樣一件事。中間兩張圖：上面那張是一個節點裡面的執行、測試、修正、完成，底下一條虛線寫著測試沒過就回到執行；下面那張是拆解任務分出商品列表、會員登入、購物車三個節點，三個再匯回整合與驗收。最後一塊左右兩欄，用同一個電商題目對照兩層各自在回答什麼問題。

**逐字稿**

> 接下來這一段，我們要把視角往上拉一層。

> 先給一個名字。工作節點，英文是 Node：有一個講清楚的目標、有一套做完的標準、做完會交出一個東西。

> 前面那一整套，寫清楚目標、寫出什麼叫做完、讓它自己驗、沒過它自己改，跑的就是這樣一件事。

> 畫面上半這一張就是一個節點裡面的樣子。執行、測試、修正，測試沒過就回到執行再來一次，過了才算完成。這一圈我們在計時器那五題就讓它跑過一次了。

> 下半這一張是另一件事。一個題目先被拆成三塊，三塊各自去做、各自驗，不用等別人做完，最後再匯回來整合跟驗收。

> 這兩張圖不是在比誰好。Loop 在一個節點裡面，Graph 在節點跟節點之間，它們在不同的層。所以你不用選一個。

> 用同一個題目會更清楚。假設你交代 Claude Code 做一個電商網站。

> Loop 在回答的是：商品加入購物車這個功能，測試過了沒有？沒過的話它自己改得回來嗎？

> Graph 在回答的是：商品列表、會員登入、購物車，哪幾塊可以同時做？哪一塊非等共用的 API 做完不可？最後怎麼接起來，誰說可以交？

> 結論是兩層都要有，用剛才那個電商網站看最清楚。

> 第一種，只有 Graph，節點裡面沒跑那一圈。三塊同時開工，三塊都回報做完了，接起來才發現購物車根本加不進商品。三份沒人驗過的東西同時交回來，比一塊一塊慢慢做還難收拾。

> 第二種，只有 Loop，外面沒有 Graph。購物車做得很乾淨，每一條測試都過，但它排在會員介面後面等了三天，而這兩塊其實誰都不用讀誰的東西。

**這頁的教學意圖**：把兩層切開，建立「工作節點」這個詞，並且讓學員知道這不是二選一。
**預估時間**：4 分鐘

## Slide 163｜40 支影片轉字幕，一句話為什麼不夠？

**畫面**
開頭一句交代給 Claude Code 的話。接著一塊琥珀色的區塊列出五個它答不出來的問題。中間把同一個題目畫成 Graph：最上面是共用詞庫那一格，往下 40 支影片排成一張進度表，每一支裡面是語音轉錄、專有名詞修正、品質檢查，底下註明壞掉只重跑這一支，三條匯進一個統一的驗收閘門，最後輸出 40 份 SRT 加一張待人工複核的清單。最後是四個判斷問題。

**逐字稿**

> 這裡用一個我最近真的在做的題目來看。

> 我手上有 40 支影片，要全部轉成字幕檔。我可以直接跟 Claude Code 說：幫我把這 40 支影片轉成字幕，專有名詞要改對，時間軸要對得上，最後輸出 SRT 檔。

> 這句話它接得住。它會自己排一排，然後開始做。

> 但是琥珀色這一塊列的五件事，它沒有地方可以記，也沒有辦法回答你。

> 第二十三支轉到一半失敗了，要從哪裡接回去？40 支能不能同時跑，會不會打爆 API 的用量限額？轉出來了但字幕品質不合格，要不要整支重轉？中途斷掉之後，哪幾支已經好了？每一支是不是都用同一把尺驗過？

> 這五題沒有一題是把指令寫得更好就解得掉的。它們問的是這批工作怎麼排、狀態記在哪、壞掉從哪裡接回去。

**這頁的教學意圖**：給這一整個單元一個會痛的現場，讓學員看出這五題不是指令寫得更好就解得掉的。
**預估時間**：4 分鐘

## Slide 164｜從 Loop 到 Graph：什麼情況值得畫

**畫面**
上半把同一個題目畫成 Graph：最上面一格藍色的「先轉三支，整理出一份共用詞庫」，往下 40 支影片排成一張進度表，每一支裡面是語音轉錄、專有名詞修正、品質檢查，底下註明壞掉只重跑這一支，三條匯進一個藍色的統一驗收閘門，最後輸出 40 份 SRT 加一張待人工複核的清單。接著一塊把上一頁那五題一題一題對回 Graph 上。再來一塊講流程本身並不需要 40 個 Agent。下半藍色區塊是四個情境，各帶一個判定（不用／可能用得上／很適合／就是這種），最後一塊灰色補充。

**逐字稿**

> 排好之後就是這張 Graph。最上面先轉三支，整理出一份共用詞庫。40 支都要等它做完才能開始。

> 往下，40 支排成一張進度表，每一支記著現在跑到哪、過了沒有。每一支裡面是轉錄、改專有名詞、檢查品質，而且壞掉只重跑那一支。全部做完匯進同一個閘門，用同一套標準驗：檔案格式、時間軸、有沒有漏段。最後輸出 40 份字幕，外加一張要人看一眼的清單。

> 那剛才那五題呢？一題一題對回去。

> 第 23 支失敗了從哪裡接回去：進度表上記著每一支跑到哪，重跑那一支就好。能不能同時跑、會不會打爆限額：同時最多幾支是你設的上限，進度表排出接下來輪到誰。品質不合格要不要整支重轉：閘門判定，沒過的那一支退回去重跑。中斷之後哪幾支已經好了：狀態寫在進度表這個檔案裡，對話關掉也還在。每一支是不是同一把尺：同一個閘門跑 40 次，標準只有一套。

> 三題靠那張進度表，兩題靠閘門。而進度表是一個檔案，不在模型的腦子裡，對話關掉它還在，所以中斷了才接得回去。

> Graph 上最頂那一格是另一件事，我要特別講，因為它是這個例子裡唯一的依賴。

> 40 支彼此獨立，誰都不用讀誰的產出。但它們全都要等那份共用詞庫，不然同一個人名、同一個產品名，會在 40 支裡譯成 40 種。

> 這一條擋住全部：共用詞庫沒出來，40 支都不能開始；共用詞庫做錯了，40 支都要重跑。這就是前面講的依賴。

> 那會不會跑到一半才發現共用詞庫不夠？會，而且很常。底下這三格就是那個流程。

> 第一格，第 17 支的品質檢查冒出一個詞庫裡沒有的詞。第二格是重點：補進共用詞庫，那份表 40 支都在用。第三格，回頭重跑用到那個詞的那幾支，轉錄稿搜一下就知道是哪幾支。

> 整批不用重來，但也不能只改那一支。改上游的那一次，下游全部要跟著對一遍。

> 這裡有一件事我一定要講清楚，因為前面一整章都在講多 Agent 分工，很容易混在一起。

> 流程本身並不需要 40 個 Agent。實際上只要一個轉錄服務、一個負責校正專有名詞的模型，再加一段驗檔案格式的程式就夠了。Graph 講的是流程怎麼排、狀態記在哪、壞掉怎麼接回去，跟你派幾個 Agent 是兩件事。

> 所以你如果已經在用 n8n、Make，或者一段每天自己跑的腳本，那就是一張 Graph，只是沒有人用這個名字講它。

> 這一點我想特別說：這一段不是在教你蓋一套新東西。很多人手上的流程早就長這樣了，只是沒有把它畫出來、也沒有想過狀態要記在哪。

> 那到底什麼情況才需要畫？用四個情境看，從不用排到就是這種。

> 第一個，幫計時器加一個新功能。不用。Claude Code 一輪就把規劃、實作、測試、修正做完了，它中間自己派幾個子代理，也不等於你要畫一張 Graph。

> 第二個，同時開發電商的會員、商品、購物車。可能用得上。三塊各有自己的測試與驗收條件，你說得出哪幾塊同時做、哪一塊非等不可，整合失敗也知道退回哪一個。

> 第三個，每天跑一次的競品整理。很適合，而且它的形狀最完整。

> 幾個來源同時收，但要全部收完才合併去重；合併完才分得出價格、活動、商品三個角度，而那三個角度又可以同時跑；最後併成一份報告。

> 有要等的、有能同時做的，而且明天還要再跑一次。收資料那一段不用一個來源派一個 Agent，一段程式就做完。

> 第四個，40 支影片轉字幕。就是這種。40 支彼此獨立，每一支裡面是同一串固定的節點，某一支壞掉只重跑那一支。

> 它的依賴只有一條，就是剛才那份共用詞庫，但那一條擋住全部。

> 落在第一種情境就讓它跑一輪就好。一件小事拆成好幾塊，光是切開、傳來傳去、再接回來，花的時間跟錢就比直接做完還多。差別在量、在會不會重複做、在壞掉能不能只補一塊。

**這頁的教學意圖**：給這一整個單元一個會痛的現場，並且當場擋掉「Graph 等於多開 Agent」這個誤解。
**預估時間**：6 分鐘

## Slide 165｜先定義成功與失敗，再排出真正的依賴

**畫面**
上半一段文字回指前面學過的驗收，底下一張三欄的表，比較同一件事在 Loop 與 Graph 的差別（驗幾個、誰在驗、驗完往哪去），Graph 那一欄標成藍色。中間一塊講有一類條件要全部做完才驗得到，接著一塊灰色補充。下半列出五個工作、各自要讀誰的產出，最後一條藍色的線寫出真正的執行順序。

**逐字稿**

> 開工之前要先定兩件事，第一件是驗收。

> 驗收條件要寫成程式判定得了的，這件事我們在計時器那五題做過一次了。`/goal` 那一頁也講過，判定交給另一個模型，做事的那一個就不能自己放行。

> 不過換一個模型來判，只擋掉「自己說自己做好了」這件事。你給它的條件如果是「頁面要好看」，它一樣只能憑印象回答，換誰來判都會過。

> 所以這裡不重講條件怎麼寫，我們看的是同一件事叫驗收，在兩層的差別在哪，因為 Graph 多出三個 Loop 不會遇到的問題。

> 第一，驗幾個。在一個節點裡面，就一個單元、一套條件。在節點之間，是很多單元，而同一套條件要套很多次。40 支影片的驗收標準只能有一套，不然你根本不知道哪幾支是真的好。

> 第二，誰在驗。在一個節點裡面，驗的是自己剛做完的那一塊。在節點之間，驗收是一個只判定不做事的節點，它驗的是別人的產出。

> 第三，驗完往哪去。Loop 只有一個去處，沒過就重做。Graph 有三個：退回那一塊、要你點頭、直接放行。等一下看整張 Graph 的時候會再看到這三個。

> 還有一類條件最容易漏，它要全部做完才驗得到。

> 40 份字幕的檔案格式是不是同一套？三塊畫面接起來之後還跑不跑得動？同一個名詞在 40 支裡面有沒有翻成 40 種？

> 這幾題在任何單一節點裡面都看不到，因為每一塊自己都是對的。所以合併之後還要再驗一次，而且條件要另外寫。

> 不過這裡要說清楚，不是每一種品質都判定得了。視覺上好不好看、這個功能該不該做、使用者用起來順不順，這幾類沒有一條布林條件框得住，還是要人看過。能寫成條件的先寫成條件，剩下的留給你自己看，不要硬寫成條件丟給它。

> 第二件事是依賴。

> 你把五件事寫成一串，多半是因為你是照那個順序想出來的。真正該問的是：下一步真的讀得到上一步的產出嗎？說不出是哪個東西傳過去，那兩件事就沒有先後關係。

> 看底下這五個。A，講好 API 回傳什麼，誰的都不用讀。B 介面設計跟 C API 開發，兩個都只要讀 A 講好的那份格式。D 前後端接起來，要讀 B 跟 C 的產出。E 整合測試，要讀 D 的產出。

> 所以先做 A，B 跟 C 同時做，兩邊好了才做 D，最後 E。原本寫成一條直線的五步，其實只有三層。

> 這裡要特別講 A。很多人會把介面跟 API 直接標成可以同時做，但那只有在資料格式已經講好的時候才成立，不然兩邊各做各的，接起來要重做的比省下來的多。那份格式本身就是一個節點。

> 最後一句但書也要聽：能同時做，不代表開越多越好。兩個節點改到同一個檔案、用同一個測試環境、或是還沒講好資料格式就各做各的，接起來的時候要重做的比省下來的多。先確認它們碰的東西不重疊，再讓它們一起跑。

**這頁的教學意圖**：把驗收從 Loop 升級到 Graph（同一把尺套很多次、獨立的判定節點、三個去處、合併之後才驗得到的那一類），並且排出真實依賴。不重講條件怎麼寫，那在前面兩個單元做過了。
**預估時間**：7 分鐘

## Slide 166｜Graph 由哪四種節點組成，壞了怎麼退

**畫面**
上半一個小標「Graph 上每一格，都是這四種的其中一種」，底下一張表列出四種節點各自負責什麼、誰來做，表後一段說明流程往哪走只有拆解跟閘門決定，其中程式節點那一列標成藍色。中間一塊藍色區塊專講程式節點。下半四格顯示商品列表、會員登入、購物車、搜尋的通過狀態，只有會員登入是紅的。最後兩段文字說明這張單子誰寫、給誰、格式彈性在哪，底下左右兩欄：左邊一張可複製的退回單，右邊先說檔名行號不用自己找，再逐行解釋那幾個欄位在幹嘛。

**逐字稿**

> Graph 裡的節點只有四種。

> 拆解，把一件大事切成幾塊，決定誰等誰，這是模型加上你定的規則。執行，做完其中一塊，自己測、自己修，這可以是一個 Agent，也可以是一個現成的服務。閘門，看證據決定退回、要你點頭，還是直接放行，這是程式檢查，必要時加人看。

> 再補一件事。流程往哪走，只有拆解跟閘門決定：拆解決定切成幾塊、誰等誰，閘門決定這一塊過不過、要不要先問你。節點裡面怎麼判斷是它自己的事，不會改變流程的走向。

> 第三種是最容易被忘記的，而且它不用模型。

> 舉個例子。三個節點各交回一份資料，現在要把它們合起來、把重複的拿掉、照分數排好。這件事只有一個正確答案，規則你也說得出來，那就寫成一段程式，不要再叫第四個 Agent 來想。交給模型等於多花一次錢、多等一次，而且每次跑出來還不一定一樣。

> 判斷方式我給你一個很好用的：描述這件事的時候，你用不用得到判斷、決定、評估、摘要這四個詞？用不到就是程式的事。

> 這跟 Hook 那一段的道理是一樣的。寫成文字，每一次都要它重新判斷一遍；寫成程式，每一次都照同一段跑。

> 再來是退回。

> 假設四塊同時在做：商品列表過了、會員登入沒過、購物車過了、搜尋過了。

> 把四塊一起丟回去，那三塊原本是對的也會被重寫一次。重寫出來的版本只是不一樣，而你還得把四塊重驗一遍，其中任何一塊都可能這次換別的地方壞掉。一次失敗就這樣變成四個不確定的結果。

> 所以退回只退沒過的那一塊，而且要帶著證據退。

> 這張單子是閘門判定沒過的時候寫的，收件人是做那一塊的節點。你一個人用 Claude Code 的時候，閘門就是你，一次改四個檔案壞了一個，回頭貼給它的就是這段話。左邊這張你可以直接複製。

> 格式沒有規定。欄位名稱你要用中文也可以，寫成一段話也可以。要齊的是那五樣：哪一塊、過沒過、為什麼、你看到什麼、只准動哪一塊。少哪一樣，它就自己補一個。

> 指名退回哪一塊、判定結果、哪裡沒過、應該是什麼、實際是什麼、你看到什麼，然後是範圍，最後是最多重試幾次。

> 這裡有一件事要講清楚：檔名跟第幾行不用你找，那是它的工作。你給的是你看得到的東西，畫面怎麼了、紅字寫什麼。紅字怎麼讀，前面那一頁講過。

> 範圍那一行比看起來重要。少了它，它會打開那個檔案，順手看到旁邊兩個問題也一起改掉，你一個檔案的修正就變成四個檔案的改動，而且沒有人審過。

> 最後一行寫著三次。這裡要講清楚，最多重試幾次不是 Graph 才有的，我們在計時器那一輪寫過「最多 5 輪」。

> 不一樣的是次數用完之後。用 Loop 的時候，它就停下來等你看。

> Graph 多一個去處：把這一塊送回給負責拆解的那個節點，請它換個切法。例如把「會員登入」分成「登入表單」跟「登入後跳到哪一頁」兩塊，各做各的。

> 同一塊改三次都改不好，通常代表它一開始就被切得太大。

**這頁的教學意圖**：講完四種節點（重點在不用模型的那一種），以及退回要退多少、要帶什麼。
**預估時間**：6 分鐘

## Slide 167｜從規格到交付：拆解一張完整的 Graph

**畫面**
上半一張由上往下的 Graph：規格（標明不是節點）、拆解節點、三個執行節點（商品列表、會員登入、購物車，每一個裡面是做、測、沒過就改，三欄持續動著而且彼此錯開）、合併（標明就是程式節點）、閘門，閘門底下分成三格：紅色的沒過、灰色的過了但難收回、綠色的過了而且救得回來，再往下一段文字講閘門看東西的順序。

**逐字稿**

> 這張 Graph 從上往下看。

> 最上面是規格，寫著要做什麼、怎樣叫做完、哪些東西不能碰。那是你給的輸入，底下才開始是節點。

> 往下第一個節點是拆解，切成幾塊、誰等誰、哪一塊出錯最難收回。

> 中間三個是執行節點，就是剛才那三塊：商品列表、會員登入、購物車。每一個裡面都是做、測、沒過就改，那一圈就是前面幾個單元在講的 Loop。三塊是同時在跑的，畫面上它們各跑各的。

> 三塊做完往下合併，接起來並且比對這一輪改了哪些東西。合併這一格就是剛才講的那個程式節點，它不用模型。

> 再往下是閘門。它只回答一件事：這一塊能不能放行。它看四樣東西：測試過了沒、改到的檔案有沒有超出講好的範圍、這件事錯了救不救得回來、有沒有證據。

> 底下分成三個去處。沒過，只退回這一塊，而且帶著證據。過了但錯了難收回，停下來等你點頭。過了而且救得回來，直接放行。

> 閘門看東西是有順序的：先看程式跑出來的結果，再看這一輪的過程，最後才看它自己怎麼說。

> 它說自己有多確定，排在最後。因為那是這幾項裡面，唯一一個它自己影響得了的。

> 那該看什麼？答案在那五道邊界裡，就是那句話：這件事做錯了，你十分鐘之內救不救得回來。救不回來的，不管它多有把握都不放行。

**這頁的教學意圖**：把前面幾頁收攏成一張 Graph，並且講清楚閘門看東西的順序。
**預估時間**：4 分鐘

## Slide 168｜讓失敗成為規則：從錯誤回饋到下一輪執行

**畫面**
上半兩列流程，底下兩行小字把字幕那個例子接回來。第一列灰色的修正路徑（執行、測試沒過、修正，底下虛線寫著回到原本那一塊重做），第二列藍色的學習路徑（做完的結果、查出原因、寫成規則，底下虛線寫著進到下一輪的拆解裡）。中間一塊用計時器的手機按鈕走兩個階段，第一階段壓成一行、第二階段三行。下半一段灰底的 `CLAUDE.md` 片段。

**逐字稿**

> Graph 上那條退回的線，其實不只一條。

> 第一條叫修正路徑，它救的是這一輪。執行、測試沒過、修正，然後回到原本那一塊重做。前面那張退回單就是它。

> 第二條叫學習路徑，它救的是下一輪。做完的結果拿來查出原因，原因寫成規則，那條規則進到下一輪的拆解裡。

> 這裡要講精準一點：第二條靠的是你把驗證過的經驗變成它下次讀得到的東西，模型本身沒有重新訓練。

> 前面字幕那張 Graph 其實兩條都有。補一個漏掉的名詞、重跑那幾支，那是修正路徑，救的是這一批。下一批影片一開始就帶著那份更長的共用詞庫，那是學習路徑，救的是下一批。

> 用一個你手上就有的例子。你叫 Claude 幫計時器加一顆固定在畫面底部的開始鈕，桌機上好好的，手機上點不到。

> 第一階段，修正路徑。測試在手機尺寸下點不到，Claude 讀錯誤紀錄、改掉手機版的版面、重測，過了。到這裡那一輪就結束了，Loop 的工作做完。

> 第二階段，學習路徑。這時候多問一句：為什麼會做錯？答案是固定在畫面底部的按鈕，沒算到手機底部那條橫線佔掉的高度。

> 然後把它寫成下次就要帶上的規則，下一輪拆解就帶著它走。同時補一個手機尺寸的測試，不要只靠它記得。

> 那條規則長什麼樣，就是底下這幾行，直接寫進 `CLAUDE.md`：固定在底部的按鈕要留出手機底部安全區的高度、不能跟底部操作列重疊、要有一個手機尺寸的測試確認主要按鈕點得到。

> 下一次做任何固定在底部的東西，都從這一條開始。

> 最後一句很重要：這一條要你看過才寫進去。做成每次出錯就自動加一條的話，手冊會被偶發狀況灌爆，而那正是你在手冊健檢那一段在收的爛攤子。

**這頁的教學意圖**：把兩條回路分開，並且用一個學員手上就有的專案走完整個第二階段，包含最後那道人工審核。
**預估時間**：6 分鐘

## Slide 169｜經驗的五個落點，最後一個是流程本身

**畫面**
上半一張表，五種落點各自在做什麼、適合放什麼，最後一列「Graph 本身」標成藍色。中間藍色區塊標題是「在流程裡多插一個節點」，底下是流程的前後對照：原本是做畫面、整合測試、交付；改成中間多插一個「手機上點一次」。下半五個步驟（收、萃、驗、寫、用），第三個標成藍色。最後一塊灰色的框，裡面收著兩件事。

**逐字稿**

> 落點有五種。

> 第一種是 `CLAUDE.md`，讓之後每一輪都讀得到，適合放這個專案的開發慣例。第二種是 Skill，讓某一類工作照同一套流程走，像做畫面、做字幕、審程式碼。

> 第三種是自動化測試，把出過的問題變成每次都會跑的檢查。第四種是記下來的經驗，留著給人看，不一定要機器讀，像常踩的坑、當初為什麼這樣決定。

> 第五種最值得講，因為它改的是走法。

> 假設你發現做畫面的那幾輪，十次有六次卡在最後的整合測試，而且原因都是手機版。那與其每次都寫一條規則提醒它，不如在流程裡多插一個節點。

> 原本是做畫面、整合測試、交付。改成做畫面、手機上點一次、整合測試、交付。

> 之後每一輪做畫面的工作都會先過這一關，不會再等到最後才發現。改掉的是這一類工作的走法。

> 底下這五步是一條經驗從出錯走到下次用上的全程：收、萃、驗、寫、用。

> 收，把失敗原因、測試結果、怎麼修好的收在一起。萃，看看裡面有沒有下次還會遇到的東西。驗，確認它真的成立，而且不只適用這一次。寫，寫進手冊、測試、Skill 或 Graph。用，下次真的套上去，再看有沒有變好。

> 中間那一步最容易被跳過。跳過它，偶然發生過一次的事就會變成永久規則，手冊越長越肥，而且開始自己跟自己打架。

> 最後兩件事。

> 第一，Claude Code 沒有一個指令叫做這個。這一整套是 Graph 的設計，沒有對應的指令，也沒有要裝的東西。它給你的是材料：`CLAUDE.md`、Skill、Hook、測試，還有你自己寫的那段流程。要做到哪一步由你決定，從每次做完問一句為什麼會錯、然後手動加一條規則開始，就已經成立了。

> 第二，人不是只站在最後一步。如果規格一開始就寫錯，每一個節點都會通過測試，交出來的東西照樣不是你要的。所以至少留兩個要你點頭的地方：一開始的目標與驗收條件，以及高風險的東西交出去之前。

**這頁的教學意圖**：把學習路徑的落點講完，重點在最後一種（改流程本身），並且擋掉「這是某個可以裝的功能」與「全部自動化」兩種誤解。
**預估時間**：6 分鐘

## Slide 170｜怎麼叫 Claude 排出這張 Graph，排完怎麼跑

**畫面**
上半一個問句小標「如何和 Claude 討論工作流程？」，底下就是第一段可複製的 Prompt（先排 Graph）。中間藍色區塊列出三件自己要檢查的事。再來是第二段可複製的 Prompt（照 Graph 開工）。下半三種跑法（從你盯著到它自己跑），底下一段講跑順之後怎麼存起來。最後一塊灰色的框。

**逐字稿**

> 簡單講，這張 Graph 不會自己長出來，要你跟它講定。

> 前面那七件事它不會主動問你，所以第一句話先別派工作，把七條一次問完。

> 開頭兩行是目標跟完成的樣子，那是你在交辦一輪工作那一段學過的寫法。題目換成你自己的，七條照抄。

> 我念一遍這七條，因為每一條都是前面八頁的其中一塊。

> 第一，拆成哪幾塊，每一塊給一個名字，寫出它的輸入與產出。

> 第二跟第三是依賴。哪幾塊可以同時做，每一組要說明它們為什麼互不相干；哪幾塊必須排前後，每一條要指名是哪一個產出傳給下一塊。

> 第四，每一塊各寫一條完成條件，要能用程式判定，或我看一眼就能確認；寫不出來的就叫它標成「要人看」，不要硬掰一條。

> 第五，40 支全部做完、合併之後還要驗什麼，那是另外一組條件。

> 第六，退回規則：沒過的時候要回報哪些欄位、最多重試幾次、超過之後怎麼辦。

> 第七，進度表：記在哪一個檔案、每一塊會記下哪些狀態、中斷之後怎麼從裡面接回去。

> 最後那一行有兩件事。用清單或表格回答，不要寫成一段文章，不然你很難逐條檢查。還有「先給我這份，我看過再開工」，少了這一句它會一邊排一邊就動手。

> 它交出來之後，有三件事要你自己看，因為它這三個地方最常寫鬆。

> 第一，有沒有把「然後」當成依賴。每一條箭頭問一次：下一步讀得到上一步的什麼？說不出是哪個東西傳過去，就叫它拆開同時做。

> 第二，驗收條件是不是「看起來如何」。「品質良好」「格式正確」這種要退回去重寫，換成數得出來或看一眼就知道的。

> 第三，有沒有說進度表記在哪一個檔案。沒寫的話狀態就留在對話裡，換一個對話、換一台電腦它就接不回去，只能整批重來。

> 這三件改完，才貼第二段。第二段只有三條，都是它最容易忽略的：一塊沒過就只退那一塊；每做完一塊把狀態寫回那張進度表；最後那五種動作先停下來問你，就是你在五道邊界那一段看到的同一組：推上遠端、發信給別人、付款、刪除雲端資料、公開部署。

> 跑起來有三種做法，由鬆到緊。

> 第一種，你自己當閘門。一塊一塊交代，每一塊做完你自己看，沒過就照那張退回單退回去。慢，但你每一步都知道發生什麼事，第一次從這裡開始。

> 第二種，叫它自己跑。在那句話裡多加一句「用 workflow 跑這件事」，它會照你那張 Graph 現場寫一支腳本，然後自己跑完。分工那一段講過這個。

> 第三種，接到排程上。每天要自己跑一次的那種，接到 n8n、Make 這類工具上，或請它寫一段腳本掛排程。

> 還有一件事要補：跑順了就存起來。打 `/workflows` 選那一次按 `s`，它會存進這個專案，以後打那個名字就重跑同一張 Graph。

> 上一頁問「這件事會長期重複做嗎」，答是的話，真正省下時間的就是這一步，不是每次重打那段 Prompt。

> 最後一句提醒：第一次不要排到十個節點。挑兩塊可以同時做的先跑，看它的退回單長什麼樣、進度表有沒有真的寫進去，再把其餘的補上。

> 拆解那一步寫錯，底下每一塊都會照著錯的走，而且每一塊都會通過自己的驗收。所以你要到最後才會發現。

**這頁的教學意圖**：給學員一個可以直接打的起點，而且兩段 Prompt 的每一條都對應前面八頁教過的東西。三種跑法接回章節六的 workflow，不重教。
**預估時間**：7 分鐘
