## Slide 156｜把專案推上 GitHub，它才不只在這台電腦

**畫面**
頁首有 `LiveDemo`。上方三格風險：硬碟壞了、換一台電腦、想傳給別人看。中間一塊定義 GitHub，分兩用（給你自己用、給部署平台用）。下面一段可複製的 Prompt。最後一句講你不用打 git 指令。

⚠️ **這是單元 8-4 的第一頁**，所以口白前四段是整支影片的開場（這一段在做什麼、為什麼卡住你的是帳號不是程式），**畫面上沒有這幾句**，不要跳過。

**逐字稿**

> 前面那幾支做的都是同一件事：把一個功能交辦出去，讓它自己跑到完成條件過為止。計時器現在會記你跑過幾趟，也會自己驗。
>
> 但有一件事從頭到尾沒變過：它只存在你這一台電腦上。你沒辦法傳給任何人，換一台電腦也打不開。接下來這一段就是把它送出去，從存到 GitHub 開始，一路到拿一個手機打得開的網址。
>
> 先說一件事，免得你以為接下來還是一直貼指令：這一段卡住你的多半不是程式，是帳號跟授權。登入 GitHub、授權 Vercel、去 Supabase 複製金鑰，這幾下它做不到，因為那是你的帳號，它沒有你的滑鼠。所以這一段的節奏會變成「它做一段、停下來叫你點一下、你點完它再繼續」。
>
> 那個「停下來叫你點一下」其實你認得，就是前面講的人類閘門。只是這一次你沒有寫，它本來就過不去。
>
> 好，從第一步開始。你前面做的那些存檔點，一個都沒有離開過你這台電腦。這件事在三種情況下會變成問題。硬碟壞了，整個專案跟著沒了，沒有第二份。
>
> 換一台電腦，要自己複製資料夾，還常常漏東西。想傳給別人看，總不能把整個資料夾壓縮寄過去。
>
> 解法是 GitHub，它就是專案的線上存放處。
>
> 推上去之後，那些存檔點會有一份在雲端。它有兩個用途，而且第二個對你更重要。
>
> 第一個，給你自己用：換電腦、找回舊版本、給別人看，都從這裡。
>
> 第二個，給部署平台用。這一句請記住，它是後面走不走得下去的關鍵：Vercel 不是讀你的電腦，是讀 GitHub。
>
> 所以沒有推上去，後面部署整條路就接不上，不管你本機跑得多好。也就是說，推上 GitHub 不是備份而已，它是上線那條路的第一步。
>
> 這件事你前面學 Git 的時候就看過一次了，這裡是真的要用了。下面這段話可以直接複製：幫我把這個專案推到 GitHub。
>
> 設成 private 還是 public 先問我。推之前先確認沒有把密碼或金鑰帶上去。後面那半句不要刪掉，金鑰的事等一下會整頁講。
>
> 最後這句：你不用打任何 git 指令。它會自己建好、推上去，然後把網址給你。桌面版的 Code 頁籤右下角也有按鈕可以按。
>
> 但是有一件事它做不了，而且這是整堂課到現在第一次遇到，所以我要先講：它會停下來等你。前面每一步都是它自己做完的，所以第一次推的時候畫面停住，多數人的第一個反應是「壞了」。
>
> 沒有壞，是 GitHub 要確認你是本人。三件事只有你做得到。
>
> 第一，你要先有一個 GitHub 帳號。還沒有的話現在去 github.com 註冊一個，免費。
>
> 第二，第一次推的時候要在瀏覽器登入並且按同意。它會給你一段文字或一個連結，你照著做完，再回到對話框跟它說好了。
>
> 這一步跟前面講部署授權是同一回事，你的帳號它代不了。
>
> 第三，這個專案要設成 private 還是 public，要你決定。剛才那句 prompt 已經叫它先問你。
>
> 裡面有客戶資料或還沒公開的東西就選 private，之後隨時改得回來。
>
> 如果中間卡住、看不懂它在說什麼，最簡單的做法是把它給你的那段訊息整段貼回去，跟它說「我看不懂，告訴我現在要點哪裡」。

**這頁的教學意圖**：GitHub 有兩個用途，而「部署平台讀的是 GitHub 不是你的電腦」是後面走得下去的前提。
**預估時間**：4 分鐘（動手）

## Slide 157｜金鑰和客戶資料不能跟著推上去

**畫面**
兩個判斷並排。判斷一：public 還是 private，各附適用情境與一句限制。判斷二：哪些檔案不跟著走，列出幾個打叉的檔名。下面一塊介紹 `.gitignore`，並把它接回規則歸位的第一格。再一塊「它怎麼知道那串字是金鑰？」列出三種偵測方式、跑的位置與限制。最後一句講 Vercel 綁一次就好。

**逐字稿**

> 判斷一，公開還是不公開。public，想當作品集給人看、想讓人試用的選這個。而且有一個限制：免費帳號要用 GitHub 自己掛網頁的話，只能選這個。
>
> private，跟工作有關、裡面有客戶的東西的選這個。
>
> 這種要上線就接 Vercel，它吃 private。一般的建議是：不確定就選 private，之後隨時可以改成公開，反過來很麻煩。
>
> 但這一格選什麼，會決定你上線能走哪一條路。所以它是隱私的選擇，同時也是路線的選擇。等一下部署的時候會回來收這一題。
>
> 判斷二，哪些檔案不跟著走。畫面上打叉的那幾個就是不能推上去的。
>
> 為什麼要特別講，理由寫在下面：推上 public 之後才發現，刪掉也來不及，紀錄裡還留著。
>
> 這一句你在講安全邊界的時候聽過同樣的結論：金鑰一旦被推上去，就當它已經外洩了。
>
> 再來這一塊有一點里程碑的意思：這是你自己設的第一道機制。前面學了那麼多「規則要用擋的不要用寫的」，這是第一次你真的擋了一個東西。
>
> 擋住這些檔案的東西叫 `.gitignore`。列在裡面的檔案，git 根本不會碰。
>
> 這份清單是你自己列的，跟它說「幫我建一份 `.gitignore`，把金鑰、環境設定與客戶資料擋掉」它就幫你建好。
>
> 然後它把這件事接回去了：這就是前面規則歸位的第一格，會出事的交給機制，不要只寫進手冊。差別在於這次是程式在擋，不經過 AI 的判斷。
>
> 這裡會有人問一個很好的問題：所謂的檢查，程式真的分得出哪一串字是金鑰嗎？分得出來，但它不是看得懂你的密碼，它是在比對長相，三種做法疊在一起。
>
> 第一種，固定格式。各家服務發出來的金鑰有自己的開頭跟長度，有的還帶檢查碼，所以一看就認得出是哪一家的。
>
> GitHub 認得的那一組叫 partner patterns，掃到的時候它還會通知那家服務把那把金鑰作廢。
>
> 第二種，看旁邊的名字。那串字前面寫著 password、api_key、token 這類字眼，那就很可疑。
>
> 第三種，像不像亂碼。一長串沒有規律、唸不出來的英數字，本來就不像人會寫的文字。
>
> 跑的位置有兩個。掛在你機器上的檢查可以在推出去之前就擋下來；GitHub 那邊也會自己掃，公開的專案免費，而且掃的是整段歷史紀錄，不是只看你這一次推了什麼。
>
> 它偵測到的時候會直接把那一次推送擋掉，告訴你擋在哪一行。但限制要講清楚：它認得的是「長得像金鑰的字串」。
>
> 你自己取的那種好記的密碼，它只能靠第二點猜，猜不到就漏了。
>
> 所以真正的解法不是靠掃描，是一開始就不要寫進程式碼，放進 `.env` 再用 `.gitignore` 擋住，掃描只是最後一道。
>
> 所以你現在手上有兩道同一種性質的防線：`.gitignore` 擋 git，`settings.json` 的 deny 擋 AI 讀。
>
> 兩個擋的是不同的人，所以兩個都要有。只擋一邊，另一邊照樣會把東西帶出去。
>
> 最後那句是在預告下一步：推上去之後，Vercel 綁一次 GitHub 就好。之後你只要說「幫我更新上線」，它推完，網站自己跟著換新版。

**這頁的教學意圖**：public／private 的選擇會決定上線路線；`.gitignore` 是學員親手設的第一道機制。
**預估時間**：4 分鐘

## Slide 158｜部署上線：把 GitHub 上的專案接上 Vercel
**畫面**
上方一段長的 Prompt，底下一句解釋它為什麼那麼長。中間一塊 Vercel 的四步（登入、選 repo、按 Deploy、拿到網址），每一步附一句說明，底下一句講接上之後每推一次就自己重新上線。再下面一個灰底的 Callout 講 GitHub Pages 這條路，以及它的兩個限制（要 public、沒有環境變數可以放金鑰）。然後是「卡住的話，通常是這五件事」。最後一個綠色 Callout 講做完你手上會有什麼。

**逐字稿**

> 這一步要做的就是把網址生出來。先看這段 Prompt，它比前面幾段都長：幫我把這個資料夾部署到 Vercel。
>
> 先確認本機打開沒問題，推上 GitHub，再接 Vercel 完成部署。需要我去瀏覽器授權的時候停下來告訴我要點哪裡。
>
> 完成後把網址給我，並且確認那個網址真的打得開。
>
> 底下那句解釋了它為什麼長：它把要做什麼、什麼時候該停下來問你、做完給你什麼都講完了。這三段結構你應該認得，那就是這一章開頭那五個步驟的縮寫版。
>
> 中間那半句「需要我去瀏覽器授權的時候停下來告訴我要點哪裡」，就是 Human Gate。
>
> 因為授權這件事它真的做不到，它沒有你的滑鼠。
>
> 這門課只走 Vercel 這一條，四步。第一步，用 GitHub 帳號登入 vercel.com，不用另外註冊，也不用在電腦上裝任何東西。
>
> 第二步，選你剛推上去的那個 repo。如果你前面選了 private，它一樣選得到，只是授權的時候要把那個 repo 勾進去。
>
> 第三步，按 Deploy，等它跑完。計時器這種純前端的專案不用改設定，它自己判斷得出來要怎麼打包。
>
> 第四步，拿到網址，長得像「你的專案名點 vercel 點 app」，免費，馬上就能傳給別人。
>
> 接上之後有一件事會一直幫你：你每推一次，它就自己重新上線一次，網址不會變。這也回答了前面那個「為什麼要先推上 GitHub」：Vercel 看的是那個 repo，不是你的電腦。
>
> 底下那個灰框是另一條路，GitHub Pages。你在別的教學裡大概會看到它，所以我講一下它的限制在哪。做法是在 repo 的 Settings 找到 Pages，Source 選你的分支，存檔，就會拿到「你的帳號點 github 點 io 斜線專案名」。好處是不用再開一個平台的帳號。
>
> 但免費帳號的 repo 要設成 public 才掛得上去，而前面的建議是不確定就選 private。還有一件事等一下你就會撞到：再過兩頁你要把一把金鑰放進平台的環境變數，而 GitHub Pages 沒有那個地方，金鑰只能寫進程式碼跟著推上去。所以這門課一路走 Vercel。
>
> 兩邊的後台都會改版，按鈕位置跟名字可能跟我講的不一樣。流程不會變：推上 GitHub、授權、選 repo、部署。
>
> 這一頁的另外一半會比上面那段 Prompt 更花你的時間：卡住的五件事。
>
> 這五件不是你做錯，它們幾乎每個人都會撞到，因為它們都牽涉到你的帳號跟授權，那是它幫不了你的部分。
>
> 第一，它停下來叫我去瀏覽器點同意。這是正常的，第一次推上去要授權 GitHub，它沒辦法幫你點。點完回來跟它說「好了，繼續」。
>
> 第二，推不上去，說認證失敗。GitHub 現在不收密碼了。跟它說「幫我改用瀏覽器授權登入 GitHub」，它會帶你走一次。
>
> 第三，推上去了，但 Vercel 找不到我的 repo。private 的 repo 要在 Vercel 授權那一步勾進去，回到授權頁面重選一次，把那個 repo 加進可存取的清單。
>
> 第四，部署成功，但打開是一片空白。多半是 `index.html` 不在 repo 最外層，或程式裡寫死了你電腦上的路徑。把網址跟畫面截圖一起貼給它。
>
> 第五，我改了東西，但網址上還是舊的。改完要再存一次檔、再推一次，平台才會知道要重新上線。第五條特別標著「這是最多人以為壞掉的地方」。
>
> 請記住它，因為它不會有任何錯誤訊息，畫面上一片正常，只是內容是舊的，你會一直重新整理然後懷疑人生。
>
> 做完你手上會有什麼：一組別人打得開的網址，對方不用裝任何東西，手機也開得起來。然後是驗收方式，這一段請務必照做，不要用電腦開一下就算數：用手機開一次那個網址，不要用你部署的那台電腦，也不要連同一個 wifi。
>
> 手機開得起來，才代表它真的在線上，不是只有你這台打得開。
>
> 用手機打開之後你會看到那件事：紀錄是空的。那不是壞掉，是你在加航行日誌那一頁就知道的代價。

**這頁的教學意圖**：真的生出網址；Vercel 的四步裡哪兩步要自己點；GitHub Pages 的 public 限制是它不當主線的理由；五個卡點各自的處理方式。
**預估時間**：15 分鐘（動手，含實機）

## Slide 159｜手機打開，紀錄卻是空的

**畫面**
上方一組對照：你的電腦（12 趟、連續出勤 5 天）對上你的手機（0 趟、連續出勤 0 天），底下一句提問。中間一塊給答案，並引出資料庫（那個東西就叫資料庫、用 Supabase 這類託管服務），最後一行接到下一頁（接下來就把它接上去，四步）。下面一塊列部署平台後台的四個地方。最後一個 amber 的 Callout：綠燈不等於打得開。

**逐字稿**

> 我猜你第一個反應是「是不是哪裡做錯了」。沒有，這一頁就是要讓你撞到這件事。你的電腦上顯示 12 趟、連續出勤 5 天，手機上是 0 趟、0 天。同一個網址，同一個人，紀錄卻不一樣。
>
> 為什麼？這個答案你在加航行日誌那一頁就聽過了。因為 `localStorage` 是記在那台電腦裡的。它從來沒有離開過你的筆電。
>
> 這一句要聽清楚：網站是上線了，資料沒有。程式跟資料是兩件事。你上線的是程式，而資料從頭到尾都躺在你的筆電裡。這就是你在加航行日誌那一頁選擇的代價。
>
> 那時候 `localStorage` 讓你不用註冊、不用後端、不用付錢，一句話就有。它的代價現在來了。
>
> 要讓任何一台裝置打開都看得到同一份紀錄，就需要一個放在雲端、大家共用的地方。
>
> 那個東西就叫資料庫。你前面看過它的樣子（四張表那一頁），現在你知道它為什麼存在了。用 Supabase 這類託管服務就好，不用自己架，但會多出註冊帳號、金鑰、環境變數這幾下設定。
>
> 這件事等一下就做，四步，其中兩步要你自己動手。先把這一頁剩下的講完。
>
> 再來是實用的部分：部署交給它動手，但後台這四個地方你要自己看得懂。
>
> 這四個是 Vercel 的叫法，換一家平台名字不一樣，但這四種東西都會有。
>
> 第一，Deployments，每一次上線的紀錄。綠燈代表建置成功，紅燈點進去看最後幾行紅字，那就是它失敗的原因。
>
> 第二，Build Logs，建置過程的完整輸出。網站打不開的時候，這裡通常已經寫清楚是缺了哪個套件或哪個檔案。
>
> 第三，Environment Variables，金鑰與密碼放這裡。本機跑得動、線上壞掉，第一個要查的就是這一欄有沒有漏設。
>
> 第三條記一下，它是「本機好好的，上線就壞」這種情況的頭號嫌疑犯。
>
> 第四，Functions 或 Runtime Logs，網站跑起來之後出的錯記在這裡。建置成功但畫面是白的，答案幾乎都在這一頁。
>
> 再來要把最容易搞混的兩件事分開，這個混淆會害你查錯方向：綠燈不等於打得開。Deployments 那顆綠燈說的是「檔案送上去、建置沒有失敗」。
>
> 它不會幫你打開網站看一眼。綠燈配上白畫面是最常見的組合，原因多半在 Functions 那一頁的錯誤紀錄裡。

**這頁的教學意圖**：程式上線不等於資料上線；後台四個分頁各自對應一種症狀；綠燈只代表建置成功。
**預估時間**：6 分鐘

## Slide 160｜把紀錄搬上 Supabase，換台裝置也看得到

**畫面**
頁首有 `LiveDemo`。開場一句講接資料庫就是把紀錄從這台電腦搬到一個雲端的共用地方。中間四步，每一步右上角標著「你自己做」或「可以發包」：建表（發包）、複製可以公開的那把金鑰（自己做）、把金鑰貼進 Vercel 的環境變數（自己做）、打開 RLS 並寫一條規則（發包）。下半左邊一段可複製的 Prompt（五點），右邊兩塊：兩把金鑰只有一把該出現在前端（底下接回五道邊界的第二道），以及一個 amber 的 Callout「沒有登入，大家就是共用同一份」。最後一塊講做完怎麼確認。

**逐字稿**

> 這件事有解，而且不難：把紀錄從「這台電腦的瀏覽器」搬到一個雲端的共用地方，就是接資料庫。
>
> 程式那一段你不用寫。但下面四步裡有兩步得你自己動手，因為那是你的帳號跟你的金鑰，它沒辦法代你點。
>
> 第一步，開一個 Supabase 專案，建一張表。欄位就是你前面那三個：出發時間、飛行分鐘數、有沒有完成。表讓它幫你建，你只要在後台看一眼欄位對不對。
>
> 第二步，複製那把可以公開的金鑰。Supabase 會給你兩把，這裡要很小心：前端用的那把本來就設計成會被看到；另一把是後台用的，權限很大，這個題目完全用不到，不要複製它，更不要貼進對話。
>
> 第三步，把金鑰貼進 Vercel 的環境變數。這一步跟章節三講金鑰那四段是同一條路：不進程式碼、不進版控、執行的時候由平台餵給它。
>
> 第四步，打開 RLS，再寫一條規則。RLS 全名是 Row Level Security，白話講就是「這張表的每一列，誰能讀、誰能寫」。沒開的話，任何人拿到那把公開金鑰就能把你的表讀光、刪光。這一步不能跳過，案例三會整段講這個取捨。
>
> 畫面左下那段話可以直接複製。裡面第 1 點跟第 3 點不要刪掉，那兩句是煞車：第 1 點要它先列步驟不要動檔案，第 3 點是金鑰我自己填，你只要告訴我填在哪裡。
>
> 右邊這一塊解釋為什麼那把金鑰可以公開：純前端的網頁藏不住任何字串，使用者打開開發者工具就看得到。所以能放前端的只有那把本來就設計成可以公開的，而真正擋住別人的不是金鑰，是 RLS 那條規則。
>
> 底下那一句要停一下講：這是你整堂課第一次手上真的有一把金鑰。放手前那五道邊界的第二道就是在講這件事，當時我說等你真的拿到再回來做，現在就是那個時候。規則只有一句：不進程式碼、不進版控，執行的時候由平台餵給它。
>
> 最後這一塊我要先說，免得你做完發現不是你想的那樣：接上資料庫之後，換一台裝置確實看得到同一份紀錄。但這個計時器沒有帳號，所以別人打開你的網址，看到的也是同一份。
>
> 要變成「我的紀錄跟著我走」，還要再加一個登入。這就是為什麼章節三說 Supabase 是「資料庫加會員登入」兩件一起賣的。自己用的話，現在這樣就夠了；要給別人用，就把登入加上去。
>
> 做完怎麼確認？在電腦上跑一趟，然後拿手機開同一個網址。手機上看得到那一趟，才算接上了。看不到的話，九成是金鑰沒設進環境變數，或是 RLS 那條規則把讀取也一起擋掉了，把畫面截圖連同網址貼回去給它。

**這頁的教學意圖**：接資料庫四步裡哪兩步只能自己做；兩把金鑰只有一把能進前端，真正擋人的是 RLS；而沒有登入就是所有人共用同一份，這是這個題目解不掉的那一半。
**預估時間**：12 分鐘（動手，含實機）

## Slide 161｜DEPLOY.md：服務、資料、排程、金鑰

**畫面**
開場一段講計時器現在有兩個服務、一份跨裝置的資料、一把金鑰，四欄有三欄填得出來。中間一段可複製的 Prompt。下面四格：這個專案要幾個服務、資料存在哪裡、有沒有東西要一直醒著、哪些設定不能寫進程式碼，**每一格底下多一行「你的計時器：⋯」寫著那一欄的答案（兩個／Supabase 的一張表／沒有／那把 Supabase 金鑰）**。最後一個 sky 的 Callout「怎麼驗收它寫的那一份」。

**逐字稿**

> 你的計時器現在不只是一個網頁了：它有兩個服務、一份跨裝置的資料、一把金鑰。這一頁的四欄，你現在有三欄是真的填得出來的，而填不出來的那一欄剛好最重要，等一下講。
>
> 我不希望你把剛才那條路當成通用流程，然後下次照做撞得莫名其妙。要定時跑、要長時間算、要寄信的專案，走同一條路會在不同的地方卡住，而卡住的時候畫面上通常只有一句看不懂的紅字。
>
> 所以這一頁教的是一個動作：部署之前，先叫它寫一份診斷文件。這個模式你已經做過兩次了，我點一下你就會發現它其實是同一招：前面叫它讀完專案寫 `CLAUDE.md`，後來叫它讀完手冊跑健檢，這次是叫它讀完專案寫部署診斷。
>
> 形狀都是「叫它讀完產出一份文件，你負責驗收」。之後遇到陌生的場合，你可以自己套這個模式。
>
> 那段 Prompt 可以直接複製，它會要它回答四件事。
>
> 第一，這個專案要開幾個服務才跑得起來，各是什麼。你的計時器答案是兩個：網頁掛在 Vercel，資料在 Supabase。兩個各自要上線、各自有免費額度，壞掉的時候也要分開查。接資料庫之前你只有一個，第二個是剛才那一步多出來的。
>
> 第二，資料存在哪裡，換一台裝置還在不在。你剛才那一步就是在回答這一欄：本來存在瀏覽器裡，換一台就不見了，所以你把它搬到 Supabase 的一張表上。
>
> 第三，有沒有東西需要一直醒著。每天定時寄一封信、每小時抓一次資料，這種不能靠「有人打開網頁才跑」。
>
> 它要一個不會睡著的地方。你的計時器這一欄是空的，沒有任何東西需要定時跑，所以你到今天都沒撞到它。第三條是這四條裡最容易被忽略的，因為它在本機測完全看不出來，而且只有在你換一個題目的時候才會冒出來。
>
> 第四，哪些設定是金鑰或密碼，不能寫進程式碼。你的計時器有一把：Supabase 那把公開金鑰，它放在 Vercel 的環境變數裡，沒有跟著程式碼上去。
>
> 這一條你已經做過兩次了，一次是用 `.gitignore` 擋掉，一次是剛才親手把金鑰貼進環境變數。
>
> Prompt 裡還有兩句要注意。一句是「每一條都要指出你是從哪個檔案看出來的」。
>
> 另一句是「最後列出照現在這樣直接部署會先撞到的三件事，從最早撞到的開始排」。
>
> 第一句話的用途在最後那一塊：怎麼驗收它寫的那一份。它說得出檔名的那幾條，是真的讀過你的專案。說不出來的，多半是照一般專案的樣子寫的，跟你這個專案沒關係。
>
> 所以把說不出來的那幾條挑出來，問它一次：這一條你是從哪個檔案看出來的？這個驗收方式你應該覺得很熟悉了，前面那個審查子代理用的是同一招，看的都是它指不指得出來。

**這頁的教學意圖**：把「叫它讀完產出文件、你負責驗收」這個模式用在部署上；驗收只有一個問句，「這一條你是從哪個檔案看出來的」。
**預估時間**：6 分鐘（動手）
