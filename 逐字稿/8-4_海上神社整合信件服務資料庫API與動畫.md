## Slide 183｜案例四：海上許願神社

**畫面**
左邊一張成品截圖：海中央一座 low-poly 神社，紅色鳥居立在水裡，三艘船在周圍，右上角可以切白天、黃昏、夜晚。右邊 sky 底的框寫這個案例在練什麼（挑選合適的開發架構，實作更複雜的互動機制），底下是起點、過程、產出三列，每一列都是條列，內容照手冊的〈學員路線圖〉（起點兩條：一個空資料夾，以及另外下載的那一份成品；產出四條，收在「加一份開發日誌」）。中間一塊小標「和案例三的差別」，底下三列對照表，表底下四條：用到的技術（每個後面掛一句它負責什麼）／不用看懂程式碼／畫面上哪裡不對先截圖給 ChatGPT／貼給 Claude 之後先比對。最後一個 amber 的 Callout 講要你自己準備的三件：聲音素材、素材的授權、寄信服務；再下面一行是完整手冊與下載網址。再下面一塊「這份 PDF 可以直接給 AI 帶你做」：一段說明加一句可以複製的指令（五個案例頁都有這一塊）。

**逐字稿**

> 第四個案例，海上許願神社。網址是 www.wishingshrine.com，那是這個案例最後自己買、自己掛上去的網域，不是平台給的那一串。海中央一座神社，點水面會起漣漪，三艘船跟著浪起伏，右上角切白天、黃昏、夜晚。神社旁邊掛著一排繪馬，就是日本神社裡寫願望的那種木牌，點一塊可以讀別人的願望，也可以自己寫一張。
>
> 這個案例在練的是兩件事：挑選合適的開發架構，還有實作更複雜的互動機制。
>
> 為什麼要練這兩件？前三個案例畫面是靜的，改壞了你一眼就看到。這一個畫面每一幀都在動，船在晃、浪在跑、光線在變，改壞了你第一眼看不出來，所以架構跟驗收方式都得跟著變。
>
> 表上比的是案例三和這一個。登入、資料庫、權限這三樣案例三都做過，這個案例照同一套再做一次。多出來的是一個 3D 場景：畫面一直在動，改壞了不一定看得出來。
>
> 技術有五樣。Three.js 畫 3D；Astro 把程式整理成網頁檔案，案例三用的也是它；React 做介面，繪馬卡片、控制列、登入視窗都是它；Web Audio 管聲音；Supabase 管登入、資料庫權限、檔案和雲端函式。
>
> 你不用看懂裡面的程式碼。指令都由 Claude 下，設定檔你不用碰，手冊裡出現的程式碼和數字是拿來核對結果的。
>
> 接下來這兩條是做法，不是工具介紹。畫面上哪裡不對，這種問題很難用文字講，但截圖給得出來。所以我的做法是先把畫面截圖給 ChatGPT 看，跟它討論要改什麼，討論完請它寫成一份規格，再貼給 Claude。這個案例幾份長規格都是這樣來的。
>
> 但貼過去之後要先比對一次。ChatGPT 看不到你的程式，規格裡的套件、檔名、數字都可能跟你的專案不一樣。所以第一件事是叫 Claude 把規格和現在的程式碼比一遍，列出哪裡對不上，你確認完再讓它動手。
>
> 動手之前有三件事要先說，都是課程沒有幫你準備、要你自己處理的。
>
> 第一，聲音素材。五個環境音、五首背景音樂課程沒有附，你要自己準備。我這一份的五首背景音樂都是用 Suno 生成的。
>
> 第二，素材的授權。生成之前要先看那個工具的條款：免費方案常常只能個人使用，放到公開的網站上不算。
>
> 第三，寄信服務。網站是真的部署上線了，但 Supabase 內建的寄信只寄得到專案成員，要讓別人登入得自己接一個，那一步等一下會講到。
>
> 這一頁最底下有一行，〈海上許願神社〉這份手冊可以下載，網址印在上面。它要花好幾個小時，照著做得完，數字不用記。四個案例加上規格那一份，五份手冊都在同一個講義頁。

**這頁的教學意圖**：讓學員知道這個案例多出來的難題是「畫面一直在動，改壞了不一定看得出來」；以及長規格的做法（截圖給 ChatGPT 討論，貼給 Claude 之前先比對）。

## Slide 184｜水面、浮力與接合處

**畫面**
上方四張圖排成 2×2：第一張是黃昏海上神社的宣傳插畫（做完之後才畫的，說明寫「這個作品想給人的感覺」）；第二張是浮在米色背景上的方形石台，單色、沒有海；第三張是階段 1 做完的海上神社，海是平的、三艘船長得一樣；第四張是階段 16 的成品，水面有浪的層次、船各有船型。中間一塊列出八個階段的標籤（水面與光線、漣漪與船的浮力、時段與燈籠、接合處、環境動態、鏡頭、船型與雷雨、背景音樂）。下面左右兩塊：左邊 sky 底的小標是「每疊一層，就多一個接合處會出錯」，先講接合處是什麼、再用木樁與碼頭板的兩個數字講一次，然後列四處的症狀與兩邊各寫的數字，最後兩條是改法與寫進手冊；右邊是「改完拿什麼證明其他東西沒變」的三個方法，逐像素比對那一條底下還有兩個細項。最後一個 sky 的 Callout 叫「不會讀程式碼，一樣驗得動」，裡面用一二三分成三段：一、程式裡的錯在畫面上長什麼樣（三列）；二、所以這件事的分工是（你做的／它做的）；三、這一類檢查不要每次用問的（三條：盤點那一次列一遍／會重複驗的寫成測試／不能破的寫成 Hook）。

**逐字稿**

> 最左邊那張插畫，是這個作品做完之後才畫的宣傳圖，程式畫不出這一張。放在這裡只有一個用途：讓你先看到它想給人的感覺，黃昏、海面、一座安靜的神社。
>
> 右邊三張才是程式真的畫出來的，由左到右是時間順序。
>
> 第一張是最早的版本：一塊方形石台浮在米色背景上，屋頂、柱子、石頭都是單色的，沒有海，什麼都不會動。
>
> 第二張是階段 1 做完：神社落到海上了，但海是平的，三艘船長得一模一樣，樹只有一棵松。
>
> 第三張是階段 16：浪分成三道、有層次，船各有各的船型，介面整個重做過。
>
> 這兩張之間差了十幾個階段，分別是：水面與光線、漣漪與船的浮力、白天黃昏夜晚、把柱子與木樁接上、風與花瓣、鏡頭、船型與雷雨、背景音樂。
>
> 每一層都是單獨一個階段，都先寫清楚要什麼、做完怎麼驗，下一層才疊上去。一句「做得精緻一點」換不到最後那張的水面。
>
> 這一頁的重點在左下那一塊：每疊一層，就多一個接合處會出錯。
>
> 意思是這樣。疊上去的零件要跟底下那一層接在一起：柱子要頂到屋頂、木樁要站在碼頭板上。兩邊的位置如果是各寫各的數字，就會差一點點。
>
> 舉畫面上看得到的那一個：木樁寫在正負一點五的位置，碼頭板只到正負一點三。這兩個數字是分開寫上去的，一點五和一點三看起來差不多，但畫面上就是木樁站在板子外面，頂端根本沒碰到板子。
>
> 同一種毛病在這個案例出現四處。本殿後排柱：柱子一樣高，但屋頂底面是曲面，後排空出零點二五。碼頭木樁就是剛剛那一個。繪馬架：轉四十五度之後，前柱在 z 五點五五，砂利邊緣只到正負五點四，所以穿出去了。屋形船的篷：柱子在 z 正負零點五，篷的半徑是零點六六，柱頂懸在篷裡面。
>
> 改法每次都一樣：讓其中一邊用對方的數字去算。後排柱子的高度不要自己寫一個數，改成用屋頂的曲線算。之後把屋頂改高，柱子會自己跟著長。
>
> 到第四處，也就是船篷那一次，才把這一條寫進 `CLAUDE.md`。前三處都只修了那一處，木樁和繪馬架還是各寫各的數字。
>
> 再來是這整個案例的核心：改完之後，拿什麼證明其他東西沒變。
>
> 這個畫面每一秒重畫六十次，改壞了你看一眼看不出來，只能說「看起來沒壞」。所以要有三樣東西替你看。
>
> 第一個是逐像素比對：同樣的角度、同樣的時間各截一張圖，算出有幾個像素不一樣。搬進 Astro 那一步的要求是百分之零。比對的腳本是它寫的，你只看那個百分比。
>
> 這裡有一個很容易漏掉的前置動作。這個畫面本來就一直在動，所以開始改之前，要先用沒改過的那一版截兩張圖，自己跟自己比一次。
>
> 如果這兩張是百分之零，表示在那個角度、那個時間點，畫面每次都截得出一模一樣的結果。之後比出來的差異，才算是你改出來的。
>
> 這個案例第一次比對是百分之零點七五，不是零。先自己跟自己比過，才確定不是畫面隨機在變，然後去找是什麼在變，最後找到是「模擬其他人在祈願」那段，每次發生的時間都不一樣。
>
> 第二個是 Node 測試：浮力、選曲這種純算數的部分寫成測試，不用開瀏覽器就跑得完。
>
> 第三個是接合處的特寫截圖，左邊那四處被退的縫就是這樣看出來的：全景看不出零點二單位的差距，鏡頭要推到柱子和屋頂交界的地方才看得見。
>
> 最後一塊叫「不會讀程式碼，一樣驗得動」，它分成三段。
>
> 第一段。你自己做出第一版之後，請 Claude 盤點現況、寫成規格。它逐行讀你這一份程式的時候，會順手列出有問題的地方，我這一次是三個，你的版本不會剛好一樣。每一個你都讀不出來，但畫面上都有對應的症狀。
>
> 第一個：浪看久了會像在跳針。原因是三道浪的速度都是同一個數的倍數，整片海每六十二點八秒完整重複一次。
>
> 第二個：浪把船頭抬起來的時候，船頭反而往下壓。原因是俯仰的正負號寫反了。
>
> 第三個：同一個畫面在別台電腦上快慢不一樣。原因是好幾段過渡寫成每一幀乘固定比例。
>
> 第二段講分工。你做的是把症狀講準：什麼時候出現、哪個角度看得到、看起來是怎麼不對。「海浪看久了覺得在重複」「船頭的反應怪怪的」，這種程度就夠了。它做的是去查原因、提幾個修法，你從它給的方案裡挑一個。
>
> 所以這件事不是叫你去讀程式，這門課也沒有要你讀。講得出症狀，你就有辦法跟它討論。
>
> 第三段是怎麼讓這件事不用每次用問的。盤點那一次請它把看不出來的問題列一遍就好，這個案例的三個就是那時候抓到的。會重複驗的那幾條，像浮力、選曲這種算得出對錯的，寫成測試，改完先跑它。真的不能破的規則就寫成 Hook，讓程式去擋。寫成一句話，每一次都要它重新判斷一遍；寫成程式，每一次都照同一段跑。

**這頁的教學意圖**：精緻是一層一層疊出來的；每疊一層就多一個接合處，要接在一起的東西位置用對方的數字去算；改完要有三種方法證明其他地方沒變；不會讀程式碼也驗得動，你負責講症狀。收尾第三段接回章節五：會重複的檢查寫成測試或 Hook，不要每次重貼一段話。
**預估時間**：8 分鐘

## Slide 185｜中途為什麼要把專案搬進 Astro

**畫面**
開頭一行是 Astro 的 Logo 與 astro.build 的連結，接一句「這個案例做到一半，網站從一個 HTML 檔變成一個 Astro 專案，同一步裡介面也改成用 React 寫，畫面上看不出任何差別」。底下兩塊並排對照：左邊 sky 的「導入 Astro 之前」、右邊 indigo 的「導入 Astro 之後」，各三列（網頁有幾個／套件怎麼來／怎麼打開）。再往下兩塊一問一答：為什麼不是一開始就用、跟 3D 有什麼關係。最後一個 sky 的 Callout 講搬完怎麼確認沒壞。

**逐字稿**

> 這一頁要解釋一個名詞，因為前面那張技術表上出現過它，而且這個案例中途真的搬過一次。
>
> Astro 是一套做網站的工具。先看左右兩塊的差別。導入之前，整個網站就是一個 HTML 檔，加上拆出來的幾個檔案；套件直接從網路上載，電腦裡什麼都不用裝；要看的時候 Claude 給你一個本機網址，貼進瀏覽器就看得到。同一步裡介面也改成用 React 寫。
>
> 導入之後有兩個網頁：首頁，還有後面才加的 API 文件頁。登入、上傳、我的參拜紀錄都是首頁裡的面板，不是各自的網址。套件改成用 npm 裝進專案，而且版本寫死，之後不會自己變。另外多一個建置步驟，建置就是把你寫的東西整理成瀏覽器直接能用的檔案。
>
> 為什麼不是一開始就用？做 3D 那一段的時候，我先問過 Claude「要不要改成 React 那種架構」，它的回答是現在不用：畫面只有一個，狀態十幾個變數，拆成資料夾之後邊界已經夠清楚。後來要接資料庫跟登入、網站真的變成好幾頁，同一個問題再問一次，答案才變成要。
>
> 跟 3D 有什麼關係？沒有關係。3D 場景的程式一行都沒改，它是被掛進其中一頁裡的一塊。場景也沒有改寫成 React Three Fiber，因為重寫畫面上不會多任何東西，卻會打掉已經用測試跟逐像素比對驗過的水面、浮力跟燈光。
>
> 搬完怎麼確認沒壞？搬家這種事最怕的是「我也不知道哪裡變了」。所以搬之前先把舊版凍結起來，搬完跟它同角度、同時間各截一張，逐像素比對要零，畫面一個點都不能變。
>
> 另外一件在後面才用得到：登入要用的那兩把金鑰寫在一個叫 `.env` 的檔案裡，建置的時候 Astro 才決定哪一把寫進網頁、哪一把留在後台。接 Supabase 那一步會用到這件事。

**這頁的教學意圖**：Astro 在全片只出現過兩句，而這個案例的過程那一列寫著「中間導入 Astro 與 React」，不解釋學員會卡住。這一頁只講這個案例自己的敘事（什麼時候搬、搬前搬後差在哪、3D 有沒有被動到），「它跟 React 差在哪」是下一頁的工作。
**預估時間**：3 分鐘

## Slide 186｜Astro 與 React，以及這個案例的四層分工

**畫面**
開場一句講兩者最大的差別是「對網站應該怎麼運作的預設不一樣」。底下兩塊並排：indigo 的 React（當成會持續變動的應用程式）、sky 的 Astro（當成要快速呈現的內容，只在需要互動的地方加程式）。中間一塊是示意圖，上下兩排各六個同名的區塊（導覽列、文章內容、圖片區塊、頁尾、互動元件、動態搜尋）：上排整排 indigo，下排只有互動元件與動態搜尋亮著 sky、其餘是灰的；圖底下一行小字寫明這是跟典型 React SPA 比。再往下一張五列的表「什麼時候哪一個比較好」，接著一塊「這個案例最後怎麼分」：一張四列的表（Astro／React／Three.js／Supabase），兩欄是「在這個網站裡做什麼」與「代價」，底下隔一條線是好處與代價那一段，收在「避免同一份狀態有兩個地方在管」的具體說明。最後一個 sky 的 Callout 講一件容易誤會的事，底下掛 docs.astro.build 的連結。

⚠️ **這一頁不要講成效能比較。** 它的論點是預設不同，不是誰比較快。圖底下那一行但書要念，少了它這張圖就變成「React 一定比較慢」。

**逐字稿**

> 這一題值得單獨講，因為它最常被問：我已經有 React 可以把畫面切成一塊一塊重複用了，那 Astro 到底幫上什麼？
>
> 兩者最大的差別，不是誰比較新、誰比較快，是它們對「網站應該怎麼運作」的預設不一樣。
>
> React 把網站當成一個會持續變動、互動的應用程式。整個畫面交給它管，所以瀏覽器要先下載那一包程式。
>
> Astro 把網站當成一份應該快速呈現的內容，只在真的需要互動的那幾塊才加程式。而且它可以直接用 React 寫那幾塊，兩個不是互斥的。
>
> 中間這張圖就是這件事。兩排的區塊名字一模一樣：導覽列、文章內容、圖片區塊、頁尾、互動元件、動態搜尋。
>
> 上面那一排是常見的純前端 React 架構，整排都由 React 管，所以瀏覽器要下載的程式比較多。
>
> 下面那一排是 Astro。灰色那四塊是直接送出去的現成網頁，只有亮起來的兩塊要載入程式。這個做法有個名字叫群島架構，Islands Architecture，那兩塊就是島。島還可以指定什麼時候才載入，例如等使用者捲到它才載入。
>
> 這裡要講公平話：這張圖比的是 Astro 跟典型的純前端 React。React 搭配 Next.js 那類框架，一樣做得到伺服器先產生 HTML。所以它不是「React 一定比較慢」。
>
> 那什麼時候哪一個比較好？品牌官網、部落格、課程頁這種，Astro 很適合；搜尋引擎要讀得到內容，Astro 預設就是。反過來，儀表板、後台報表，用 Astro 可以但未必划算；複雜的表單跟狀態，在 Astro 裡那一塊還是用 React 寫；即時協作、拖曳操作這種，Astro 不適合當主架構。
>
> 講完一般的選法，回到這個案例最後怎麼分。它們不是二選一，這個網站四層一起用，一層負責一件事：登入視窗、繪馬卡片是 React 寫的島，其餘的頁面是 Astro 直接輸出的網頁。
>
> Astro 組成網站頁面，讓網址、文件與分享資訊有一致的管理方式；React 負責互動介面，依照登入、選取、載入與錯誤等狀態呈現畫面；Three.js 專心處理 3D 場景、相機與場景動畫；Supabase 負責認證、資料與權限。
>
> 右邊那一欄是代價，這一欄要念。Astro：首頁幾乎都是互動內容，只用到它的一小部分，不用它也做得出這個網站。React：多一套要懂的東西，而且首頁要等程式下載完介面才出現。Three.js：3D 跟介面要自己接線。Supabase：規則要自己寫對，寄信還要另外接一家。
>
> 這樣分工的好處，是新增介面功能的時候比較容易控制影響範圍，也能分別測試各層。代價是工具與整合規則變多，所以每一層都要有清楚的責任，避免同一份狀態有兩個地方在管。那一句在這個網站裡的意思是：「現在開著哪張卡片」由 React 管，「船現在在哪裡」由 Three.js 管，「誰能讀哪一筆繪馬」由 Supabase 管。兩個地方同時管同一份資料，畫面就會對不上。
>
> 最後一件容易誤會的事：Astro 也不是只能做靜態網站。它一樣做得到由伺服器即時產生頁面、對外開 API。只是當整個網站都要複雜互動的時候，它原本的優勢就比較用不上。

**這頁的教學意圖**：回答「有 React 為什麼還要 Astro」，而答案是預設思維不同，不是效能數字；那張圖讓「只有兩塊要載入程式」變成看得到的；「什麼時候 React 反而比較好」一定要給，否則學員回去碰到儀表板那種題目會選錯；收尾給這個案例自己的四層分工，而且好處與代價都要講，只講好處就變成在推薦一套技術堆疊。
**預估時間**：5 分鐘

## Slide 187｜背景音樂、登入、資料庫、對外 API 與寄信

**畫面**
五格，兩欄排列，**一格一格出現**，而且**只有正在講的那一格是亮的**，其餘淡下去，五格都出現之後全部恢復，標題列是「序號＋圖示＋名稱」：1 背景音樂、2 會員登入（標主色）、3 資料庫與權限、4 對外 API、5 寄信服務（Resend）。每一格固定三段：先一句「為什麼用到」，再一段「設計與指令的重點」，最後一段「做完檢查這個」。最後一下出現的是右下角那一格 amber 的 Callout，講「需要登入」不等於權限控管。它裡面是兩條並排的路線圖（使用者從網站進來／別人的程式根本沒開網頁），每一段之間有一顆會跑的光點，第二條的「登入視窗」畫成虛線並打叉，被跳過的那一段是灰掉的箭頭、沒有光點。

**逐字稿**

> 這五樣都不是 3D 的事，每一格左上角的號碼是它們被做出來的先後。它們一格一格出現，每一格我都先講為什麼會用到它，再講做的時候要交代什麼，最後是做完要檢查什麼。
>
> 第一格，背景音樂。為什麼用到：一個會動的 3D 場景沒有聲音就少一半，而現成的曲子多半不能放進公開的網站，所以五首都是自己用 Suno 生成的。
>
> 做的時候三件事：三首綁白天、黃昏、夜晚，另外兩首可以自己指定；面板上三條音量，總音量、音樂、海浪與雨，想把音樂關掉只留海浪聲，這三條分得開；兩首交叉的時候各自是零點七零七，不是零點五，這樣合起來聽到的響度才不會凹下去。
>
> 做完檢查兩件：連續切時段，不會有兩首疊在一起，選曲和淡化都寫成測試了；還有一件更重要，放上公開網站之前先看那個生成工具的條款，免費方案常常只能個人使用。
>
> 第二格標了主色，會員登入。為什麼用到：繪馬要記得是誰寫的，網站就得先知道來的人是誰。沒有這一層，「我的參拜紀錄」做不出來。
>
> 做的時候：介面只呼叫六個函式，後端是真是假它不知道。所以先做一個假後端，不寄信、登入碼一律 123456，把流程跑通；流程確定對了，再換成 Supabase 的信箱連結登入，網站的介面一行都不用改。
>
> 做完檢查：在哪個瀏覽器點信，就在那個瀏覽器登入。還有一件上線前一定要看的，正式站的登入視窗要寫「寄登入連結」，不能還留著開發用的密碼登入。
>
> 第三格，資料庫與權限。為什麼用到：繪馬要留得住，而且別人改不動你的那幾塊。這一層不做，網站看起來是對的，但資料誰都動得了。
>
> 做的時候三件：繪馬的內容是公開的，但「這一塊是誰寫的」另外放一張表，不併進公開那一張，不然別人從公開的牆就反查得出哪幾個願望是同一個人寫的；每個帳號十分鐘最多掛五塊，這個限制由資料庫擋，不是靠前端的按鈕；前端那把金鑰本來就會被看到，擋住別人的是資料庫的規則。
>
> 做完檢查：用第二個帳號登入，看得到別人的繪馬，但改不動也刪不掉。
>
> 第四格，對外 API。為什麼用到：別人想把繪馬牆放進自己的網站或程式，就需要一個不經過你的網頁也呼叫得到的入口。
>
> 做的時候：讀繪馬牆不用登入，寫入要帶登入權杖，也就是登入之後拿到的那串通行碼，權限一樣交給資料庫。另外附一頁文件，寫網址開頭、權杖怎麼帶、端點表、錯誤代碼、還沒開放的項目。
>
> 做完檢查：不帶權杖呼叫要回 401。文件頁上就能按「不帶權杖呼叫」和「帶我的權杖呼叫」，當場看回傳差在哪。
>
> 第五格，寄信服務。這一格是前面那個初稿的但書的答案。
>
> 為什麼用到：Supabase 內建的寄信每小時大約兩封，而且只寄得到專案成員的信箱，所以一般訪客根本收不到登入信。要讓別人登入得進來，就得接一個自己的。
>
> 做的時候：接法是把自訂 SMTP 填進 Supabase，網站的程式一行都不用改。我用的是 Resend，免費方案大概是每月三千封、每天一百封、一個網域，這些數字各家會變，照它官網為準。還有一件，那把 API 金鑰的權限只給寄信，而且只貼到 Supabase，不進程式碼。
>
> 做完檢查：Resend 後台那個網域的狀態要變成 Verified；然後用一個不是專案成員的信箱登入，看收不收得到信、點連結回不回得到網站。
>
> 最後右下角這一格，是這一段最容易誤會的事：做完登入介面那一步，網站看起來已經「要登入才寫得了繪馬」。但那是兩條路線裡的其中一條。
>
> 第一條，使用者從你的網站進來：先碰到登入視窗，再碰到資料庫的權限規則，擋兩次。第二條，別人的程式根本沒開你的網頁，它直接對資料庫送請求：登入視窗完全沒碰到，只剩資料庫那一層在擋。畫面上第二條的登入視窗是虛線打叉的，那一段的箭頭也是灰的，沒有光點走過去，那就是「繞過」。
>
> 真正擋住他的是後面那三張表的權限規則。這件事案例三的兩層權限講過一次，在這裡換一個形狀又出現了一次。

**這頁的教學意圖**：五樣外掛的東西各自為什麼會用到、做的時候要交代什麼、做完檢查什麼；介面流程不等於權限控管，真正擋住人的是資料庫的規則。
**預估時間**：8 分鐘

## Slide 188｜系統架構：三個入口，權限都在資料庫

**畫面**
開頭一句只解釋權杖（登入成功之後拿到的那串通行碼，一小時有效）。底下三欄並排（**欄與欄之間沒有箭頭**，它們是位置不是流程）：使用者的瀏覽器（3D 引擎、介面外殼、公開金鑰）、Supabase（Auth 會員、Postgres 資料庫、Storage、Edge Functions）、外部（Resend 寄信、別人的程式）。再下面是**一整個淡 sky 的匯流框**，框裡上半是三個入口並排（你的網站、別人的程式、API 文件頁），底下三條短豎線接到一條橫線，再由中間一支箭頭往下；光點先各自走到橫線，中間那一顆再把它們帶下去。框底就是權限規則那一塊，列四條路線各自要不要帶權杖，盾牌 icon 會慢慢亮一下。最後一個 sky 的 Callout 講三個入口走的是同一個資料庫。

**逐字稿**

> 先講一個待會每一條路線都會用到的詞：權杖，就是登入成功之後拿到的那串通行碼，一小時有效。
>
> 上面三塊是東西放在哪。先從左邊看起。
>
> 左邊是使用者的瀏覽器。這個網站本身是一包靜態檔案，放在 Vercel 上，裡面有 3D 引擎、介面外殼，還有那把公開金鑰。公開金鑰寫在網頁裡，任何人都看得到，這件事本來就是這樣，不是誰做錯。
>
> 中間是 Supabase。這個專案沒有自己的伺服器，登入、資料庫、照片、對外 API 全部在這裡。信箱連結登入成功之後，它會發一張權杖給你，一小時有效。
>
> 右邊是外部。一個是 Resend，登入信從那裡寄出去；另一個是從外面呼叫 API 的人，他的程式直接呼叫 Edge Functions 對外開放的那幾個 API 網址，根本不會經過我的網站。
>
> 注意那三塊之間沒有箭頭。它們是位置，不是順序：右邊那個「別人的程式」不是走完 Supabase 才出現的，他跟你的網站一樣是一個入口。
>
> 看下面那一列。同一份資料有三個入口：你的網站、別人的程式，還有文件頁上那個可以當場按的試呼叫。別人的程式還有第二條路：網頁裡那把公開金鑰他也拿得到，可以直接讀寫資料表。畫面上三條線會收成一條，再往下指到同一個地方。
>
> 那個地方就是這一頁要你記住的：資料庫自己的權限規則，每一次查詢都重新檢查一遍權杖是誰。不是進來的時候檢查一次就算了。
>
> 框裡面灰字那一條是不用登入也走得通的，讀繪馬牆就是。亮起來那三條要帶權杖：掛繪馬與祈願、上傳照片、看我的參拜紀錄。
>
> 這就是為什麼前一頁說，介面上的登入視窗擋不住人。他繞過介面，繞不過這一層。
>
> 完整的那張架構圖在手冊裡，上面連每個檔案放在哪、每個端點的網址都有。這一頁只留你要判斷的那一件事。

**這頁的教學意圖**：把前兩頁的零件接成一個系統，並且讓學員看出「入口有三個、把關的只有一層」。
**預估時間**：4 分鐘

## Slide 189｜AI 無法幫你決定的事情

**畫面**
一張三欄的表（這一題／判斷依據／判斷錯的代價），八條一列一條，由上往下讀，左欄會出現兩個分組標題：畫面與素材（前四條）、登入與資料（後四條）。代價那一欄寫的都是畫面上或資料上看得到的後果。第一列整列標主色，底下掛著一行「逐像素比對、Node 測試、接合處特寫，就是拿來量的那三樣」。最後一個 sky 的 Callout「表上這幾條的共同點：錯了不會當場報錯」，底下三條是照代價那一欄去試的動作。

**逐字稿**

> 這一個案例的八條沒有單一的主題，因為它接上的東西最多：3D、音樂、登入、資料庫、對外 API。
>
> 八條分成兩組，左欄上面有標：前四條是畫面與素材的，後四條是登入與資料的。
>
> 標起來的是第一條：畫面不對的時候，先叫它報出數字，還是直接叫它改。
>
> 判斷依據是，它說不說得出那個地方現在的數字，座標、尺寸、重複的秒數都算。說不出來就是在猜。第一個修法沒效的時候，要它回頭報數字，不要讓它猜第二次。怎麼量？就是上一頁那三樣：逐像素比對、Node 測試、接合處的特寫截圖。
>
> 代價那一欄寫的是真的發生過的事：畫面縮小的時候，下緣會露出一塊空白。第一次的修法是把海加大，沒有用。真正的原因是鏡頭太近，把前景切掉了。沒有先量，就會一直加大那片海。
>
> 前四條是畫面與素材的，後面四條是登入與資料的。
>
> 我挑三條講。第四條：這首曲子能不能放進公開的網站與教材。判斷依據是，它是誰的錄音；如果是 AI 生成的，那個工具的條款允不允許你公開使用。代價是，網站一上線，就是在散布一首你沒有權利散布的錄音。這一條跟你會不會寫程式完全無關，但它是這個案例裡最容易出事的一條。
>
> 第六條：願望是誰寫的，要不要跟願望存在同一張表。資料庫的規則管得到「哪幾筆資料看得到」，但管不到「同一筆裡面的哪一欄」。願望要公開、名字不公開，就只能分成兩張表。不分的話，別人從公開的繪馬牆就反查得出，哪幾個願望是同一個人寫的。
>
> 第八條更隱形：錯誤訊息叫你把權限開給沒登入的人，要不要照做。判斷依據是，這個「拒絕」是不是本來就該發生。照抄那一行，沒登入的人就讀得到所有人的祈願紀錄。
>
> 最後一塊收的是這八條真正的共同點：代價那一欄沒有一條是當機或紅字。網站照樣會動、畫面照樣對，錯的地方要等別人撞到才知道。
>
> 所以要自己照代價那一欄寫的狀況，一條一條試一次。換第二個帳號登入，讀讀看別人的那幾筆；不開網頁，直接打一次你的 API；把那首曲子、那張圖的授權頁翻出來看。
>
> 這三個動作換到你自己的專案一樣成立，而且不需要你會寫程式才做得到。

**這頁的教學意圖**：這八條沒有單一主題，因為這個案例接的東西最多；收尾收的是它們的共同點（錯了不會當場報錯），所以驗的方式是照代價那一欄去試一次。
**預估時間**：6 分鐘
