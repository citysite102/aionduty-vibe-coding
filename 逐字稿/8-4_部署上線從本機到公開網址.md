## Slide 154｜把專案推上 GitHub，它才不只在這台電腦

**畫面**
上方三格風險：硬碟壞了、換一台電腦、想傳給別人看。中間一塊定義 GitHub，分兩用（給你自己用、給部署平台用）。下面一段可複製的 Prompt。最後一句講你不用打 git 指令。

**逐字稿**

> 你前面做的那些存檔點，一個都沒有離開過你這台電腦。
>
> 這件事在三種情況下會變成問題。硬碟壞了，整個專案跟著沒了，沒有第二份。換一台電腦，要自己複製資料夾，還常常漏東西。想傳給別人看，總不能把整個資料夾壓縮寄過去。
>
> 解法是 GitHub，它就是專案的線上存放處。
>
> 推上去之後，那些存檔點會有一份在雲端。它有兩個用途，而且第二個對你更重要。
>
> 第一個，給你自己用：換電腦、找回舊版本、給別人看，都從這裡。
>
> 第二個，給部署平台用。這一句請記住，它是後面走不走得下去的關鍵：Vercel 不是讀你的電腦，是讀 GitHub。
>
> 所以沒有推上去，後面部署整條路就接不上，不管你本機跑得多好。
>
> 也就是說，推上 GitHub 不是備份而已，它是上線那條路的第一步。這件事你前面學 Git 的時候就看過一次了，這裡是真的要用了。
>
> 下面這段話可以直接複製：幫我把這個專案推到 GitHub。設成 private 還是 public 先問我。推之前先確認沒有把密碼或金鑰帶上去。
>
> 後面那半句不要刪掉，金鑰的事等一下會整頁講。
>
> 最後這句：你不用打任何 git 指令。它會自己建好、推上去，然後把網址給你。桌面版的 Code 頁籤右下角也有按鈕可以按。
>
> 但是有一件事它做不了，而且這是整堂課到現在第一次遇到，所以我要先講：它會停下來等你。
>
> 前面每一步都是它自己做完的，所以第一次推的時候畫面停住，多數人的第一個反應是「壞了」。沒有壞，是 GitHub 要確認你是本人。
>
> 三件事只有你做得到。第一，你要先有一個 GitHub 帳號。還沒有的話現在去 github.com 註冊一個，免費。
>
> 第二，第一次推的時候要在瀏覽器登入並且按同意。它會給你一段文字或一個連結，你照著做完，再回到對話框跟它說好了。這一步跟前面講部署授權是同一回事，你的帳號它代不了。
>
> 第三，這個專案要設成 private 還是 public，要你決定。剛才那句 prompt 已經叫它先問你。裡面有客戶資料或還沒公開的東西就選 private，之後隨時改得回來。
>
> 如果中間卡住、看不懂它在說什麼，最簡單的做法是把它給你的那段訊息整段貼回去，跟它說「我看不懂，告訴我現在要點哪裡」。

**這頁的教學意圖**：GitHub 有兩個用途，而「部署平台讀的是 GitHub 不是你的電腦」是後面走得下去的前提。
**預估時間**：4 分鐘（動手）

## Slide 155｜金鑰和客戶資料不能跟著推上去

**畫面**
兩個判斷並排。判斷一：public 還是 private，各附適用情境與一句限制。判斷二：哪些檔案不跟著走，列出幾個打叉的檔名。下面一塊介紹 `.gitignore`，並把它接回規則歸位的第一格。最後一句講 Vercel 綁一次就好。

**逐字稿**

> 判斷一，公開還是不公開。
>
> public，想當作品集給人看、想讓人試用的選這個。而且有一個限制：免費帳號要用 GitHub 自己掛網頁的話，只能選這個。
>
> private，跟工作有關、裡面有客戶的東西的選這個。這種要上線就接 Vercel，它吃 private。
>
> 一般的建議是：不確定就選 private，之後隨時可以改成公開，反過來很麻煩。
>
> 但請注意底下那一句：這一格選什麼，會決定你上線能走哪一條路。所以它是隱私的選擇，同時也是路線的選擇。等一下部署的時候會回來收這一題。
>
> 判斷二，哪些檔案不跟著走。畫面上打叉的那幾個就是不能推上去的。
>
> 為什麼要特別講，理由寫在下面：推上 public 之後才發現，刪掉也來不及，紀錄裡還留著。
>
> 這一句你在講安全邊界的時候聽過同樣的結論：金鑰一旦被推上去，就當它已經外洩了。
>
> 再來這一塊有一點里程碑的意思：這是你自己設的第一道機制。
>
> 前面學了那麼多「規則要用擋的不要用寫的」，這是第一次你真的擋了一個東西。
>
> 擋住這些檔案的東西叫 `.gitignore`。列在裡面的檔案，git 根本不會碰。這份清單是你自己列的，跟它說「幫我建一份 `.gitignore`，把金鑰、環境設定與客戶資料擋掉」它就幫你建好。
>
> 然後它把這件事接回去了：這就是前面規則歸位的第一格，會出事的交給機制，不要只寫進手冊。差別在於這次是程式在擋，不經過 AI 的判斷。
>
> 所以你現在手上有兩道同一種性質的防線：`.gitignore` 擋 git，`settings.json` 的 deny 擋 AI 讀。
>
> 兩個擋的是不同的人，所以兩個都要有。只擋一邊，另一邊照樣會把東西帶出去。
>
> 最後那句是在預告下一步：推上去之後，Vercel 綁一次 GitHub 就好。之後你只要說「幫我更新上線」，它推完，網站自己跟著換新版。

**這頁的教學意圖**：public／private 的選擇會決定上線路線；`.gitignore` 是學員親手設的第一道機制。
**預估時間**：4 分鐘

## Slide 156｜部署上線：Vercel 與 GitHub Pages 兩條路
**畫面**
上方一段長的 Prompt，底下一句解釋它為什麼那麼長。中間兩條路並排：Vercel（主色）與 GitHub Pages，各附網址長相、怎麼做、好處與限制。下面一塊「卡住的話，通常是這五件事」。最後一個綠色 Callout 講做完你手上會有什麼。

**逐字稿**

> 這一步要做的就是把網址生出來。
>
> 先看這段 Prompt，它比前面幾段都長：幫我把這個資料夾部署上線。先確認本機打開沒問題，推上 GitHub，再接部署平台完成部署。需要我去瀏覽器授權的時候停下來告訴我要點哪裡。完成後把網址給我，並且確認那個網址真的打得開。
>
> 底下那句解釋了它為什麼長：它把要做什麼、什麼時候該停下來問你、做完給你什麼都講完了。
>
> 這三段結構你應該認得，那就是這一章開頭那五個步驟的縮寫版。
>
> 中間那半句「需要我去瀏覽器授權的時候停下來告訴我要點哪裡」，就是 Human Gate。因為授權這件事它真的做不到，它沒有你的滑鼠。
>
> 兩條路。
>
> 第一條，Vercel。網址長得像「你的專案名點 vercel 點 app」。做法是到 vercel.com 用 GitHub 帳號登入，選你剛推上去的那個 repo，按 Deploy。
>
> 好處有兩個：之後每次 push 它會自己重新上線，你什麼都不用做；而且 repo 設成 private 也可以。
>
> 第二條，GitHub Pages。網址長得像「你的帳號點 github 點 io 斜線專案名」。做法是在 repo 的 Settings 裡找到 Pages，Source 選你的分支，存檔。
>
> 好處是不用再開一個平台的帳號。但限制寫在後面：免費帳號的 repo 要設成 public 才掛得上去。
>
> 所以 public 還是 private 那個判斷，在這裡收了。你選了 private，這條路就沒有了，要走 Vercel。
>
> 兩邊的後台都會改版，按鈕位置跟名字可能跟我講的不一樣。流程不會變：推上 GitHub、授權、選 repo、部署。
>
> 下面這一塊是這一頁的另外一半，而且老實說，它會比上面那段 Prompt 更花你的時間：卡住的五件事。
>
> 這五件不是你做錯，它們幾乎每個人都會撞到，因為它們都牽涉到你的帳號跟授權，那是它幫不了你的部分。
>
> 第一，它停下來叫我去瀏覽器點同意。這是正常的，第一次推上去要授權 GitHub，它沒辦法幫你點。點完回來跟它說「好了，繼續」。
>
> 第二，推不上去，說認證失敗。GitHub 現在不收密碼了。跟它說「幫我改用瀏覽器授權登入 GitHub」，它會帶你走一次。
>
> 第三，推上去了，但 Vercel 找不到我的 repo。repo 設成 private 的話，要在 Vercel 授權時勾選那個 repo。或是直接把 repo 改成 public。
>
> 第四，部署成功，但打開是一片空白。多半是 `index.html` 不在 repo 最外層，或程式裡寫死了你電腦上的路徑。把網址跟畫面截圖一起貼給它。
>
> 第五，我改了東西，但網址上還是舊的。改完要再存一次檔、再推一次，平台才會知道要重新上線。
>
> 第五條特別標著「這是最多人以為壞掉的地方」。請記住它，因為它不會有任何錯誤訊息，畫面上一片正常，只是內容是舊的，你會一直重新整理然後懷疑人生。
>
> 做完你手上會有什麼：一組別人打得開的網址，對方不用裝任何東西，手機也開得起來。
>
> 然後是驗收方式，這一段請務必照做，不要用電腦開一下就算數：用手機開一次那個網址，不要用你部署的那台電腦，也不要連同一個 wifi。
>
> 手機開得起來，才代表它真的在線上，不是只有你這台打得開。
>
> 用手機打開之後你會看到那件事：紀錄是空的。那不是壞掉，是你在加航行日誌那一頁就知道的代價。

**這頁的教學意圖**：真的生出網址；兩條路的差別由上一頁的 public／private 決定；五個卡點各自的處理方式。
**預估時間**：15 分鐘（動手，含實機）

## Slide 157｜手機打開，紀錄卻是空的

**畫面**
上方一組對照：你的電腦（12 趟、連續出勤 5 天）對上你的手機（0 趟、連續出勤 0 天），底下一句提問。中間一塊給答案，並引出資料庫，附一句起步用的 Supabase 提問。下面一塊列部署平台後台的四個地方。最後一個 amber 的 Callout：綠燈不等於打得開。

**逐字稿**

> 我猜你第一個反應是「是不是哪裡做錯了」。沒有，這一頁就是要讓你撞到這件事。
>
> 你的電腦上顯示 12 趟、連續出勤 5 天，手機上是 0 趟、0 天。同一個網址，同一個人，紀錄卻不一樣。
>
> 為什麼？這個答案你在加航行日誌那一頁就聽過了。
>
> 因為 `localStorage` 是記在那台電腦裡的。它從來沒有離開過你的筆電。
>
> 這一句要聽清楚：網站是上線了，資料沒有。
>
> 程式跟資料是兩件事。你上線的是程式，而資料從頭到尾都躺在你的筆電裡。
>
> 這就是你在加航行日誌那一頁選擇的代價。那時候 `localStorage` 讓你不用註冊、不用後端、不用付錢，一句話就有。它的代價現在來了。
>
> 要讓任何一台裝置打開都看得到同一份紀錄，就需要一個放在雲端、大家共用的地方。那個東西就叫資料庫。
>
> 你前面看過它的樣子（四張表那一頁），現在你知道它為什麼存在了。
>
> 真的要接的話，用 Supabase 這類託管服務，不用自己架資料庫，但會多出註冊帳號、金鑰、環境變數這些設定工。所以接資料庫留作延伸練習，這門課不走完那一段。要起步的話，畫面上那句可以直接用：幫我評估把這個計時器的紀錄改存到 Supabase 要做哪幾件事，先列步驟不要動檔案。
>
> 下面這一塊是實用的部分：部署交給它動手，但後台這四個地方你要自己看得懂。這四個是 Vercel 的叫法，換一家平台名字不一樣，但這四種東西都會有。
>
> 第一，Deployments，每一次上線的紀錄。綠燈代表建置成功，紅燈點進去看最後幾行紅字，那就是它失敗的原因。
>
> 第二，Build Logs，建置過程的完整輸出。網站打不開的時候，這裡通常已經寫清楚是缺了哪個套件或哪個檔案。
>
> 第三，Environment Variables，金鑰與密碼放這裡。本機跑得動、線上壞掉，第一個要查的就是這一欄有沒有漏設。
>
> 第三條記一下，它是「本機好好的，上線就壞」這種情況的頭號嫌疑犯。
>
> 第四，Functions 或 Runtime Logs，網站跑起來之後出的錯記在這裡。建置成功但畫面是白的，答案幾乎都在這一頁。
>
> 再來要把最容易搞混的兩件事分開，這個混淆會害你查錯方向：綠燈不等於打得開。
>
> Deployments 那顆綠燈說的是「檔案送上去、建置沒有失敗」。它不會幫你打開網站看一眼。
>
> 綠燈配上白畫面是最常見的組合，原因多半在 Functions 那一頁的錯誤紀錄裡。

**這頁的教學意圖**：程式上線不等於資料上線；後台四個分頁各自對應一種症狀；綠燈只代表建置成功。
**預估時間**：6 分鐘

## Slide 158｜部署前，叫它寫一份 DEPLOY.md

**畫面**
開場一段講為什麼要這一頁。中間一段可複製的 Prompt。下面四格：這個專案要幾個服務、資料存在哪裡、有沒有東西要一直醒著、哪些設定不能寫進程式碼。最後一個 sky 的 Callout 講驗收的那一句。

**逐字稿**

> 我不希望你把剛才那條路當成通用流程，然後下次照做撞得莫名其妙。
>
> 有資料庫、要定時跑、要長時間算的專案，走同一條路會在不同的地方卡住，而卡住的時候畫面上通常只有一句看不懂的紅字。
>
> 所以這一頁教的是一個動作：部署之前，先叫它寫一份診斷文件。
>
> 這個模式你已經做過兩次了，我點一下你就會發現它其實是同一招：前面叫它讀完專案寫 `CLAUDE.md`，後來叫它讀完手冊跑健檢，這次是叫它讀完專案寫部署診斷。
>
> 形狀都是「叫它讀完產出一份文件，你負責驗收」。之後遇到陌生的場合，你可以自己套這個模式。
>
> 那段 Prompt 可以直接複製，它要它回答四件事。
>
> 第一，這個專案要開幾個服務才跑得起來，各是什麼。
>
> 純前端只要一個地方掛靜態檔案。一旦有登入、有後端 API，那就是兩個要各自上線、各自付錢的東西。
>
> 第二，資料存在哪裡，換一台裝置還在不在。
>
> 存在瀏覽器裡的資料換一台裝置就不見了，手機打開紀錄是空的，就是這麼來的。
>
> 第三，有沒有東西需要一直醒著。
>
> 每天定時寄一封信、每小時抓一次資料，這種不能靠「有人打開網頁才跑」。它要一個不會睡著的地方。
>
> 第三條是這四條裡最容易被忽略的，因為它在本機測完全看不出來。
>
> 第四，哪些設定是金鑰或密碼，不能寫進程式碼。
>
> 金鑰與密碼要放平台的環境變數，不是放在檔案裡跟著推上去。這一條你已經用 `.gitignore` 擋過一次了。
>
> Prompt 裡還有兩句要注意。一句是「每一條都要指出你是看了哪個檔案下的判斷」。另一句是「最後列出照現在這樣直接部署會先撞到的三件事，從最早撞到的開始排」。
>
> 第一句話的用途就在這裡：它寫完之後，你要核的是這一句。
>
> 每一條都要指得出是看了哪個檔案下的判斷。指不出來的那幾條，是它照一般專案的樣子猜的，不是讀你的專案讀出來的。把那幾條退回去再問一次。
>
> 這個驗收方式你應該覺得很熟悉了。前面那個審查子代理用的是同一招：不要看它說什麼，要看它指不指得出來。

**這頁的教學意圖**：把「叫它讀完產出文件、你負責驗收」這個模式用在部署上；驗收的唯一問句是「你看了哪個檔案」。

### 1.【缺漏】Slide 158 的「哪些檔案不跟著走」列了檔名，但沒有說 `.gitignore` 是誰寫的

### 2.【矛盾】Slide 157 的 Prompt 寫死 `private`，但 Slide 158 才教怎麼判斷

- Slide 157 的可複製 Prompt 是：「幫我把這個專案推到 GitHub，**設成 private**。」下一頁整頁在教 public 跟 private 怎麼選。

- **建議**：兩種改法。把 Slide 157 的 Prompt 改成不指定（「設成 private 或 public 先問我」），或者把兩頁對調，先判斷再推。前者改動小，而且「先問我」本身就是這一章教的 Human Gate。
